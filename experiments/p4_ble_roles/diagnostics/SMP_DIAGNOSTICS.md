# Temporary SMP diagnostics

The copied IDF 5.5.5 `bt` component is isolated in `diagnostic-components/bt` with no symlinks. `smp-diagnostic.patch` and `smp-diagnostic-manifest.json` identify all changes. The production SDK and application were not edited by this diagnostic fixture.

After activating the pinned IDF environment, run `bash experiments/p4_ble_roles/private/build-p4-smpdiag.sh` from the repository root. This uses `-DEXTRA_COMPONENT_DIRS=<absolute diagnostic-components/bt>` and the separate `private/build-p4-smpdiag` directory. Its first run copies the existing P4 sdkconfig, then preserves the same profile/default layering as the normal build script. The application sources are read at build time; coordinate their freeze before running. Verify `project_description.json` and `compile_commands.json` select the copied `bt` component before flashing. This helper does not flash.

Only three component files differ: two source units add log calls and one header implements metadata logging. Both modified units passed `-fsyntax-only` with the existing P4 compiler command and copied component include paths. Relative BT source references remain within the full copied component; regular IDF dependencies remain supplied by the pinned SDK. No CMake/component dependencies were added.

`HW1_SMP_DIAG` stages distinguish `RX_PAIR_FAILED` (peer sent an SMP failure), `TX_PAIR_FAILED` (host sending a failure), `LOCAL_DHKEY_MISMATCH` (host rejected the peer check), and `LOCAL_DHKEY_MATCH`. Calculation and DHKey-check TX/RX stages provide context. A received error may precede or follow a local decision, so use event ordering. `RX_PAIR_FAILED` reports the incoming reason explicitly; the control block status may still reflect the previous state at that instant.

The logs include public/connection addresses and address types, HCI controller public BD_ADDR, global address policy, ACL presence/handle, role/state/association, public IO capability/authentication/OOB flags, encryption size and counters. They do not log cryptographic keys, shared secrets, check values, passkeys, nonces, randomizers or packet payloads. All normal comparison, failure, state-transition and crypto calls are unchanged. The added logging itself changes timing and must remain a diagnostic-only build.

Bluetooth `reason=88` in the existing authentication-complete warning maps to raw SMP reason `0x0b` (DHKey-check failure); it is not the HCI link-disconnect code. An app-layer AUTH or encrypted-command success does not establish BLE SMP success. P4 and S3 both select TinyCrypt and effective controller privacy support; S3 privacy support is derived from its controller/SoC rather than the visible P4 sdkconfig flag.

The initial P4 diagnostic image used `TX_PAIR_FAILED` even when this state-machine action completed with status zero without sending a failure. Interpret `TX_PAIR_FAILED reason=0` from that image as successful completion. The copied component now labels this case `PAIR_COMPLETE`, labels other local results `LOCAL_PAIR_RESULT`, and emits `TX_PAIR_FAILED` only inside the existing branch that actually sends a nonzero protocol failure. This changes logging only. The S3 diagnostic build uses these corrected labels. Run `bash experiments/p4_ble_roles/private/build-s3-smpdiag.sh` for the equivalent native control image; it seeds the S3 config and writes only `private/build-s3-smpdiag`.

The current diagnostic component additionally applies the five-file official TinyCrypt fix from Espressif commit `9fd7cb7e606a06111e1b14be7f4e00d77d9cf3dd`. See `tinycrypt-fix-provenance.json` for baseline/output hashes and `../idf-tinycrypt-9fd7cb7.patch` for the exact upstream change. `smp-diagnostic.patch` remains metadata-only. `smp-diagnostic-manifest.json` now describes both layers. Original files and the pre-fix manifest are retained in `smpdiag-before-tinycrypt-fix`; the completed S3 diagnostic binary predates this fix. The unrelated NimBLE submodule update was intentionally omitted. Hardware validation of the corrected P4 image remains separate from build success.
