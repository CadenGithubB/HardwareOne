# Known issues

Open problems that affect users, with the workaround where one exists. Entries leave when the fix
is on `main` and has a dated hardware check. Readiness item P1-12; the release gate in `RELEASING.md`
requires every open P1 defect to be listed here or fixed.

| Area | Problem | Workaround | Status |
|---|---|---|---|
| ESP32-P4 (P4X-EYE, Waveshare) | Occasional reboot (`reset=panic`, heap-corruption abort or a load fault in the VFS table) a few seconds after a speech session ends or when one starts with the radio on. Root cause found on 2026-11-07: the CPU clock is switched (400 MHz during a session, lower afterwards) without the MSPI/PSRAM speed-mode sync, so PSRAM transfers land at the wrong address. | Keep the CPU at a constant clock (Performance power mode) until the fix lands. | Fixed on this line (clock switch with the MSPI sync and memory quiesce, `System_Power.cpp`), verified on the bench P4X-EYE for 300 clock toggles and 40 fast sessions, and on 2026-11-08 for eleven 7.5-10.5 minute continuous sessions plus 60 fast start/stop cycles (no panic, no dropped audio). See `docs/P4X_PANIC_HUNT_20261107.md` and `docs/STT_MIC_PATH_INVESTIGATION_20261107.md` section 6. |
| ESP32-P4 | `task_wdt: IDLE0` register dumps ~8 s after boot and right after a Wi-Fi join: the main loop holds core 0 for 7-9 s (LOOPHEALTH IO stall). Cosmetic, the watchdog does not panic. The opt-in watchdog soak build (`--wdt-soak`) uses a 20 s timeout to clear it. | None needed. | Open; a ticket, not a release blocker. |
| Local STT (P4) | A speech session occasionally fails half a second after starting with `Microphone audio loss detected` (logged as `warm-up failed: Cancelled`): 4 of 40 fast start/stop cycles on 2026-11-07, 1 of 20 on 2026-11-08, all with the bench raw recorder (`sttraw`) armed. The onboard mic's 256 ms DMA ring overflowed before the session's first read, while the recorder opened its SD file, and the strict loss rule counted that pre-session audio. | Start it again. | Fixed on this line: the loss baseline is taken just before the first read (`TL capture_preroll_overrun` logs a pre-read drop); 40 of 40 fast cycles with `sttraw` armed on 2026-11-08. |
| Local STT (P4) | Quiet speech more than about a foot from the microphone was not captioned: the loudness onset rule needed speech ~10 dB above the room. | None needed on this line. | Addressed by the automatic defaults: `sttautogain 1` (STT's own gain, agreed over sessions, and a 120 Hz high-pass) and `sttdecisionpre 97`, which since the speech repository's version 3.1 port is the level-robust onset (host replay with the shipped model: 1,568 -> 1,103 word errors over 2,614 words against the raw level only; not yet measured on the device). The device figures in `docs/STT_MIC_PATH_INVESTIGATION_20261107.md` sections 6-7 (quiet read speech at 1 ft captioned 8/8 instead of 0/8, all-WER 72 -> 44-48%) were measured with the earlier pre-emphasis judge the port replaced. Background talkers are captioned more often. The G2 glasses mic has its own profile (`sttg2*`, 97 by default); the onset has not been scored on glasses audio yet. |
| R1 ring health history | A forged SNTP reply (plain SNTP is trusted as it arrives) moves the device clock, and the device used to push that clock to a connected ring, which keys its daily pages off it; days stored with a far-future date push the oldest of the 30 kept days out. Narrowed on this line: once the clock has been set in this boot (RTC, NTP, `timeset`, CM5), an NTP reply that moves it by more than a day is not passed to the ring. The ring keeps the earlier clock until `timeset`, a local time source, an NTP reply that agrees with the earlier clock, or a restart; a TIME event is logged and `time` shows the hold. Still open: the first sync after a start without a clock is taken as it arrives, and a forged clock in force at a restart reaches the ring (on boards with an RTC the forged time is written to the RTC and trusted after the restart). A clock that really was wrong by more than a day and is corrected by NTP reaches the ring only after `timeset` or a restart. | Use a trusted network. After a TIME event `ntp moved the clock by more than a day`, check the time and run `timeset` if it is right. | Narrowed on this line (readiness G-79); host-tested, not yet tested on hardware. |
| Debug logging | Two persistent owners of the debug mask: the system-log autostart re-applied the saved `log start flags=` mask on every boot, so a category turned off for good with `debug<x> 0` came back after a reboot. | None needed on this line. | Fixed on this line (readiness Section 8): a persistent `debug<x> 0\|1` (and the sub-flag commands) also updates the saved system-log mask when one is saved, so the two agree. `temp` changes stay runtime-only and still end at the reboot. Host-tested (`system_log_status`) and built for every board; no hardware check yet. |
| Host test suite | The four browser suites (`map_live_browser`, `g2_status_browser`, `sensor_mic_card`, `logging_system_config_browser`) are disabled without Node.js; `ctest` reports them as not run. | Install Node.js (`HW1_NODE_EXECUTABLE` for a custom path) before the release gate. | By design; documented in `RELEASING.md`. |
| OTA | The recovery OTA layouts have no dated PASS on a current image (last FeatherS3 record 2026-08-05 at v0.99.8; Feather V2 2026-08-25). | Cable update until the release bench run records PASS lines. | Scheduled for the release candidate bench (readiness P0-6). |
| OTA | On the recovery OTA layout `idf.py erase-flash` (and `erase_flash`) was not refused, unlike the stock `flash` and erase targets: idf.py runs esptool directly, so the whole chip was erased, including the `factory` recovery updater, NVS (the recovery credential) and `littlefs`. | To wipe only the filesystem use `littlefs-flash` (`encrypted-littlefs-flash` on `feathers3_fe`); to replace only the updater use `factory-flash` (`encrypted-factory-flash`). For a deliberate full erase set `HW1_ALLOW_FULL_ERASE=1`, then provision again with `migration-flash` (`encrypted-migration-flash` on `feathers3_fe`) and `setpin` or `otapin`: `docs/OTA_DEVICE_SETUP.md`, "Known rough edges". | Fixed on this line (readiness G-65): the project's `idf_ext.py` refuses both spellings from a recovery-OTA build directory unless `HW1_ALLOW_FULL_ERASE=1` is set. Host-tested (`tools/ota/tests/test_idf_ext.py`) and run against ESP-IDF 5.5.5's idf.py with no board attached. Not covered: a direct `esptool.py erase_flash`, the separate `updater/` project, and a build directory configured for another layout than the attached device. |
| Account recovery | A single-account device cannot recover a lost admin password in place: `factoryreset` needs a super-admin login. | Keep a second admin, or erase the LittleFS region over the cable (settings and captures are lost). | Documented in `docs/COMPATIBILITY.md`; first-time setup now refuses names that would lock the device out. |
| Backup restore | "Import from Backup" is not one transaction. Every file is staged and checked first, then moved into place one rename at a time, so a power cut during that last step can leave a mix of old and new files. `users.json` goes last, so until it lands the device still boots into first-time setup. | Run Import from Backup again with the same bundle after the reboot. | By design (per-file promotion); readiness G-68. |
| Waveshare ESP32-P4 Touch LCD 5 | Experimental board: bring-up acceptance records exist, but no soak or OTA qualification. | Use as a development board. | Experimental in the support matrix. |
| Seeed XIAO ESP32S3 (base, no Sense) | Was not selectable: every ESP32-S3 build defined `XIAO_ESP32S3_SENSE_ENABLED`, so a base XIAO got the Sense build, whose camera, microphone and SD card expect the Sense expansion board. | Build the saved configuration: `python3 tools/build_config.py build xiao-base`. | Fixed on this line (readiness G-63): the flag is set only in `System_BuildConfig.h` and its override headers, and `configurations/xiao-base.json` selects the base board (no camera, microphone or SD card; user LED on GPIO 21). Host-tested and the image builds; not yet run on a base board. |
| WiFi | After a lost connection the device retried only the network that dropped, so a device carried to another saved network stayed offline until `openwifi` or a reboot. | None needed on this line. | Fixed on this line (readiness G-66): when a connection is lost without a command asking for it and the device is still offline 60 s later, it hunts across all saved networks, and again after 60 s, 120 s and then every 300 s until one answers. Host-tested (`wifi_rehunt_policy_tests`) and built for every board; no hardware check yet. Not covered: a boot that never connected (run `openwifi`). With one saved network nothing changes. With two or more, once the first hunt has failed a router that comes back is rejoined at the next hunt instead of within seconds. `wifidisconnect`, `closewifi` and `wifiautoreconnect 0` stop the hunting. |
| WiFi | `openwifi` connects synchronously on the shared command executor, so while it runs every other command, from every transport, waits behind it. With saved networks that associate but fail (wrong password, weak link), plain `openwifi` (the best-network hunt, also run by the web Wi-Fi "save and connect" button) holds it for up to about 150 s (the hunt budget; each network gets up to three 35 s attempts). `openwifi --index` and `--saved-id` give the chosen network the same three 35 s attempts (about 110 s) and then up to about 50 s to rejoin the previous network, so up to about 160 s. A network that is out of range gives up after a few seconds per attempt. A web caller gets a timeout after 60 s while the attempt continues. | Wait for it to finish; the console shows each `Connecting to` / `Retrying` line. An `openwifi` typed on the serial console stops at the next key press. Use `--index <n>` for a network you know is in range, so only that one is tried. | Deferred past 1.0 (readiness G-87). |
| Recording | A recording cut by a power loss or reset was lost: the WAV header got its length only when the recording stopped, and nothing was flushed meanwhile. | None needed on this line. | Fixed on this line (readiness G-69): a manual recording is committed to storage every 5 s, and the next boot completes the header of an interrupted recording (it is logged as `repaired ...`), so a power cut loses at most about the last 5 s. Host-tested (`mic_wav_repair`) and built for every board; no hardware check yet. |
| Automations | Every fire of an interval trigger rewrote `/system/automations.json` to save its next run time, so intervals of a few seconds wore the flash over months. | None needed on this line. | Fixed on this line (readiness G-70): an interval shorter than 15 minutes keeps its next run in memory and no longer writes the file when it fires (up to 16 such triggers; further ones still write). After a restart such a trigger first fires one interval after the automations start. Host-tested (`test_automation_scheduler.py`) and built for every board; no hardware check yet. |
| Web UI | The web server has one worker task, so handlers run one at a time: an upload or a slow client can hold the UI for up to 20 s (HTTPS) or 30 s (HTTP) socket timeouts, and each events (SSE) poll holds the worker for about 0.6 s. | Avoid other web actions during uploads; close idle tabs. | Open (readiness G-72). |
| Power (FeatherS3) | In Performance, Balanced or UltraSaver mode the idle downclock changes the CPU clock, which once collided with in-flight sensor reads such as GPS (fixed in v0.98.8: the switch now drains the I2C buses first). The ESP32-S3 switch path changed again on 2026-11-08 (MSPI speed-mode sync) and is host-tested only; a 30-minute bench soak with GPS running is pending. | Adaptive (the default) or Locked, which do not change the clock at idle. | Open (readiness G-74, G-48). |
| ESP-NOW security | Session keys, the rekey private key, the bond token and the decrypt buffer live in PSRAM, so with flash encryption off they can be read with bench (physical) access to the device. | Enable flash encryption (for example `feathers3_fe`); re-bond the other devices after one is lost. | Open (readiness G-77). |
| Time | Plain SNTP replies are trusted as they arrive (lwIP steps the clock before the firmware sees them), so an attacker on the same LAN can set the device clock, moving timed automations and timestamps. | Use a trusted network. | Open (readiness G-79). |
| Device handover | `factoryreset` removes the accounts, their settings and transcripts, and the phone-pipe code; saved WiFi networks, MQTT and LLM endpoint credentials, other Bluetooth bonds and the ESP-NOW identity and keys stay. `factoryreset all` (serial console, super admin) now erases those as well: after the reboot the whole internal filesystem and NVS are erased before anything is mounted, then first-time setup runs. Not erased: the SD card apart from `/sd/stt/u*`, and on boards with a radio companion chip (P4) the WiFi network that chip last joined. The `otapin` recovery credential is erased too and must be set again. | Before giving a device away run `factoryreset all` on the serial console and remove or wipe the SD card. Until the command has been checked on hardware, the erase over the cable (`tools/build_board.sh <board> -p PORT erase-flash`; from a recovery-OTA build put `HW1_ALLOW_FULL_ERASE=1` in front) is the proven way; see the User Guide, Account recovery. | Fixed on this line by `factoryreset all` (readiness G-80); host-tested and compiled for every board, not yet run on hardware. |
