# Code Health Sweep

Read-only audit. **No code was modified.** General robustness findings that are neither
ESP32-platform-specific nor auth-specific.

> **Verification caveat.** Findings were produced by independent finder agents and then attacked by
> adversarial verifier agents instructed to refute them. In aggregate the verifiers upheld 398 and
> refuted 84 — roughly a 17% refutation rate. The run was interrupted and resumed several times, and
> the per-finding link between a verdict and its finding was not preserved in the journal, so the
> refutations could not be subtracted from individual entries. **Treat each finding's own
> `Confidence` field as the primary signal, and expect roughly one in six of these to not survive
> closer scrutiny.** Duplicate independent reports (noted inline) are a stronger signal.

### Core system / tasks — 14 findings (1 critical/high)

### [HIGH] certgen reports "certificate generated and saved" without checking either PEM write
- **Where:** `components/hardwareone/System_WiFi.cpp:1541`
- **What:** After a successful open, the cert is written with `cf.print((const char*)certPem)` (:1541) and the key with `kf.print((const char*)keyPem)` (:1549), both return values discarded, both files closed with the void close(). Control then falls into the unconditional success snprintf at :1552 and `systemEventPost(SYSEVT_CERT_GENERATED, ...)` at :1561. The two files are also written non-atomically with no staging and no rollback.
- **Why it matters:** A PEM cert plus an RSA-2048 key is roughly 3-5 KB. On a filesystem with less than that free, one or both writes short-write, the command still returns "Self-signed RSA-2048 certificate generated and saved: ..." (stamped "OK: " by stampOkStatus, audited `-> OK`), and SYSEVT_CERT_GENERATED fires. The user enables httpsEnabled 1 and reboots; the HTTPS server fails to start on an unparseable key with no connection back to the certgen that reported success. A crash between :1542 and :1549 leaves a cert that does not match the key with the same reporting.
- **Confidence:** CONFIRMED — board: all (ENABLE_HTTPS); prior art: recon_persist.md §6.3 flags the two-file non-atomicity; the success-on-failure report is separate.
- **Direction:** Compare each print() against strlen of its PEM buffer, write both to .tmp files and rename only after both succeed, and route failures to the existing `goto cleanup` path so the gDebugBuffer error text (and the Error: prefix) is what the user sees.

### [MEDIUM] AVI recorder performs zero write checks and advances its frame/size counters from intent, so a failed recording is reported as a successful one
- **Where:** `components/hardwareone/System_Camera_Video.cpp:229`
- **Also:** components/hardwareone/System_Camera_DVP.cpp:2148-2150
- **What:** writeFrameChunk() (:221-249) issues three unchecked s_file.write() calls and then unconditionally does `s_moviPayloadBytes += 8 + len` and `s_frameCount++`. finalizeAndClose() (:251-297) issues eight more unchecked writes (idx1 chunk + four header patches), logs "Recording finalized: %s (%u frames, %u bytes)", and posts SYSEVT_VIDEO_SAVED. startVideoRecording() gates on VFS::isSDWritable() and a successful create but performs NO free-space check at all (unlike ImageManager, which has one), and per-frame write failures never call VFS::noteSDWriteFailure — that is only done on open failure (:391).
- **Why it matters:** An SD card that fills mid-recording (the normal outcome for a multi-minute capture) silently drops frames while s_frameCount and s_moviPayloadBytes keep incrementing. finalizeAndClose then patches avih.dwTotalFrames and the movi LIST size from those inflated counters, producing an AVI whose declared structure does not match its bytes. `camerarecord stop` answers "OK: Recording stopped — /sd/videos/VID_x.AVI (N frames)" with the phantom N (System_Camera_DVP.cpp:2148-2150), and isSDWritable() still reports the card healthy.
- **Confidence:** CONFIRMED — board: XIAO ESP32S3 Sense only (ENABLE_CAMERA_SENSOR)
- **Direction:** Check the writes in writeFrameChunk; on a short write stop the recording, mark the card via VFS::noteSDWriteFailure, and let finalizeAndClose record the real frame count. Add a free-space gate in startVideoRecording matching ImageManager's MIN_FREE_SPACE_BYTES pattern.

### [MEDIUM] CommandArgs::value()/hasKey() match keys by unanchored substring search, so one key silently steals another's value
- **Where:** `components/hardwareone/System_Command.cpp:485`
- **Also:** components/hardwareone/System_Automation.cpp:998-999 (dayofmonth/month), :1007+1009 (condition/on), :1001+1004 (delayms/bootdelayms), :1151 and :1436/:1515/:1628/:1878 (`a.value("id")` — matched by any earlier value containing the bytes "id="); components/hardwareone/System_Command.cpp:527 (hasKey, same unanchored search)
- **What:** `CommandArgs::value(key)` builds `needle = key + "="` and locates it with `raw_.indexOf(needle)` (System_Command.cpp:486-487). There is no token-boundary check on either side: any occurrence of the literal bytes `<key>=` anywhere in the raw argument text wins, including inside a longer key name or inside another key's value. `hasKey()` (:527) has the same flaw.

`cmd_automation_add` reads 19 keys through this API (System_Automation.cpp:992-1010). Several of the key names are suffixes of one another:
  * `"month="` is the last 6 characters of `"dayofmonth="`
  * `"on="` is the last 3 characters of `"condition="`
  * `"delayms="` is the last 8 characters of `"bootdelayms="`

Because `indexOf` returns the FIRST hit, whichever of the pair appears earlier in the command line wins. The shipping web Automations UI emits `dayofmonth=` immediately before `month=` in both builders it has (WebPage_Automations.h:1366-1367 for create, :1626-1628 for import), so the collision is not hypothetical — it is the normal path.
- **Why it matters:** User configures a yearly automation in the web UI: recurrence=yearly, day 15, month July. The page builds:

  automation add name=X type=atTime time=08:00 recurrence=yearly dayofmonth=15 month=7 commands="..." enabled=1

`a.value("dayofmonth")` correctly returns "15". `a.value("month")` then does `raw_.indexOf("month=")`, which matches the `month=` embedded in `dayofmonth=` (an earlier index), so `monthOfYear` is also "15".

Serialization at System_Automation.cpp:1288-1291 gates on `moy >= 1 && moy <= 12`; 15 fails, so the `"month"` key is omitted entirely from automations.json. On the next scheduler pass `parseTrigger` (System_Automation.cpp:2237-2241) reads `int moy = trig["month"] | 0` and returns false because `moy < 1` — the trigger is discarded and **the automation never fires, silently, with no error anywhere** (the `automation add` call returned OK).

If the user had picked a day of 1-12 instead, the automation is created successfully but fires in the wrong month (month := dayOfMonth). The `Trigger::YEARLY` branch of `nextFire` (System_Automation.cpp:2381-2413) has no way to detect this.

The `condition=`/`on=` pair is the same defect on the CLI: `automationadd name=x type=event condition=BATTERY<20 on=battery_low ...` (a documented-legal argument order — the usage string imposes none) makes `a.value("on")` return the condition's value, and the command fails with a confusing "event requires on=<kind>" listing every valid kind (System_Automation.cpp:1120-1128).
- **Confidence:** CONFIRMED — independently reported by 2 finders
- **Direction:** Anchor the search: only accept a `<key>=` occurrence that starts at offset 0 or is immediately preceded by a space (and, for quote-safety, is not inside a quoted token). The parser already computes quote-aware token offsets in `parse()` — reuse `offsets_`/`quoted_` instead of scanning `raw_`. A cheap interim guard is to sort the collision-prone key lookups longest-first and blank out each match before the next lookup.

### [MEDIUM] loglevel debug / debughttps verbose set ESP_LOG_DEBUG on IDF tags that CONFIG_LOG_MAXIMUM_LEVEL=3 has already compiled out
- **Where:** `components/hardwareone/System_Debug.cpp:559`
- **Also:** components/hardwareone/System_Settings.cpp:822,830-833; components/hardwareone/System_Debug.cpp:1216-1221
- **What:** `CONFIG_LOG_MAXIMUM_LEVEL=3` with `CONFIG_LOG_MAXIMUM_EQUALS_DEFAULT=y` (sdkconfig:2084-2087) and `CONFIG_LOG_MASTER_LEVEL` unset (sdkconfig:2092). `LOG_LOCAL_LEVEL` therefore resolves to CONFIG_LOG_MAXIMUM_LEVEL = ESP_LOG_INFO for every ESP-IDF translation unit (esp-idf/components/log/include/esp_log_level.h:57), and `ESP_LOGD`/`ESP_LOGV` expand to `if (ESP_LOG_ENABLED(level))` with a compile-time-false condition (esp_log.h:163-165, esp_log_level.h:86) — the call sites are removed by the compiler. Meanwhile cmd_loglevel maps `loglevel debug` to `espLevel = ESP_LOG_DEBUG` and applies it via `esp_log_level_set("wifi"/"wifi_init"/"phy_init", espLevel)` (System_Debug.cpp:559, 563-566), applySettings does the same (System_Settings.cpp:822, 830-833), and `applyHttpsLogLevels(true)` sets ESP_LOG_DEBUG on esp-tls-mbedtls / esp_https_server / httpd / httpd_txrx (System_Debug.cpp:1216-1221).
- **Why it matters:** `esp_log_level_set` only lowers a *runtime* threshold; it cannot resurrect call sites that were never compiled. So `loglevel debug` behaves identically to `loglevel info` for every ESP-IDF framework tag, and the documented contract at System_Debug.cpp:1214-1219 ("verbose=false -> NONE, verbose=true -> DEBUG") is half dead — the NONE direction works, the DEBUG direction can never emit anything beyond INFO. A developer chasing a WiFi association or TLS handshake failure turns on the exact knob that is supposed to help and gets no additional output, with nothing indicating why.
- **Confidence:** CONFIRMED
- **Direction:** Either raise CONFIG_LOG_MAXIMUM_LEVEL to 4 (DEBUG) in sdkconfig.defaults — costs flash for the retained ESP_LOGD strings but makes the knob real — or clamp the app-side mapping to ESP_LOG_INFO and say so in the command help so the surface stops advertising a level it cannot deliver.

### [MEDIUM] HTTPS certificate and private key are written as two independent truncating writes with no return checks, no staging and no rollback
- **Where:** `components/hardwareone/System_WiFi.cpp:1535`
- **What:** `certgen` opens `/system/certs/https_server.crt` in "w" mode, does `cf.print((const char*)certPem); cf.close();` with no return check and no flush, then separately opens `/system/certs/https_server.key` in "w", `kf.print(...)`, `kf.close()`. If the key file's open fails the code does `goto cleanup` — after the certificate has already been overwritten. This is the only two-file invariant writer in the tree; every other paired-state writer uses tmp+rename on a single file.
- **Why it matters:** A reset, a full filesystem, or an open failure between the two writes leaves a new certificate paired with the previous private key. The mismatch is not detected at write time (no RVs are checked) and surfaces at the next boot as an HTTPS server that will not start, on a device whose only recovery path may be the web UI it just disabled. Under the undetectable-commit finding above, a full filesystem produces the same mismatch with no error at all.
- **Confidence:** CONFIRMED — board: all with ENABLE_HTTPS; prior art: recon_persist.md #3
- **Direction:** Write both PEMs to .tmp siblings, verify both wrote their full length, then rename both — key first so a crash between renames leaves the old (self-consistent) pair or an unusable-but-detectable new key rather than a silent mismatch.

### [LOW] g2ParseEnvelope underflows the payload length when the declared fragment length is 0 or 1
- **Where:** `components/hardwareone/System_G2_Protocol.cpp:66`
- **What:** `g2ParseEnvelope` computes `const size_t pbLen = isLast ? (size_t)declared - G2_ENVELOPE_CRC_LEN : (size_t)declared;` where `declared = in[3]` is an unsigned wire byte and `G2_ENVELOPE_CRC_LEN` is 2. For declared==0 or 1 this wraps to SIZE_MAX-1 / SIZE_MAX, and the next statements are `pb[pbLen]`, `pb[pbLen+1]` and `g2CrcCcittFalse(pb, pbLen)` (:72-73) — an unbounded read loop. Nothing between :57 and :66 rejects declared < 2; the only length guards are `len >= 10` (:53) and `declared + 8 <= len` (:60), both of which a 10-byte frame with declared=0 satisfies.
- **Why it matters:** Latent only because of an accident in the single caller. `handleNotify` (G2_Glasses.cpp:2104-2148) sets `t.rxExpected = G2_ENVELOPE_HDR_LEN + declared` and calls `g2ParseEnvelope(t.rxBuf, t.rxExpected, &env)`, so declared==0 yields len==8 and declared==1 yields len==9, both of which the `len < 10` check at :53 rejects before the subtraction. The function is exported in System_G2_Protocol.h:237 and its own guards read as if they were sufficient, so any second caller that passes the true buffer length rather than 8+declared (a relay, a capture replayer, a unit test) turns a 10-byte BLE notify from the paired glasses into an immediate multi-gigabyte read.
- **Confidence:** CONFIRMED — independently reported by 2 finders; board: all (ENABLE_G2_GLASSES)
- **Direction:** Add `if (isLast && declared < G2_ENVELOPE_CRC_LEN) return false;` before computing pbLen, so the function's contract does not depend on its caller's arithmetic.

### [LOW] `checkBusRecoveryNeeded()` bypasses the recovery cooldown that the BUS_ERROR path is careful to honour
- **Where:** `components/hardwareone/System_I2C_Manager.cpp:490`
- **What:** `recordError`'s BUS_ERROR branch consults `mgr->busRecoveryThrottled(bus)` before recovering (lines 873-878), with a 5 s `BUS_RECOVERY_COOLDOWN_MS`. The NACK and TIMEOUT branches instead call `checkBusRecoveryNeeded()` (lines 823, 852), which calls `performBusRecovery(b)` at line 490 with no throttle check at all.
- **Why it matters:** Once a bus has >=3 registered devices and a real fault degrades >66% of them, every subsequent `recordError` from any of those devices re-enters `checkBusRecoveryNeeded()`. `performBusRecovery` does clear `degraded` for the whole bus (lines 414-419), so the cascade must rebuild before it re-fires — but each device only needs 3 more consecutive failures, which on a genuinely dead bus is one poll cycle each. The result is repeated ~70 ms teardowns (pollPause + `wire->end()` + 9 bit-banged clocks + `delay(50)` + re-begin) with the bus mutex held, at whatever the poll cadence is, instead of once per 5 s. The BUS_ERROR path was explicitly protected against exactly this (comment at lines 866-871); the sibling path was not.
- **Confidence:** CONFIRMED
- **Direction:** Move the `busRecoveryThrottled(b)` check into `checkBusRecoveryNeeded()`'s per-bus loop (or into `performBusRecovery` itself, with an explicit `force` flag for the operator-initiated `i2creset` path that the header comment at System_I2C_Manager.h:253-255 says must ignore the cooldown).

### Sensors / I2C / HAL — 3 findings (1 critical/high)

### [HIGH] Sensor-log row writes are unchecked while the header write is checked, so a full filesystem silently rotates real data away while recording nothing
- **Where:** `components/hardwareone/System_SensorLogging.cpp:909`
- **Also:** System_SensorLogging.cpp:930,942,948,951 (rotate remove/rename returns all discarded)
- **What:** In the append hot path the header goes through writeHeaderChecked() and its failure aborts the write (System_SensorLogging.cpp:901-908), but the two lines immediately after — `f.write((const uint8_t*)line, len);` and `f.write('\n');` (:910-911) — discard their returns. The code then unconditionally advances gSensorLogLastWrite, writeCount, log_writes and, critically, `gApproxSizeBytes += (len + 1);`.
- **Why it matters:** gApproxSizeBytes is the rotation trigger (:921). When writes are failing, the counter still climbs, so rotation fires on schedule: it deletes <path>.N (the oldest rotation), shifts .i→.(i+1), and renames the base file to .1 (:925-951, all four VFS calls also discarding their returns). The net effect on a full filesystem is that the logger destroys previously-captured sensor data at a steady rate while adding nothing, and reports success the whole time — `log_writes` increments and the DEBUG_LOGGER line prints "wrote %d bytes" using strlen(line) rather than anything the filesystem returned. The asymmetry is self-evidently unintended: the author applied the checked-write pattern one statement earlier.
- **Confidence:** CONFIRMED
- **Direction:** Have the row write use the same checked form as writeHeaderChecked, abort the append and bump log_open_fail on a short write, and do not advance gApproxSizeBytes for bytes that were not accepted.

### [MEDIUM] Sensor-log append discards `f.write()` but still advances `gApproxSizeBytes`, so phantom growth on a full filesystem drives the rotation cycle over real data
- **Where:** `components/hardwareone/System_SensorLogging.cpp:901`
- **What:** The append block does `f.write((const uint8_t*)line, len); f.write('\n'); f.close();` at :901-903 with both returns discarded, then unconditionally `writeCount++; log_writes++; gApproxSizeBytes += (len + 1);` at :905-907. The rotation trigger at :922 is driven purely by `gApproxSizeBytes > gSensorLogMaxSize`. Note the header write on the same path *is* checked (`writeHeaderChecked` at :900), which makes the unchecked row write look like an oversight rather than a decision.
- **Why it matters:** `resolveOverflowPath` correctly passes `gSensorLogMaxSize` as the reserve (:891-893), but when no SD card is mounted the latch falls back to the primary path and accepts silent loss by design (System_VFS.cpp:628-631).
