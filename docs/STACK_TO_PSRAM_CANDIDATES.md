# Stack → PSRAM candidates (list-only audit)

Large **stack-allocated** buffers that could be moved off task stacks into PSRAM, to
free internal DRAM and reduce stack-overflow headroom pressure. **Inventory only — no
changes made, nothing scaled down.** Generated by a fan-out scan + adversarial verify
of `OLED_*` and `Web*` sources.

## How to read this

Two move approaches, driven by whether the enclosing function is **reentrant** (can two
contexts execute it at once):

- **`static-psram`** — a file-static `EXT_RAM_BSS_ATTR` buffer. Cheapest move (no per-call
  alloc), but **only safe when the function runs on a single task** (never concurrent).
  All OLED render/input paths qualify (one OLED task).
- **`per-call-heap-spiram`** — `heap_caps_malloc(n, MALLOC_CAP_SPIRAM)` + `free` per call.
  Needed when the function can run concurrently, since a shared static buffer would race.

### ⚠️ The one decision that changes half this list

Most web handlers are marked `per-call-heap-spiram` **conservatively**. The ESP-IDF
`esp_http_server` default runs **a single task** that services sockets sequentially — if
that's how it's configured here (worth confirming in the `httpd_config_t` setup in
`WebServer_Server.cpp`), then **every web handler is effectively non-reentrant** and the
whole web set collapses to the cheaper `static-psram` approach. If concurrent request
handling is ever enabled, the reentrant ones must use `per-call-heap-spiram`. **Confirm
the httpd task model before implementing the web side.**

### Not overflow risks by themselves (but still DRAM to reclaim)

- The httpd task stack is ~7680 B, so even the 2 KB `body[2048]` frames aren't overflows
  on their own — the value here is **reclaiming internal DRAM**, not just stack safety.
- Naive per-function sums mislead: mutually-exclusive `if/else` branch buffers (e.g.
  `handleSensorData`, `handleGPSTracksAPI`) get **overlapped stack slots under `-O2`**, so
  they do *not* add up. The "hot functions" table below already accounts for this.

# Part 2 — System functions, tasks & heap

Sweep of `System_*`, `Bluetooth.cpp`, `BLE_*`, `G2_*`: **101 stack candidates (~55 KB)**,
**46 tasks (~248 KB of stack)**, **47 notable heap allocations**.

## 🔴 Finding 1 — task-stack accounting is 4× wrong (VERIFIED)

**ESP-IDF's `xTaskCreate` stack depth is in BYTES**, not words (a documented deviation from
vanilla FreeRTOS; `StackType_t` is `uint8_t`). The codebase assumes words throughout:

- `System_TaskUtils.h` — `CMD_EXEC_STACK_WORDS = 8192; // ~32KB` → **actually 8 KB**
- `System_TaskUtils.cpp:148` — `stackBytes= String(usStackDepth * 4)` → **reports 4×**
- `System_TaskUtils.cpp:565` — `allocBytes = kt.stackWords * 4`, `freeBytes = watermark * 4`

**Sanity check that settles it:** the raw values sum to **~248 KB**, which fits the ESP32-S3's
512 KB SRAM. The ×4 reading would be **~992 KB — the device could not boot.** So the raw
numbers are bytes and the `_WORDS` naming + `~NNKB` comments + `*4` reporting are all wrong.

**Why this matters for "tasks not overflowing":** every task has **¼ the headroom its comment
claims**. `thermal_task` believes it has ~24 KB; it has **6144 B**. Several sizing comments cite
observed HWMs *larger than the real allocation* (e.g. `g2_tap_disp` "peak ~11.5 KB" vs a
6400 B stack) — impossible, and a symptom of the same mis-scaling. The *percentages* in
`System_TaskUtils.cpp:565` stay correct (numerator and denominator both ×4); only absolute
bytes are inflated. **Re-measure before trusting any stack-sizing rationale in this repo.**

## 🔴 Finding 2 — MQTT thermal silently never publishes (VERIFIED, real bug)

`System_MQTT.cpp:1048` — `char thermalJson[2048];` → `thermalBuildDataJSON(thermalJson, 2048)`.
The builder (`i2csensor_mlx90640.cpp:1113-1131`) loops **768 pixels** writing `"%d,"` each
(~3.8 KB needed). On overrun it does `return 0`, and the caller gates on `if (len > 0)` — so
whenever the thermal sensor is actually *running*, thermal is **silently dropped from the MQTT
payload**. (Sensor-stopped returns a short JSON that fits, which masks it.) Fix the size
contract — this is a correctness bug, not a placement question.

## Tasks (46 tasks, ~248 KB) — ⛔ PSRAM task stacks are RULED OUT

> **Decision (2026-07-16): task stacks stay in internal DRAM.** Moving FreeRTOS task stacks to
> PSRAM has **historically been bad on this hardware**. The feasibility analysis below is
> retained as reference only — **do not pursue the relocation.** A task stack in PSRAM pays
> PSRAM latency on *every* frame push/pop and local access (not just one buffer), and the
> failure modes (cache-disabled flash ops, IRAM ISR frames landing on the stack) are hard to
> prove absent by inspection.
>
> Correction to an earlier note in this doc: `G2_Page_TestSuite.cpp:1072` is **not** a precedent
> to copy — it's a *fallback that only fires when the internal allocation fails*, i.e. a
> degradation path, not a chosen design.
>
> **What remains valid for internal-DRAM relief:** shrink the *frames* by moving large
> **buffers** out of them (Part 1 + the stack-buffer section below), and fix the 4× accounting
> so the real numbers are known.

The task inventory below is still useful for one reason: **these are the corrected, real byte
sizes** (the repo's own comments are 4× off — see Finding 1). Feasibility verdicts are recorded
but **not being acted on**.

### Hard `no` — two disqualifiers, both real

- **Flash op with cache disabled runs on the *calling task's own stack*** → a PSRAM stack is
  unreadable at that moment: `debug_out` (inline LittleFS log writes), `cam_record` (writes every
  frame), `sr_snip_wr`, `mic_record`, `cmd_exec_task` (settings persist).
- **IRAM-safe ISR frames land on the stack** → can fire while cache is off: `espnow_task`,
  `espnow_tx` (its comment is a first-hand crash account: "an interrupt frame landing at
  `_frxt_int_exit` is genuinely ~12-16 KB deep"), `sensor_bcast`.
- **Latency**: `llm_gen` — already PSRAM-bus-bound; and it's moot anyway, its stack is a static
  `.bss` array (`gLLMWorkerStack`) chosen *because* dynamic 16 KB creates were failing on the
  fragmented heap. Moving it would reintroduce a fixed bug.

### `risky` — ✅ RESOLVED: they were all a hard NO

The open question was "does the VFS read path **suspend** or **disable** the cache?" — it gated
six G2 viewers (`g2_bmp_view/full`, `g2_jpg_view/full`, `g2_llm_page`, + `mapRender`,
`g2_map_page`), which are idle-priority and transient (good) but **read files**.

**Answered from sdkconfig: it DISABLES.**

```
# CONFIG_SPI_FLASH_AUTO_SUSPEND is not set      ← IDF default is n
```

With auto-suspend off, flash ops take the `spi_flash_disable_interrupts_caches_and_other_cpu`
path: the cache goes down while the flash routine keeps executing **on the calling task's own
stack**. A PSRAM stack is unreadable in that window. (Auto-suspend only ever covered long
erase/write ops anyway.)

So the "risky six" resolve to **NO**, not yes — any task touching LittleFS could never have held
a PSRAM stack. This independently corroborates the ruling above: PSRAM task stacks being
"historically bad on this hardware" is exactly what this config predicts, since most tasks touch
flash. The 22 "feasible" count was optimistic.

**Why the lc3 workspace move is safe** (verified, not assumed): `micWavWritePacketLocked` (:1613)
and `handleAudioNotify` (:1718) are *structurally identical* consumers — both call `lc3_decode`
on 5 LC3 frames per packet, on the **same BLE notify task at the same rate**. The AFE twin
already accepts PSRAM and is the *more* latency-sensitive of the two (it feeds real-time speech
recognition). The WAV path additionally writes each packet to SD, which dominates any PSRAM
decoder-state access. liblc3 is pure-CPU scratch — nothing DMAs from it, and the decoded PCM
lands in a separate stack buffer.

**Correction — these fixes reclaimed REAL DRAM.** An earlier draft of this doc hedged that both
sites "may already land in PSRAM implicitly via `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL`". They did
not. The threshold is:

```
CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=16384
```

Allocations **≤16 KB always go to internal DRAM**; only larger ones drift to PSRAM. At ~6 KB
each, both of these were landing in internal DRAM on every call. Making them explicit
`ps_alloc`/`MALLOC_CAP_SPIRAM` is a genuine internal-DRAM win, not a no-op.

⚠ This threshold is worth remembering for the rest of the audit: **any `malloc`/`new` under
16 KB is internal DRAM**, so the per-call-heap-spiram candidates in Part 1 (all ≤2 KB) are
*all* currently consuming internal DRAM and would need an explicit `MALLOC_CAP_SPIRAM` to move —
plain `malloc` will never do it for them.

Also worth making explicit (load-time temps, freed immediately, allocated when heap is
tightest): `System_LLM_Model.cpp:120` (`scales`), `System_LLM_Tokenizer.cpp:174` (`bpeReachable`).
