# HardwareOne P4 portability: code and build appendix

This is a read-only audit of the current working tree, including existing uncommitted changes. The application appears substantially reusable: the source audit found no actual Xtensa instructions in application code. The main work concerns hardware backends, dependency/configuration choices, and assumptions about wireless and power. Successful P4 compilation and hardware behavior still require experimental verification.

**Keep P4 bring-up separate from an IDF 6 migration.** The [lockfile records IDF 5.5.1](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/dependencies.lock#L107). Documented Arduino 3.3.5 already supports `esp32p4`, declares P4-only ESP-Hosted/WiFi-Remote dependencies, and requires IDF `>=5.3,<5.6`; its CMake rejects versions above 5.5.99. Therefore P4 itself does not require IDF 6. [Official Arduino manifest](https://raw.githubusercontent.com/espressif/arduino-esp32/3.3.5/idf_component.yml), [version guard](https://raw.githubusercontent.com/espressif/arduino-esp32/3.3.5/CMakeLists.txt).

**First restore a reproducible baseline.** `components/arduino/` is absent from this checkout and gitignored, although [application CMake requires it](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/components/hardwareone/CMakeLists.txt#L483). [Patch documentation](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/docs/arduino-local-patches/README.md#L4) identifies Arduino 3.3.5/commit `11bc7ac1a`, extensive BLE/WiFi/PSRAM/build patches, and an uncaptured XIAO variant. Restoring stock Arduino alone does not reproduce the documented firmware without its patches. The current `boards/xiao_s3.defaults` selects upstream `XIAO_ESP32S3`, which is present; the older uncaptured Sense variant mentioned by the documentation is not an observed blocker for this profile. Also reconcile ESP-SR constraints: the [application requests 1.x](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/components/hardwareone/idf_component.yml#L23), whereas the [recorded Arduino patch retains 2.x](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/docs/arduino-local-patches/arduino-local-patches.patch#L224). If both constraints activate, their version ranges conflict. The S3 configure reused locked ESP-SR 1.9.5 successfully, but the fresh P4 resolution failed with precisely this version conflict. This is now an experimentally confirmed dependency blocker. ESP-SR 1.9.5 itself already contains P4 libraries; it is not inherently Xtensa-only. [Official ESP-SR CMake](https://raw.githubusercontent.com/espressif/esp-sr/v1.9.5/CMakeLists.txt).

The smallest maintainable design preserves one application and separates four concerns:

- **SoC:** available peripherals, CPU/core limits, memory/DMA/cache requirements, and architecture-specific diagnostics.
- **Board:** actual pins, buses, flash/PSRAM capacities, panel/sensor identity, coprocessor wiring, and console routing.
- **Deployment:** enabled user features, resource budgets, partitions, and release/OTA identity.
- **Backend:** native or hosted wireless, DVP or P4 camera, display transport, SD transport, microphone capture, and power controls.

This extends existing structure. [The board wrapper reads the target from board metadata](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/tools/build_board.sh#L47); [the deployment loader](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/cmake/HW1Deployment.cmake#L61) already shares board/target/partition/feature policy with release tooling. Add a real P4 board definition instead of using [unknown-board GPIO defaults](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/components/hardwareone/System_BuildConfig.h#L1245). Make build dependencies, linker fragments and C++ features derive from the same capability/backend selection. Consolidate the [duplicated OTA registries](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/CMakeLists.txt#L218) into the existing descriptor model over time.

**Wireless is a lifecycle change.** P4 needs a radio coprocessor. Existing code mixes Arduino WiFi, native `esp_wifi`, ESP-NOW and Bluedroid, so validate STA/AP/channel behavior, ESP-NOW and BLE against the selected hosted stack before promising parity. A small radio adapter should own coprocessor initialization, resets and availability; retain mesh, G2/R1 and application protocols. [Device identity currently depends on the WiFi MAC being available](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/components/hardwareone/System_SelfDevice.cpp#L47), so stable identity should survive radio startup/failure. The separate recovery updater also [initializes WiFi directly](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/updater/main/recovery_network.c#L583) and needs its own hosted dependencies/configuration; a working main application does not prove recovery works.

**Camera requires a new backend.** Locked `esp32-camera` 2.1.4 compiles capture drivers only for ESP32/S2/S3; its P4 build contains conversion utilities. [Official driver CMake](https://raw.githubusercontent.com/espressif/esp32-camera/v2.1.4/CMakeLists.txt). The [public camera API exposes `esp_camera.h` and `framesize_t`](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/components/hardwareone/System_Camera_DVP.h#L60). Introduce neutral frame/resolution/capability types with DVP and P4 implementations. Preserve capture, storage and streaming consumers; explicitly handle JPEG conversion/encoding and sensor-setting differences. Gate the currently unconditional camera dependency and linker fragment.

**Reuse existing HALs where possible.** P4X-EYE uses a PDM microphone ([official BSP](https://raw.githubusercontent.com/espressif/esp-dev-kits/master/examples/esp32-p4-eye/examples/common_components/esp32_p4_eye/esp32_p4_eye.c)): the [existing audio backend already uses modern I2S/PDM APIs](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/components/hardwareone/HAL_Audio.cpp#L70), and its [16 kHz mono PCM contract](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/components/hardwareone/HAL_Audio.h#L13) can remain shared. Validate board pins/channel configuration before adding a new audio architecture. The board has a 240×240 ST7789 SPI screen; the [existing ST7789 branch](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/components/hardwareone/HAL_Display.h#L64) is a starting point, but its 240×320 geometry and example pins need board configuration. Register the existing ST7735/ST7789 library in `hardwareone_libs` CMake, then replace SSD1306-specific UI calls such as `clearDisplay()`, `display()` and `getBuffer()` with shared rendering operations. The current UI bypasses its HAL in several places (for example `OLED_FirstTimeSetup.cpp:172` and `OLED_Mode_Map.cpp:1206`). [Board guide](https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32p4/esp32-p4x-eye/user_guide.html). SD mounting currently [assumes SPI](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/components/hardwareone/System_VFS.cpp#L230); P4X-EYE uses SDMMC with board power setup. Select SPI or SDMMC below the VFS so permissions and file handling remain common.

**Audit low-level assumptions.** [Power modes hardcode 240/160/80/40 MHz](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/components/hardwareone/System_Power.cpp#L28); map those user policies to valid target clocks and driver-aware power constraints. [Task placement assumes local radio on core 0](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/components/hardwareone/System_TaskUtils.h#L134). Keep centralized allocation helpers, while checking DMA alignment/cache rules for camera/display buffers. [Crash recording uses private panic internals](https://github.com/CadenGithubB/HardwareOne/blob/6ba1c6c0906cbf5ccc7511fdc4d9e007239e9849/components/hardwareone/System_CrashRecord.cpp#L11), requiring RISC-V and retained-memory validation.

**IDF 6 adds independent migration work:** upgrade/rebase Arduino; replace removed built-in `json`/`mqtt` dependencies with managed components; migrate legacy ADC/I2C usage; and update legacy Mbed TLS crypto calls throughout settings, authentication, OTA hashing/signature checks and certificate generation for Mbed TLS 4/PSA Crypto. Preserve stored-data and wire-protocol compatibility with tests. [Official protocols migration](https://docs.espressif.com/projects/esp-idf/en/v6.0/esp32p4/migration-guides/release-6.x/6.0/protocols.html), [security migration](https://docs.espressif.com/projects/esp-idf/en/v6.0/esp32p4/migration-guides/release-6.x/6.0/security.html).

Suggested implementation sequence:

1. Reproduce one existing ESP32/S3 build, pin dependencies/patches, and build a minimal P4 serial/settings/filesystem profile in an isolated copy.
2. Prove the critical ESP-NOW bridge against the S3 control, plus hosted networking and shared web/CLI, including radio restart and identity behavior.
3. Bring up SD, PDM audio, display/input and camera independently; retain shared application consumers.
4. Qualify the full mesh and BLE/G2/R1 interoperability, memory pressure, task placement and power transitions.
5. Add paired recovery OTA artifacts, board/layout identity and recovery failure tests. Maintain an ESP32/S3/P4 build matrix; undertake IDF 6 migration separately once P4 behavior is understood.
