#### [automation-scheduling] A clock-due automation whose global condition is false never reschedules, so it stays permanently due
- **Where:** components/hardwareone/System_Automation.cpp:4004
- **Claim:** The condition-not-met path continues out of the automation loop before rescheduleAfterFire() runs, so nextAt is never advanced. The automation remains due forever, forcing a full file read+parse tick on every main-loop pass, and it fires whenever the condition later becomes true rather than skipping the occurrence.
- **Failure scenario:** automationadd name=vent type=attime time=08:00 condition="TEMP>90" command="fanon". At 08:00 the temperature is 70, so conditionMet=false and the code does pos=objEnd+1; continue. nextAt stays 08:00. rebuildAutomationsCache keeps nextAt=08:00 in the past, so automationsAnyDue(now) is true on every loop iteration forever: schedulerTickMinute does readText(automations.json) + deserializeJson + per-automation substring extraction + evaluateCondition every pass (the code's own comment at :483 estimates 15-30 ms). When the temperature crosses 90 at 15:40, the automation fires at 15:40 instead of skipping to 08:00 tomorrow. The identical hole exists for an automation with an empty/malformed commands array (:4067 logs "no commands found" and also skips the reschedule).
- **Evidence:** System_Automation.cpp:4010-4013 `DEBUGF(... "skipped - condition not met"); pos = objEnd + 1; continue;` -- rescheduleAfterFire is only reached at :4066 `if (clockDue) rescheduleAfterFire(id, obj.c_str(), now);`, after the command loop and inside the `if (cmdsCount > 0)` block that ends at :4067. automationsAnyDue at :600-609 returns true for any cached nextAt <= now, and HardwareOne.cpp:2463-2466 rate-limits only the event branch, never the due branch.
- **Proposed fix:** Advance the due triggers before the condition/commands gates: call rescheduleAfterFire(id, obj, now) as soon as clockDue is established (or on every early-exit path once clockDue is true), so a skipped occurrence moves nextAt to the next occurrence exactly like a fired one.
- **Verifier note (AUTHORITATIVE — may refute the fix):** Severity stands at high, but reframe the defect: firing late rather than skipping is arguably the intended "fire at or after 08:00 once the condition holds" semantics (the web UI labels it "Fire when (optional sensor condition)"), so the unambiguous defect is the unbounded busy-poll of the whole file, not the late fire. THE PROPOSED FIX IS UNSAFE AS WORDED. "Call rescheduleAfterFire(id, obj, now) as soon as clockDue is established" while leaving the call at :4066 in place double-advances: `obj` is a stale snapshot of the JSON taken at :3803, so the second call re-reads the SAME pre-advance nextAt from the snapshot and steps it forward again, silently skipping an occurrence. Correct shape: keep exactly one call site — set a `bool needReschedule = clockDue;` and move the single rescheduleAfterFire() to the bottom of the per-automation block so every early-exit path (condition-not-met, no-commands, and the normal fire) funnels through it once. Note this also converts condition-gated automations from "fire when it becomes true" to "skip the occurrence", which is a user-visible behavior change and should be a documented choice, not a silent side effect of the perf fix.

#### [automation-scheduling] An interval trigger under 1000 ms reschedules to the current second and refires every main-loop pass, rewriting automations.json each time
- **Where:** components/hardwareone/System_Automation.cpp:2318
- **Claim:** nextFire() for INTERVAL computes from + intervalMs/1000 with integer division, so any 1..999 ms interval yields nextAt == from. The trigger is instantly due again and each fire runs rescheduleAfterFire -> writeAutomationsJsonAtomic, i.e. a LittleFS write per loop iteration. The add path only checks that intervalms is numeric.
- **Failure scenario:** automation add name=x type=interval intervalms=500 command="print hi". computeInitialNextAt -> nextFire(INTERVAL, now) = now + 500/1000 = now, persisted as nextAt=now. First tick: clockDue (now >= nextAt) -> fires -> rescheduleAfterFire(firedAt=now) -> nextFire(s, now) = now -> nextAt written back unchanged. Next main-loop pass: automationsAnyDue is still true -> fires again. The loop never terminates: the command executes and automations.json is fully read, parsed, re-serialized and atomically rewritten on every pass, starving the main loop and burning the flash block.
- **Evidence:** System_Automation.cpp:2318 `return (s.intervalMs > 0) ? (from + (time_t)(s.intervalMs / 1000)) : 0;` (0 is safely rejected, 1-999 is not). Validation at :1112-1115 is only `if (!isNumeric(intervalMs))`. Write-back path :2444 then :2473 writeAutomationsJsonAtomic(json).
- **Proposed fix:** Clamp in nextFire: `time_t step = (time_t)(s.intervalMs / 1000); if (step < 1) step = 1; return from + step;` and reject intervalms < 1000 in cmd_automation_add (and in the secondary-trigger parser at :1358).
- **Verifier note (AUTHORITATIVE — may refute the fix):** The clamp in nextFire is correct but INCOMPLETE: `if (step < 1) step = 1;` never runs for intervalMs == 0 because the `s.intervalMs > 0` ternary short-circuits to 0 first, and intervalms=0 passes isNumeric() today ("0" is all digits) — that produces the permanently-inert automation of finding [10] instead. So the add-path rejection must be `intervalms < 1000` INCLUDING 0, i.e. reject rather than clamp, with an error string. Also add the same bound to the secondary-trigger parser at :1365-1367 (`long ims = sv["intervalMs"] | 0; if (ims > 0)`) — as written it happily accepts 1. Fixing only nextFire leaves a 1 ms interval firing once per second forever, which is still a per-second flash write; both halves are needed.

#### [automation-scheduling] `automation recompute` is a no-op for exactly the triggers that need it
- **Where:** components/hardwareone/System_Automation.cpp:2082
- **Claim:** recompute calls computeNextRunTime, which returns the PERSISTED nextAt when it is > 0 and only calls nextFire for triggers whose nextAt is 0. So the one user-facing repair for a stale or wrong nextAt writes the same stale value back. It also only writes one trigger per automation.
- **Failure scenario:** User changes tzoffsetminutes from 540 (Tokyo) to -300 (EST). Their "07:00 coffee" automation still holds nextAt = 22:00 UTC (07:00 JST) and will fire at 17:00 EST. They run `automation recompute` to fix it: for that automation computeNextRunTime sees triggers[0].nextAt = 22:00 UTC > 0 and returns it verbatim, updateAutomationNextAt writes 22:00 UTC back, and the command reports "1 succeeded". Nothing changed. Separately, updateAutomationNextAt(id, nextAt) resolves triggerIdx=-1 to the FIRST time/interval trigger, so a 3-trigger automation's second and third triggers are never recomputed at all.
- **Evidence:** System_Automation.cpp:2485 `time_t t = (triggers[i].nextAt > 0) ? triggers[i].nextAt : nextFire(triggers[i], fromTime);` inside computeNextRunTime, called by recompute at :2082 and then written via :2084 updateAutomationNextAt -> :674-676 -> updateAutomationTriggerNextAt(id, -1, ...) whose -1 alias at :643-652 picks only the first time/interval trigger.
- **Proposed fix:** Give recompute a force path: iterate triggers via triggersFromJson, call nextFire(t, now) unconditionally for every clock trigger, and write the whole triggers array back (the same loop rescheduleAfterFire already has at :2455-2470).
- **Verifier note (AUTHORITATIVE — may refute the fix):** STRENGTHEN — it is worse than a no-op for multi-trigger automations. computeNextRunTime returns the MINIMUM nextAt across all triggers (:2483-2488), and updateAutomationNextAt(id, thatMin) resolves -1 to the FIRST schedulable trigger, so recompute writes one trigger's nextAt into a DIFFERENT trigger. Concretely: an automation with triggers [time 22:00 daily, interval 5 min] has min = the interval's nextAt; `automation recompute` stamps now+5min onto the 22:00 TIME trigger, which then fires ~5 minutes later at the wrong wall-clock time (rescheduleAfterFire repairs it afterwards from the TIME spec, so it is one spurious fire per recompute, per automation). So the single user-facing repair command actively corrupts multi-trigger schedules. The proposed fix (iterate via triggersFromJson, call nextFire unconditionally for every clock trigger, write the whole array back using rescheduleAfterFire's loop shape at :2455-2470) fixes both halves and is correct — but it must skip MANUAL triggers that are currently ARMED (cmd at :1945-1949 writes nextAt = now + delayMs/1000 into a manual trigger), because nextFire returns 0 for MANUAL and an unconditional force-recompute would silently disarm every pending afterDelay timer.

#### [anchors-and-capture-dating] The boot's time anchor is written once at the first isSynced() edge and never corrected when the clock is later re-set, so ring-adopted (admittedly stale) time permanently mis-dates promoted folders
- **Where:** components/hardwareone/System_TimeAnchors.cpp:389
- **Claim:** gAnchoredThisBoot latches the (msAtSync, epochAtSync) pair at the first moment Clock::isSynced() turns true, with no notion of source quality; a later settimeofday() (NTP true-up of a ring adoption, RTC sync, manual timeset) invalidates the pair — epochAtSync no longer corresponds to msAtSync — and nothing rewrites it, while the sweep has usually already promoted the folder within 5-10 s.
- **Failure scenario:** Dark boot at 08:00 local, Health Track autostarts into /sensors/boot-000123/health-boot123-4200.csv. At 08:05 the R1 ring connects; ringBestKnownEpoch() returns the ring's LAST STORED measurement stamp — the ring was off the finger since 23:30 last night — so the adopted epoch is 2026-07-28T23:30 (the +since-receive adjustment only covers time since WE received the frame, not since the ring measured). timeAnchorsTick then writes anchor (msAtSync≈300000, epochAtSync=2026-07-28T23:30) and, on the next 5 s pass, promotes the boot folder into /logging_captures/sensors/2026-07-28/ with 23:2x local stamps. WiFi joins at 08:20, NTP jumps the clock +8.5 h; the anchor line still says 23:30, the already-renamed files stay in yesterday's folder forever, and one contiguous stretch of health data is split across 2026-07-28 and 2026-07-29 with an 8.5 h backwards jump between the files.
- **Evidence:** System_TimeAnchors.cpp:389-394 `if (!gAnchoredThisBoot) { if (registryFind(gBootCounter) == nullptr) writeAnchorLine(); gAnchoredThisBoot = true; }` — one shot per boot, no re-anchor hook. writeAnchorLine (132-141) samples `millis()` and `time(nullptr)` together, which is only valid for the clock as of that instant. G2_Ring.cpp:377-386 ringBestKnownEpoch() adjusts only by `(millis() - rx)/1000`; the custody comment itself concedes the adoption echo "carries the ring's last MEASUREMENT time, stale by minutes" (G2_Ring.cpp:363-364) and ringAdoptClockIfDark() calls settimeofday() with it unconditionally (G2_Ring.cpp:399-400). The sweep fires 5 s later (timeAnchorsTick:387).
- **Proposed fix:** Keep the sync provenance (e.g. a global gTimeSyncSource / gLastSyncEpochShift set by the NTP, RTC and ring adoption paths). On any settimeofday() that shifts the clock by more than a few seconds, re-derive this boot's anchor (epochAtSync += shift, or resample both from the corrected clock) and rewrite the boot's line via registryPersist. Optionally hold the promote sweep until either (a) the sync source is NTP/RTC or (b) a bounded grace window (e.g. 120 s) has passed with no further correction, so a ring-only boot isn't renamed on the least trustworthy stamp available.
- **Verifier note (AUTHORITATIVE — may refute the fix):** Re-anchoring alone does not fix already-promoted names, and misses the sibling victim: the BOOT_SHAPED->day-file roll (System_SensorLogging.cpp:876-883) names the day file from the same stale adopted clock. Only the grace/provenance hold actually prevents the wrong date, and it must cover the roll too.

#### [automation-scheduling] TZ restore in the DS3231 helpers silently resets TZ to UTC0, defeating Clock::applyTimezone() on exactly the boots it was written for
- **Where:** components/hardwareone/i2csensor_ds3231.cpp:198
- **Claim:** The getenv/setenv("UTC0")/setenv(oldTZ) round-trip cannot restore the old value: newlib's _setenv_r overwrites the existing value buffer IN PLACE whenever the new value is no longer than the old, so oldTZ already reads "UTC0" when it is handed back. TZ stays UTC for the rest of the boot.
- **Failure scenario:** FeatherS3 + DS3231, tzOffsetMinutes=-300 (EST). applySettings() (System_Settings.cpp:758) sets TZ="UTC5". HardwareOne.cpp:1584 then calls rtcEarlyBootSync(): oldTZ=getenv("TZ") points into the environ entry holding "UTC5"; setenv("TZ","UTC0",1) sees strlen("UTC5")=4 >= strlen("UTC0")=4 and copies in place, so oldTZ now reads "UTC0"; setenv("TZ",oldTZ,1) is a no-op. Every later localtime_r()/mktime(), including nextFire(), runs in UTC. An "08:05 daily" TIME trigger on a WiFi-less boot then fires at 08:05 UTC = 03:05 EST, and dated folders / CSV day rollover shift 5 h. If a given newlib instead frees+reallocs, oldTZ is dangling and TZ becomes garbage - unsound either way. Every configured offset produces a string of >=4 chars, so all non-UTC zones are affected.
- **Evidence:** i2csensor_ds3231.cpp:198-207 char* oldTZ = getenv("TZ"); setenv("TZ","UTC0",1); tzset(); mktime(); if (oldTZ) setenv("TZ", oldTZ, 1); else unsetenv("TZ"); tzset(); -- newlib _setenv_r: if (strlen(C) >= l_value) { while ((*C++ = *value++) != 0); return 0; }. Boot order: applySettings() at HardwareOne.cpp:1524 (sets TZ) then rtcEarlyBootSync() at 1584 and again at 1733. Siblings at :233-242 (rtcSyncToSystem, called from rtcTask startup and rtcsync to) and :290-299 (rtcToUnixTime, called by rtc status) re-clobber even after configTime() on WiFi boots.
- **Proposed fix:** Do not round-trip through the environment. Either strdup the old value before overwriting (and free after), or drop the TZ dance entirely and compute the UTC epoch arithmetically (days-from-civil / Howard Hinnant days_from_civil, ~10 lines) so mktime and the global TZ are never involved. A cheap on-device confirmation: print getenv("TZ") immediately before and after rtcEarlyBootSync().
- **Verifier note (AUTHORITATIVE — may refute the fix):** Two evidence corrections. (1) The "dangling pointer" framing from the pre-existing triage is the LESS likely branch; in-place clobber is what actually happens for every configured offset, so the symptom is deterministic (TZ=UTC0), not garbage. (2) The `else unsetenv("TZ")` arm is now dead code, since applySettings() always sets TZ before any of these three functions can run. FIX: the proposed strdup/free is sound, but the cheapest correct fix in this codebase is to drop the restore entirely and call Clock::applyTimezone() after the mktime — it is already the single source of truth for the TZ string and needs no allocation or lifetime reasoning. The days_from_civil suggestion is also correct and avoids the global TZ entirely, but it is more code than the one-line applyTimezone() call. Do NOT "fix" this by hoisting a strdup into a static buffer shared by the three functions — rtcToUnixTime is reachable from the rtc-status command path on a different task than rtcEarlyBootSync.

#### [automation-scheduling] weekInterval week counting is floored from the anchor instant, so a late first fire permanently shifts the cadence by one week
- **Where:** components/hardwareone/System_Automation.cpp:2340
- **Claim:** deltaWeeks = (cand - anchor) / (7*86400) uses the anchor's exact instant, and onFired() sets anchor to the actual fire time rather than the scheduled time. Whenever the anchor's time-of-day is later than the candidate's, the floor undercounts by one week and the parity test picks the wrong weeks.
- **Failure scenario:** Biweekly automation: time=08:05, days=mon, weekInterval=2. The device is off overnight and boots Monday 2026-07-13 at 10:00; the persisted nextAt (Mon 08:05) is already past, so it catch-up fires at 10:00 and onFired sets anchor=2026-07-13 10:00:00. nextFire(from=10:00) scans forward: d=7 gives Mon 2026-07-20 08:05, deltaSec = 7*86400 - 6900 = 597900, 597900/604800 = 0, 0 % 2 == 0 -> accepted. The automation fires again one week later instead of two. anchor is never rewritten (onFired only sets it when anchor==0), so from then on it fires on weeks 1, 3, 5... relative to the anchor - a permanent one-week offset from the intended schedule. A tick delayed by as little as one second past 08:05:00 on the very first fire is enough to trigger this (deltaSec = 604799 -> deltaWeeks = 0).
- **Evidence:** System_Automation.cpp:2337-2342 `long deltaSec = (long)(cand - s.anchor); if (deltaSec < 0) deltaSec = 0; long deltaWeeks = deltaSec / (7L * 86400L); if ((deltaWeeks % s.weekInterval) != 0) continue;` and :2424-2429 `if (s.type == Trigger::TIME && s.weekInterval > 1 && s.anchor == 0) { s.anchor = firedAt; ...}` with firedAt = `now` passed from :4066.
- **Proposed fix:** Normalize both endpoints to local midnight before differencing (or store the anchor as a day number): compute the anchor's and candidate's civil day via localtime_r, then deltaWeeks = (candDay - anchorDay) / 7. Also set the anchor from the scheduled nextAt rather than from the wall-clock fire instant.
- **Verifier note (AUTHORITATIVE — may refute the fix):** The fix's second half is the important one and needs a concrete hook: onFired() only receives firedAt, so "set the anchor from the scheduled nextAt" requires threading the pre-advance value in — rescheduleAfterFire already has it (`triggers[i].nextAt` at :2442, read before it is overwritten at :2444), so pass that as the anchor source. The first half (normalize both endpoints to local midnight via localtime_r and difference civil days) is correct and is the robust form; note it must use localtime_r, not gmtime_r, or a non-zero tzOffsetMinutes reintroduces the same off-by-one-week near midnight. Also worth doing in the same edit: rescheduleAfterFire only persists `anchor` when weekInterval > 1 AND anchor > 0 (:2465-2467), so an anchor policy change must keep that persist condition in sync or the new anchor is computed and then dropped.

#### [automation-scheduling] No missed-fire suppression: the ~56-year dark-boot to ring-adoption jump fires every stale automation at once, each with its own full automations.json rewrite
- **Where:** components/hardwareone/System_Automation.cpp:3844
- **Claim:** clockDue is simply now >= nextAt with no grace window, and each fire does an independent read+parse+serialize+atomic write. A large forward clock step makes every automation with a past nextAt fire in a single tick - once each (no repeat burst), but all at a semantically wrong wall-clock time and with N flash rewrites of the same file back to back.
- **Failure scenario:** Dark boot (no RTC, no WiFi). timeValid is `now > 0`, which is true one second after boot, so the tick runs against a 1970 clock. 12 enabled automations hold nextAt values from the last synced session (2026 epochs), so nothing is due. At t+8 s g2RingTimeSyncTick -> ringAdoptClockIfDark settimeofday's the clock to 2026-07-29 14:32 and calls notifyAutomationScheduler. The very next tick finds all 12 nextAt values in the past: "turn the lights off at 23:00", "weekly backup Sunday 03:00" and a YEARLY "Dec 25" all execute at 14:32 on a Wednesday, and rescheduleAfterFire runs 12 times in one tick - 12 readText + deserializeJson + serializeJsonPretty + writeTextAtomic cycles on LittleFS inside a single main-loop iteration (~hundreds of ms of stall plus 12 rewrites of the same file).
- **Evidence:** System_Automation.cpp:3705-3706 `time_t now = time(nullptr); bool timeValid = (now > 0);` (not Clock::isSynced()); :3843-3844 `time_t nextAt = timeValid ? computeNextRunTime(obj.c_str(), now) : 0; bool clockDue = (timeValid && nextAt > 0 && now >= nextAt);` - no staleness bound anywhere; :4066 rescheduleAfterFire per fired automation, which re-reads and rewrites the whole file at :2450-2473. G2_Ring.cpp:399-401 settimeofday + :424 notifyAutomationScheduler (which only sets gAutomationsDirty / clears gAutomationsCacheValid, :3655-3658 - it never touches persisted nextAt).
- **Proposed fix:** Two parts. (1) Add a missed-fire grace window: if now - nextAt exceeds a bound (e.g. 2x the trigger period, or a fixed 15 min for TIME/MONTHLY/YEARLY), skip the fire and just advance nextAt, optionally logging a MISSED event. (2) Batch the reschedule: collect the fired ids during the scan and do one read/modify/write of automations.json at the end of the tick instead of one per automation.
- **Verifier note (AUTHORITATIVE — may refute the fix):** Fix part (2) — batch the reschedule into one read/modify/write at the end of the tick — is unambiguously right and is the part worth doing; it also fixes the same amplification on the ordinary reboot path. Fix part (1) is a policy change and the proposed blanket bound is too blunt: a fixed 15-minute grace for TIME/MONTHLY/YEARLY would silently drop exactly the fires users rely on after a power cut ("run the nightly backup when you come back up"). Make it per-automation opt-in (a `catchUp` flag, default = today's behavior) or the change will read as a regression. Also note the interaction with finding [9]: if you rebase INTERVAL nextAt on dark boots, those 1970-based values all become past-due the moment a clock arrives, so the batching fix should land before or with that one.

#### [automation-scheduling] Interval automations do not run at all on a boot that never gets a real clock
- **Where:** components/hardwareone/System_Automation.cpp:3705
- **Claim:** The scheduler's time guard is `now > 0`, not Clock::isSynced(), so a dark boot is treated as valid time at the 1970 epoch while the persisted nextAt values are real 2026 epochs. Elapsed-time (INTERVAL) triggers - which need no wall clock at all - therefore stall for 56 years' worth of comparison until some time source appears.

## 2. FINDINGS REACHABLE ONLY ON A DIFFERENT BOARD CONFIG

**All of the following are inside `#if ENABLE_RTC_SENSOR` and are dead code on the current FeatherS3 build.** Verified two ways: `System_BuildConfig.h:127` (`I2C_FEATURE_LEVEL 4`) + `:139` (`CUSTOM_ENABLE_RTC 0`) + `:455`, and `nm build/hardwareone-idf.elf` returns **zero** DS3231 symbols. 3. **[would be MEDIUM] `rtcSyncToSystem()` has no plausibility guard** — `i2csensor_ds3231.cpp:216`. `rtcEarlyBootSync` rejects year < 2020; `rtcSyncToSystem` — reached from `rtcTask` and the user-facing `rtcsync`/`rtcsync to` — calls `settimeofday` on whatever the RTC returns, so a dead-battery DS3231 can step a good clock back to 2000. 4. **[would be MEDIUM] Ring-adopted clock is written into the DS3231 and marks it "calibrated"** — `G2_Ring.cpp:411-421` (**new code, but board-gated**). The adopted value is the ring's last *stored measurement* time, documented stale by minutes; persisting it and setting `rtcTimeHasBeenSet` promotes known staleness into the source `rtcEarlyBootSync` trusts **first on every subsequent boot**, and suppresses the adoption path next boot because `isSynced()` will be true. 5. **[would be MEDIUM] `cmd_time`'s RTC branch prints the DS3231 raw (UTC) while its NTP branch prints local** — `System_Utils.cpp:1878-1888` (JSON), `:1912-1926` (text) vs `:1929-1936`. ## 3. COMPLETENESS CRITIQUE — what this audit did NOT cover

### (a) An entire time-distribution subsystem was never opened: ESP-NOW mesh time sync
None of the six dimensions touched it. I read it while synthesizing and it is **inert, with defects**:

- `System_ESPNow.cpp:2831` — `v4h_time_sync` sets `gTimeOffset = ts->timeOffset` and `gTimeIsSynced = true`, and **never calls `settimeofday`**. `gTimeOffset` is **written and never read** anywhere in the tree (`:343` decl, `:2831` write, that's all). So `espnowtimesync` cannot set a receiving node's clock — the feature does nothing. `ts->epochTime` is logged and discarded.

## 4. VERDICT — biggest risk in the newly written uncommitted code

**Ship it, after three small fixes. The TZ work is a clear net win and should not be held; the ring-clock custody block needs ~15 lines of hardening first.**

**Why the TZ fix is safe:** it repairs a genuine, previously-silent whole-class bug — `localtime_r`/`mktime` ran in UTC on every WiFi-less boot, mis-dating capture folders, per-day CSV rollover, the glasses date, and TIME automations. The consumers it was written for really do use `localtime_r` (`System_Automation.cpp:2321-2399`, `System_SensorLogging.cpp:276/871/1793`, `System_TimeAnchors.cpp:262`, `System_Utils.cpp:775`) and are genuinely repaired. Every generic settings surface routes through `cmd_tzoffsetminutes` → `applyTimezone()` (verified: no `SETTING_EDITOR_CMD` row, no POST handler, OLED dispatches by `cmdKey` only), so the only bypass is the wizard-cancel path (SHOULD FIX #17), which is a pre-existing shape. Its only reachable defect on this board needs a nonsense `tzoffsetminutes 30`. **Critically, the item two dimensions called a commit blocker — the DS3231 TZ round-trip undoing the fix — is compiled out on this board** (zero DS3231 symbols in the ELF), so the fix is not silently defeated on the shipping hardware.

**Why the ring custody block should not go as-is** — the risk is not that it fails, it is that it **succeeds with a wrong number**, and a wrong clock is worse than no clock because everything downstream launders it (dated folders, per-day CSV, TIME automations, the corrective push back into the ring, and on an RTC build the DS3231 itself). The HW-validated legs prove the chain *works*; they do not prove it *rejects* bad input, and the audit found three ways bad input gets in:

1. **`ringBestKnownEpoch` can pair a timestamp with the wrong receive-millis** (MUST FIX #1). Two mechanisms — the new pair is written in the harmful order and never cleared across links; and in the bridge path the `*Ts` and `*RxMs` fields are updated in different proto cases, so a stamp can advance while its rx stays stale. Either yields a clock adopted **fast** — up to `uptime` seconds in the torn case, up to the frame gap in the bridge case — and the `2100` cap at `:384` checks the raw ts, never the projected sum, so it cannot catch it. Note the sibling helper `ringSampleAgeSec` (`:333-344`) guards `if (rxMs != 0)` and prefers ring-epoch arithmetic: **`ringBestKnownEpoch` is the odd one out in its own file.**
2. **The custody statics survive a manual disconnect** (MUST FIX #12) — `ringClearGattPointers()` clears the GATT pointers but not `sRingSetupDone`/`sLastPushed*`, and `gRing.connected = true` is set at `:1459` well before setup clears them at `:1007`, so after `ringdisconnect` the corrective-push branch is armed on a fresh link with the previous link's push record.
3. **No one-shot latch on adoption** (MUST FIX #11 / POLISH #21) — this is what makes `timeset 1999-…` get silently reverted within 500 ms, and what leaves a re-entry loop possible in a narrow date window. One boolean closes both.

**Minimum pre-commit set (~15 lines, no design work):**
- Write `rx` before `ts`; clear `sRingTsSeen`/`sRingTsSeenRxMs` in `ringClearGattPointers()`; bound the **projected** epoch and reject an implied age > a few hours.
- Clear `sRingSetupDone` / `sLastPushedEpoch` / `sLastPushedAtMs` / `sDarkProbesSent` in `ringClearGattPointers()`.
- Add a one-shot `sAdoptedThisBoot` latch to `ringAdoptClockIfDark()`.
- Free rider, one line: add `writeBootAnchor()` next to `resolvePendingUserCreationTimes()` at `G2_Ring.cpp:423`, so the 8 KB `users.json` read the adoption already performs stops being a guaranteed no-op. **Do not** swap in `logTimeSyncedMarkerIfReady()` yet — it lacks an `isValidEpoch` gate and hardcodes "via NTP".

**Explicitly fine to defer** to follow-up commits: the build-date bound, the backward-echo floor, the probe-budget retry, the `noinline` stack trim, and every comment fix. And one thing to be aware of rather than fix: this change makes MUST FIX #7 (the missed-fire automation burst with N flash rewrites) reachable on WiFi-less boots for the first time — pre-existing automation code, previously masked by dark boots never getting a clock at all. If the field unit runs automations, land #7's grace window + batching in the same release even though it is not new code.
