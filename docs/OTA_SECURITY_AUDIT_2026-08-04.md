# OTA subsystem audit — 2026-08-04

Read-only assessment of the recovery-OTA subsystem (System_OTA/System_OTASafety,
components/hw1_ota_protocol, updater/, tools/ota, partition + build config).
No code was changed. Produced by a 20-agent audit: 9 parallel finders, adversarial
refutation of every finding, a completeness critic, then synthesis.
93 findings survived verification, 7 were refuted, 8 came from the critic.

Status: assessment only. Nothing here is a qualification record.

## Posture

The core of this subsystem is genuinely well-built, and I want to say that plainly before the finding list makes it look otherwise. The protocol state machine in hw1_ota_protocol.c is the strongest code in the tree: every wire parser demands an exact length, every string field has exactly one canonical encoding, record_validate enforces cross-field invariants that make most forged records undecodable, and the "persisted candidate bytes never authorize an install" rule is honored end-to-end by both consumers. The signature story is real rather than decorative — the 224-byte payload covers every field the device acts on, PSS parameters are pinned, hw1_ota_idf.c #errors out if PSA crypto could let a variable salt through, and the classic swap-between-verify-and-apply TOCTOU is closed by re-verification at otastage, otaupdate, and again against the written partition. The dual-slot NVS journal, the probation supervisor's publish-before-transition ordering, the defeat of Arduino's auto-validate, and the build-time pair audit that fingerprints both public keys are all correct as written. The weaknesses cluster in three places, none of them the crypto: the operator-facing surfaces (a recovery web page that 431s in real browsers and has one dead button), performance/robustness on hot paths that re-derive expensive state (users.json parsed per BLE frame, a 4 KB buffer on an 8 KB stack), and post-mortem diagnosis. The single biggest weakness is that third one: after the reboot that a failure causes, the operator can learn THAT an OTA failed and roughly where in the phase machine it stopped, but frequently not WHY — the probation abort reason, the recovery entry reason, and the coreHealthy predicate are never persisted; the errno that was captured is never displayed; the recovery page they are staring at does not render the journal result at all; and two failure classifications are actively wrong for several inputs. For a subsystem whose entire purpose is to survive the case where nobody has a cable attached, that is the gap worth closing first.

## Ranked findings

### 1. 512-byte HTTP header budget makes the recovery page 431 in real browsers

- **Severity:** high · **Category:** robustness · **Effort:** small
- **Location:** `updater/sdkconfig.defaults:24; updater/main/recovery_network.c:527-535`
- **What:** CONFIG_HTTPD_MAX_REQ_HDR_LEN=512 and recovery_network_start() sets stack_size/port/handlers/sockets/timeouts but never sets http.max_req_hdr_len, so the 512 applies. In esp-idf v5.5.1 that value is the budget for the whole header section after the request line, not per header (httpd_parse.c:221/239 set scratch_size_limit; :494 computes MIN(length, limit - offset) and a zero-length block becomes HTTPD_431).
- **Why it matters:** A bare Firefox GET of / is ~460-480 bytes of headers and Chrome is past 512 on its own; require_authorization then forces the browser to add Authorization: Basic (47-115 more bytes). The operator following docs/OTA_RECOVERY_UPDATER.md:749 ('Open http://192.168.77.1/') gets a bare '431 Request Header Fields Too Large' from the last-resort recovery UI, with no hint the fix is a config value. The documented curl fallback still works, which is exactly why this has not been caught.
- **Fix:** Set http.max_req_hdr_len = 2048 explicitly in recovery_network_start() (runtime field, immune to sdkconfig drift) and raise CONFIG_HTTPD_MAX_REQ_HDR_LEN off 512. Test the served page in Chrome and Firefox, not only curl.

### 2. Recovery page's 'Allow downgrade' button is dead, and action_handler's fall-through is REBOOT

- **Severity:** medium · **Category:** correctness · **Effort:** small
- **Location:** `updater/main/recovery_network.c:195; updater/main/recovery_network.c:246-254`
- **What:** Line 195 emits an unquoted onclick attribute containing spaces: onclick=confirm('Explicitly allow an older signed version for this transaction?')&&go('/allow-downgrade'). The HTML tokenizer terminates the attribute at the first space, leaving onclick="confirm('Explicitly" — an unterminated string literal that throws on parse, so the click does nothing. The four sibling buttons contain no spaces and work. Separately, action_handler strcmps request->uri, which carries the query string, and its else-branch is RECOVERY_ACTION_REBOOT.
- **Why it matters:** Installing an older signed image — rolling back to escape a bad release — is a primary reason this updater exists. allow_downgrade_for_transaction (updater_main.c:1513-1530) is a real state change that must precede the manifest POST, and with the button dead there is no HTTP route to it; the only path left is the serial 'allowdowngrade confirm' command, which the page never mentions. The fall-through means any URI with a query string (POST /cancel?ts=1739) reboots instead of cancelling, and any future handler wired to action_handler silently becomes a reboot.
- **Fix:** Quote the attribute: onclick="if(confirm('...'))go('/allow-downgrade')". Match on the path only (strip at the first '?') or better, pass the intended action through httpd_uri_t.user_ctx, and make the fall-through a 400 rather than a reboot. Add a smoke test that loads the page and clicks each control.

### 3. 4 KB hash buffer on the 8 KB cmd_exec_task stack during firmware validation

- **Severity:** high · **Category:** robustness · **Effort:** small
- **Location:** `components/hardwareone/System_OTA.cpp:447 (reached from :1099 and :1118 and :1164)`
- **What:** hashAndDescribeImage declares `uint8_t buffer[4096];` as a plain automatic array. Every command runs on cmd_exec_task, whose stack is 8192 BYTES (System_TaskUtils.h:31; HardwareOne.cpp:692 passes it as bytes). cmdOtaStage holds two CandidateInfo values simultaneously (~500 B each: verified manifest + 256-byte esp_app_desc_t + digest) before validateCandidate's own locals, then calls this twice.
- **Why it matters:** The chain cmd_exec_task -> executeCommand -> cmdOtaStage (~1.0 KB) -> validateCandidate -> hashAndDescribeImage (4.1 KB) -> LittleFS read path consumes ~5.5 KB of 8 KB, during the one operation that decides whether a firmware image is legitimate. The project already knows this frame is tight: HardwareOne.cpp:739-745 heap-allocates an identically-sized 4 KB capture buffer with the comment 'Heap-allocate the capture buffer to avoid blowing cmd_exec_task stack' — this new code puts the same size back on. The updater's own chunked hasher uses HW1_OTA_HASH_CHUNK_SIZE 1024 (hw1_ota_idf.c:9).
- **Fix:** Drop to 512-1024 bytes to match HW1_OTA_HASH_CHUNK_SIZE, or heap-allocate. Then re-measure cmd_exec_task's high-water mark with otastage in the path — the periodic watermark print at HardwareOne.cpp:701-706 will show it. Also fix the stale '32 KB stack' comment at System_TaskUtils.h:51.

### 4. Every BLE OTA frame re-derives superadmin from a full users.json read+parse under the FS lock

- **Severity:** high · **Category:** robustness · **Effort:** small
- **Location:** `components/hardwareone/System_OTA.cpp:820-825 (per frame); components/hardwareone/System_OTA.cpp:869-870 (per main-loop lap)`
- **What:** handleBleUploadFrame gates every accepted frame on isSuperAdminUser(user) before any cheap structural rejection (offset/size validation is at :837-838, after it), holding gBleUploadMutex across the whole thing. isSuperAdminUser (System_User.cpp:370-417) takes FsLockGuard, existsGuarded, readText(users.json) — which is PollPauseGuard + FsLockGuard + f.readString() of the whole file into a heap String — then an indexOf/substring roster scan. There is no cache anywhere. housekeepBleUpload does the same on every main-loop lap while a session is open.
- **Why it matters:** A 5.9 MB candidate at 477 bytes/frame is 12,365 frames; a realistic 2 MB image is ~4,400. Each one performs a whole-file flash read of an unrelated file, with sensor polling paused, under the same FS lock the OTA chunk write needs. Throughput is dominated by reading users.json rather than by writing firmware, and the repeated large transient String allocations are exactly the hot-path heap-fragmentation pattern this project already tracks. The housekeeping copy does the same from the main loop, so users.json is being read from two tasks concurrently for the whole transfer.
- **Fix:** Bind the authorized identity to the session once at 'otawrite begin': add a user field to BleUploadSession, and per frame compare against the live connection slot's in-RAM user string plus authed flag (Bluetooth.cpp:162-169). Re-run the full role derivation at most every few seconds if a periodic re-check is wanted. Same change fixes the housekeeping path.

### 5. Recovery updater's /status and serial `status` omit the journal result entirely

- **Severity:** high · **Category:** debuggability · **Effort:** small
- **Location:** `updater/main/updater_main.c:234-274 (status_json); updater/main/updater_main.c:196-212 (snapshot_record); updater/main/updater_main.c:82-99 (snapshot struct)`
- **What:** status_json emits state/detail/phase/source/journalSequence/mainValid/mainState/bytesWritten/imageSize/candidateVersion and nothing from record.last_result. The snapshot struct has no result fields at all, and snapshot_record copies only phase, source, sequence and candidate version. record.last_result is decoded by load_record() inside boot_reconcile and then discarded. print_status_console (:1752-1760) calls the same function, so the serial console is equally blind.
- **Why it matters:** An OTA fails overnight and the device parks in recovery. In the morning both operator surfaces show state:held, detail:'update failed; authenticated recovery is holding', phase:failed — while the actual result code (digest_mismatch vs flash_error vs rollback_detected vs power_unsafe) and the 96-byte detail string sit in NVS two functions away. The RAM `detail` only carries a real reason if the failure happened in this same session with no reboot, which is precisely the case where the operator was already watching. The main app's cmdOtaStatus does render these — so the blindness is confined to the exact window where it hurts most.
- **Fix:** In snapshot_record also copy last_result.code/.sequence/.native_error/.detail plus record.operation_id, request_flags and trial_boot_count; emit them from status_json as resultCode (name table mirroring System_OTA.cpp's resultName), resultSequence, resultDetail, nativeError (+esp_err_to_name), operationId, requestFlags, trialBootCount. Pure add to a function that already runs load_record at boot.

### 6. OTA has no durable log or event of any kind; the IDF-to-file bridge is off every boot and cannot be persisted

- **Severity:** high · **Category:** debuggability · **Effort:** medium
- **Location:** `components/hardwareone/System_Debug.cpp:1068 and :1091 and :1352-1355; components/hardwareone/System_OTA.cpp (zero ESP_LOG before line 1300, 25 sites at 1385-1661); components/hardwareone/System_OTASafety.cpp:70,143,238,247`
- **What:** System_OTA.cpp's entire diagnostic surface is ESP_LOG*/ESP_EARLY_LOG*. I confirmed there is literally no ESP_LOG anywhere before line 1300, so the whole staging/journal/command half logs nothing at all. The IDF log bridge that would route ESP_LOG lines into a file is `static volatile bool s_idfBridgeOn = false;` with the toggle documented 'Default OFF ... Runtime-only (not persisted yet)'. System_OTASafety uses ESP_EARLY_LOG*, which writes esp_rom_printf directly and cannot be bridged at all.
- **Why it matters:** A trial image is refused validation at 3am because the running app descriptor does not match the trial journal (System_OTA.cpp:1609). That single ESP_LOGE names the exact cause. Nobody has a cable attached, loglink was never turned on, and the device then rolls back — destroying the image, so unlike a staging refusal it is not reproducible afterwards. /system/sys_logs contains nothing about the OTA at all.
- **Fix:** Do not rely on the IDF log path for anything that must survive. Add logSystemEvent("OTA", ...) (System_Debug.h:241, file-backed, on by default) alongside each ESP_LOGE in otaSystemCanMarkImageValid (:1570/1586/1594/1603/1609/1624), otaSystemInitAfterStorage (:1515/1531/1540/1555) and otaSystemOnImageMarkedValid (:1638/1649/1661). The pre-storage paths — otaSystemCrashLoopEscapeEarly and otaSystemRecoverFromStorageFailure — cannot use the filesystem and must go to the NVS journal instead.

### 7. The recovery credential is silently trimmed, never echoed, and has no verification path

- **Severity:** medium · **Category:** robustness · **Effort:** small
- **Location:** `components/hardwareone/System_OTA.cpp:1044-1067 (cmdOtaPin); components/hardwareone/System_OTA.cpp:540-558 (credentialConfigured); updater/main/updater_main.c:506-538 (store_recovery_pin)`
- **What:** cmdOtaPin trims the input before storing it and returns only 'It is never shown by status.' The sole readback anywhere is a boolean: otastatus reports recoveryCredentialConfigured, and credentialConfigured() only checks that ap_pass and auth_token exist, are 12..63 bytes, and equal each other — it cannot compare against anything the operator knows. store_recovery_pin validates length and printability only, with no echo and no confirmation re-entry. There is no `otapin verify`, no stored fingerprint, and no reported length.
- **Why it matters:** This one string is the WPA2 PSK and the HTTP token and the only route into recovery. An operator who provisions with stray whitespace (script, copy-paste) stores the trimmed value while recording the untrimmed one; a single-character typo has the same effect. otastatus says 'configured' either way. Months later the device crash-loops into recovery, HW1-Recovery-XXXX appears, the recorded credential fails WPA2 association, and the operator cannot even reach the HTTP layer to see an error. The device the recovery updater exists to rescue is now cable-only, and nothing would have let them detect the mismatch while the firmware was healthy.
- **Fix:** Reject rather than silently trim leading/trailing whitespace, and add a constant-time `otapin verify <candidate>` that answers matches/does-not-match without disclosing the secret (or store and report a truncated HMAC fingerprint alongside the boolean). Either lets the operator confirm while the device is still reachable, which is the only time the check is useful.

### 8. `otapin clear confirm` removes the only route into recovery with no guard and no durable record

- **Severity:** medium · **Category:** robustness · **Effort:** small
- **Location:** `components/hardwareone/System_OTA.cpp:1047-1051; registration at components/hardwareone/System_OTA.cpp:1673-1675`
- **What:** The clear branch is the first thing cmdOtaPin does after the automation check, ahead of every other validation. No journal phase is loaded, no pending-result check runs, and ota_0's state is never consulted — unlike otastage (phase check at :1085-1089), otaupdate/otarecovery (credentialConfigured gate) or otaresetjournal (ORIGIN_SERIAL only at :1263). The table entry sets requiresSuperAdmin with no transport restriction, so web, BLE, MQTT and ESP-NOW sessions all reach it. No event is posted.
- **Why it matters:** start_network() refuses without a credential ('Persistent 12..63-character recovery credential unavailable; SoftAP remains off', updater_main.c:1262-1266). After a clear the device runs normally so nothing is noticed; later a crash loop or LittleFS failure redirects to factory as designed, the updater boots healthy, and refuses to raise the SoftAP. Combined with a corrupt journal or FAILED phase it parks in HELD, which process_idle_timeout skips. The exact failure this subsystem was built to survive becomes cable-only recovery, caused by a command that required no confirmation beyond the word 'confirm' and left no trace.
- **Fix:** Refuse the clear unless the journal is IDLE/terminal with no pending result and the running image is the validated main app; restrict it to ORIGIN_SERIAL the way otaresetjournal already is; and emit a durable SYSEVT so the clearing is visible in events.log afterwards.

### 9. The control watchdog flag gates far more than writes, with no self-heal and no visibility

- **Severity:** medium · **Category:** robustness · **Effort:** medium
- **Location:** `updater/main/updater_main.c:1674-1686 (boot_reconcile skipped); updater/main/updater_main.c:498-505 (latch); updater/main/updater_main.c:234-274 (not in status)`
- **What:** Two coupled defects on one flag. (a) control_task branches three ways and boot_reconcile() — its only call site in the file — is reachable from just one; a failed watchdog subscription takes the :1674 branch, which also sets UPDATER_STATE_HELD, so process_idle_timeout returns immediately. (b) feed_control_watchdog latches s_control_watchdog_active false on a single failed esp_task_wdt_reset and then never attempts a reset again; subscribe_control_watchdog is called only at boot and from the off-by-default formatfs command. status_json emits no field for it at all.
- **Why it matters:** (a) On a memory-tight boot after an overnight rollback, esp_task_wdt_add returns ESP_ERR_NO_MEM and the device skips sampling the installed image, converting TRIAL_RUNNING into a durable ROLLBACK_DETECTED, the reconcile pass, and the staged-apply resume. /status then reports mainValid:false, mainState:'undefined' for a perfectly good signed ota_0, the one breadcrumb explaining the rollback is lost forever, and the idle timeout cannot return to main because the state is HELD. A transient allocation failure becomes a permanent park with a corrupted diagnosis. (b) After one bad feed, every install is refused for the rest of the boot while the page still reads 'idle / authenticated factory recovery ready'.
- **Fix:** Run boot_reconcile unconditionally — it is the reconciliation and evidence step, not a write step; keep the write refusal keyed on the flag at the two entry points. Attempt re-subscription from the control loop when the flag is false. Surface the flag in status_json and in the snapshot detail so both surfaces say 'writes disabled: control watchdog unavailable' instead of 'ready'.

### 10. Verify chain makes two full-image flash passes with zero watchdog feeds on the panic-armed control task

- **Severity:** medium · **Category:** robustness · **Effort:** small
- **Location:** `components/hw1_ota_protocol/hw1_ota_idf.c:97-106 and :139-146; updater/main/updater_main.c:791-794 and :845-858`
- **What:** hw1_ota_idf_sha256_partition's read loop contains no watchdog call, and hw1_ota_idf_verify_partition runs esp_image_verify (a second full-image SHA-256 plus RSA-3072 signature-block verification) immediately before it with nothing between. On the control task the whole chain sits between two feeds: feed_control_watchdog() at :791, updater_verify_written_candidate at :792, feed_control_watchdog() at :794. The control task is the sole TWDT subscriber with trigger_panic=true and a 15000 ms default timeout. The sibling hash loop in updater_preflight.c:400 does feed every 4 KiB, so this is an inconsistency rather than a convention.
- **Why it matters:** A staged apply performs two complete ~5 MB reads of ota_0 plus an RSA-3072 verification with no reset for the entire stretch, and on feathers3_fe every one of those ~10,400 partition reads also runs XTS-AES decryption. If it crosses 15 s the TWDT panics the recovery firmware — the one component that must never crash — at the worst possible moment: ota_0 fully written and verified, journal not yet at IMAGE_VERIFIED, boot partition not yet set. The next boot re-enters recovery, finds APPLYING, and repeats the same unfed verify, so the panic is reproducible rather than transient. Nothing measures the actual margin.
- **Fix:** Feed inside hw1_ota_idf_sha256_partition's loop using the same esp_task_wdt_status(NULL)==ESP_OK guard as updater_preflight.c:31-36 (it is the ESP-IDF adapter, so the protocol core stays ESP-IDF-free), and add a feed between esp_image_verify and the hash pass. Log the elapsed time of updater_verify_written_candidate so the real margin against the 15 s timeout is measurable before a field board finds it.

### 11. Downgrade and forced-power-override consent leak from a FAILED transaction into an unrelated upload

- **Severity:** medium · **Category:** security · **Effort:** small
- **Location:** `updater/main/updater_main.c:943-956; consumed at :981-984, :1088-1096, :721-723`
- **What:** accept_manifest computes `retry_flags = record.phase == HW1_OTA_PHASE_FAILED ? record.request_flags : 0;` and passes it verbatim into hw1_ota_begin for a brand-new RECOVERY_UPLOAD operation. hw1_ota_begin applies no per-source masking — it only rejects bits outside KNOWN_FLAGS then assigns. Both consumers go live for the new operation: the downgrade allowance, and the skip of updater_power_require_safe. HW1_OTA_REQUEST_FORCED_POWER_OVERRIDE is only ever set by the main app (System_OTA.cpp:1184), and status_json emits no requestFlags, so neither permission is visible anywhere.
- **Why it matters:** After a staged apply fails inside the updater the device stays in recovery, so the operator's very next gesture is a SoftAP POST /manifest — exactly the inheriting path. A completely unrelated signed image is then accepted without the /allow-downgrade gesture, and a ~5 MB erase+write into ota_0 starts with the power-safety check skipped entirely, possibly at 5% battery with no USB. This is not an authentication bypass — every image is still RSA-3072 verified — but two operator consent gestures silently widen their scope, and the power-safety skip is the sharper half.
- **Fix:** Do not inherit permission flags across a source change or a new operation_id: reset retry_flags to 0 as the CANCELED/SUCCEEDED path already does, or mask inheritance to flags whose original source matches the new source. Add requestFlags to status_json so a live downgrade or power override is visible.

### 12. One never-rotated operator-typed secret serves as both the WPA2 PSK and the HTTP admin token

- **Severity:** medium · **Category:** security · **Effort:** medium
- **Location:** `updater/main/recovery_network.c:437-443; updater/main/updater_main.c:506-538; components/hardwareone/System_OTA.cpp:551-553 and :561-574`
- **What:** recovery_network_start refuses to run unless ap_password and auth_token are byte-identical and 12..63 chars. store_recovery_pin (the only writer, from serial `setpin`) checks length and printability only — 'passwordpass' passes — and writes the same string to both NVS keys; the main app's storeCredential does the same and credentialConfigured enforces the equality on read. esp_random() exists in the file but is used only for operation ids, never for credential generation, and there is no rotation path.
- **Why it matters:** There is exactly one secret in the entire recovery path, human-chosen, static across reboots and sessions. Capturing one WPA2 4-way handshake and cracking a 12-character passphrase offline does not just yield network access — it simultaneously yields the full HTTP credential, so there is no second factor between the radio and /apply, /allow-downgrade, /firmware and /reboot, and no session or expiry to close. The HTTP auth layer adds zero security over the WiFi layer. What it buys an attacker is bounded by the RSA-3072 signature policy — reboot, cancel, apply of an already-verified pair, and version choice among validly signed images — so this is DoS and downgrade authority, not arbitrary code execution.
- **Fix:** Generate the credential on-device with esp_random() (20+ chars from a 62-symbol alphabet), print it once on serial, and derive a distinct HTTP token from a separate random draw so a cracked PSK is not automatically console authority. At minimum drop the equality requirement and let setpin take two values. Note this is a documented pre-production decision (docs/OTA_RECOVERY_UPDATER.md:984-993) that has not been made yet.

### 13. Filesystem-init failure discards the recovery return value and hangs in while(1)

- **Severity:** medium · **Category:** robustness · **Effort:** small
- **Location:** `components/hardwareone/HardwareOne.cpp:1362-1369; components/hardwareone/System_OTA.cpp:1448-1508`
- **What:** `(void)otaSystemRecoverFromStorageFailure(); while (1) delay(1000);` — the bool is explicitly discarded. That function has five non-restarting false returns: not running from ota_0 (:1451), loadRecord failure (:1455), resumeRecoveryBootIntent failure (:1463), an active non-terminal phase (:1481), and hw1_ota_begin/commitRecord/bootRecoveryForRecord failure (:1493). esp_restart() is only reached at :1503, and the non-OTA #else path returns false unconditionally, so ordinary builds always hang here.
- **Why it matters:** LittleFS will not mount — the exact field failure this path exists for — AND the NVS journal is also unreadable, a plausible pairing since both live on the same flash die with the same corruption causes. The function logs and returns false, and the device spins forever. No reboot, no factory recovery, no serial CLI (Serial.begin ran but the CLI never starts), and no watchdog reset because delay() yields so the TWDT never trips on an unsubscribed task. The only recovery is a USB cable and a full reflash — the outcome this whole subsystem was built to avoid.
- **Fix:** On a false return, fall back to esp_ota_set_boot_partition(factory) + esp_restart() unconditionally, and if even that fails, esp_restart() on a timer rather than hanging. A reboot loop is diagnosable and leaves the bootloader a chance; a silent hang does not.

### 14. Five distinct probation abort causes collapse into one durable rollback_detected

- **Severity:** medium · **Category:** debuggability · **Effort:** medium
- **Location:** `components/hardwareone/System_OTASafety.cpp:69-77, callers at :90, :97, :103, :139, :216; updater/main/updater_main.c:1396-1404`
- **What:** rebootPendingImage does exactly one thing with its `reason` argument — ESP_EARLY_LOGE — then vTaskDelay(100) and esp_restart(). Nothing between the log and the restart touches NVS or any file. The five callers pass five different reasons: setup did not reach RUNNING in 5 minutes, no main-loop heartbeat for 30 s, healthy probation did not complete in 5 minutes, could not create the probation supervisor, and OTA trial journal missing or inconsistent. On the recovery side all five become the fixed `.result_code = HW1_OTA_RESULT_ROLLBACK_DETECTED, .detail = "trial main returned to factory recovery"`.
- **Why it matters:** At 3am a trial image is aborted, rolled back, and parked in recovery. The operator sees one thing: rollback_detected. They cannot distinguish 'the new firmware hung in setup' from 'the main loop stalled' from 'a healthy 60s window never accumulated' from 'the journal was inconsistent so the image was refused validation'. Those demand completely different next actions — fix a boot hang, fix a loop stall, run otaresetjournal — and the information existed as a string literal at the moment of the reboot. The device still rolls back correctly; this is lost diagnosis, not lost safety.
- **Fix:** Persist a reason code before esp_restart(). The record wire format has unused reserved bytes at offsets 12-15 and 34-35 (enforced zero at hw1_ota_protocol.c:770) and there is no backwards-compat requirement, so add a probation_abort_reason byte. Cheapest alternative needing no protocol change: nvs_set_u8 + nvs_commit in rebootPendingImage, read back by cmdOtaStatus and the updater's status_json — but note otaSafetyInitEarly runs before initArduino (main/hardwareone-idf.cpp:39 vs :42), so NVS is not up for the supervisor-alloc-failure case.

### 15. `idf.py erase-flash` bypasses the guard list entirely, and the docs say it is blocked

- **Severity:** medium · **Category:** security · **Effort:** small
- **Location:** `CMakeLists.txt:515-524; docs/OTA_RECOVERY_UPDATER.md:615-620`
- **What:** The refusal foreach includes erase_flash, but ESP-IDF 5.5.1 does not build that CMake target for the `idf.py erase-flash` action: serial_ext.py:243-248 defines it as ensure_build_directory() then a direct RunTool('esptool.py', ...), with both 'erase-flash' and 'erase_flash' mapped to that callback. By contrast `flash`, `app-flash`, `partition-table-flash` and `erase-otadata` all go through run_target() and ARE genuinely gated. The CMake target erase_flash does exist, so `ninja erase_flash` is refused — only the idf.py entry point escapes.
- **Why it matters:** docs/OTA_RECOVERY_UPDATER.md:615-620 tells operators that stock variants, erase_flash and erase-otadata 'are disabled for this layout'. An operator who has internalised that runs idf.py erase-flash on a migrated device; esptool runs directly and the whole 16 MB chip goes — factory recovery updater, ota_0, otadata, NVS, and the relocated LittleFS with all user and health data — with no prompt. On a feathers3_fe unit the encryption eFuses survive but every image is gone. The false confidence is documented, which is what makes it worth fixing rather than shrugging at.
- **Fix:** Correct the documentation to state plainly that whole-chip erase is NOT gated, and either drop the misleading foreach entry or add a real guard — an idf.py extension or a tools/ota wrapper script as the only supported entry point for cable operations. Keep erase-otadata/erase_otadata in the list; those genuinely work.

### 16. cmd_exec heartbeat is stamped only at the top of the receive loop, so a busy command reads as wedged

- **Severity:** medium · **Category:** correctness · **Effort:** medium
- **Location:** `components/hardwareone/HardwareOne.cpp:698 and :2756-2759; components/hardwareone/System_OTASafety.cpp:185-190 and :100-104`
- **What:** sCmdExecHeartbeatMs.store(millis()) is at the top of the for(;;), before xQueueReceive and before the execute block — nothing re-stamps it while a command runs, so it is stale for the full duration of any single command. ### 26. chunkMax is a compile-time 477 assuming MTU 517, with no MTU tracking anywhere

### 27. HTTP auth throttle is global, self-lockable, and launderable by the page's own status poll

### 28. set_terminal_result rejects the whole transition on a >=95-byte or non-printable detail

- **Severity:** low · **Category:** robustness · **Effort:** small

## Verified sound (do not re-audit)

- Wire parsing is genuinely hardened. Both parsers demand an exact length up front (hw1_ota_protocol.c:493 for the 224-byte manifest, :767 for the 384-byte record), so no attacker-controlled length exists anywhere; every memcpy uses a compile-time sizeof against a fixed struct field. text_is_canonical (:77-101) sweeps the padding, so each string has exactly one canonical encoding and no unterminated field can escape. I walked all 384 record bytes and the reserved-zero checks cover the layout with no gaps.
- The semver parser cannot overflow: parse_core_number accumulates into uint64_t and checks > UINT32_MAX after every digit, rejects leading zeros, and never reads past the NUL. The asymmetric prerelease comparison at :371-404 was traced by hand across five cases and is correct.
- Signature coverage is complete for what it claims. The verifier gets the full 224-byte payload containing every field the device acts on, and image_sha256 transitively authenticates the whole image because it is compared against a hash of exactly image_size bytes. Ordering is fail-closed: NULL verifier -> AUTH_REQUIRED, wrong-length signature -> SIGNATURE_INVALID, any verifier error collapses to SIGNATURE_INVALID, and verified_manifest is memset first. hw1_ota_idf.c:12-14 #errors out on MBEDTLS_USE_PSA_CRYPTO, which is what actually guarantees the 32-byte salt is enforced rather than silently accepted at any length — someone thought about that.
- The 'persisted candidate bytes never authorize an install' rule is honored end to end. hw1_ota_record_candidate_matches_verified re-encodes both manifests and memcmps the canonical payload; every apply path re-verifies the RSA-PSS envelope first (updater_main.c:833-838, :1051-1058; System_OTA.cpp:1163-1172); and boot_reconcile explicitly refuses to auto-commit any event other than RECOVERY_STARTED/APPLY_STARTED for exactly this reason (updater_main.c:1370-1375).
- No unverified byte ever becomes bootable. The order is stream -> full-stream SHA-256 against the signed manifest -> esp_ota_end (which runs esp_image_verify including the app signature, since SECURE_SIGNED_ON_UPDATE is on) -> re-read and re-hash the written partition and re-check the manifest contract -> journal commit -> only then esp_ota_set_boot_partition, which itself re-validates the target.
- There is no resume-from-offset and no splicing is possible: /firmware is a single PUT whose content_length must equal the signed image_size exactly, every byte including the 288-byte prefix feeds one hash stream, and OTA_WITH_SEQUENTIAL_WRITES only advances from 0. All abort paths leave otadata alone, so a failed upload simply reboots into recovery.
- Authorization is real rather than table-only. Every mutating ota* row uses the 8-argument CommandEntry form whose trailing `true` binds to requiresSuperAdmin (the 9-arg overload cannot match because `true` will not convert to const char*), commandRequiresSuperAdmin reads it directly, and authorizeCommand enforces before dispatch. Every mutating handler additionally rejects automation origin, and otaresetjournal further restricts to ORIGIN_SERIAL.
- The BLE staging path is correctly bound. currentSecureBleConnection requires ORIGIN_BLUETOOTH + SOURCE_BLUETOOTH + an established channel + a live superadmin; it uses bleGetAuthenticatedUser (which requires connections[slot].authed), so the AuthBypass pseudo-identity stamped when bleRequireAuth is false can never reach otawrite. Offset handling is strict-append and underflow-safe. Replay is blocked at both layers: a strictly increasing counter feeding the AEAD nonce intra-session, and fresh X25519 ephemerals plus a fresh device nonce per handshake across sessions.
- BTC_TASK discipline is respected: the GATT write callback does only a size check, a PSRAM copy and a queue push; all handshake crypto, decryption, filesystem writes and hashing run on cmd_exec_task. Lock ordering is consistent everywhere (gBleUploadMutex then FsLock, never the reverse) and housekeeping uses a zero-timeout take so the main loop cannot block on it.
- /system/ota is genuinely locked down against the other local surfaces — System_Filesystem.cpp:1371 gives it userPerms=0 and adminPerms=0, so the web file manager, ESP-NOW browser, G2 viewer and OLED browser cannot touch staging even as an ordinary admin.
- Arduino's auto-validate is genuinely defeated: main/hardwareone-idf.cpp:17-19 provides a strong verifyRollbackLater() overriding the weak definition at esp32-hal-misc.c:243-246, and otaSafetyInitEarly runs before initArduino. The probation design actually holds rather than being silently short-circuited.
- The probation state machine is carefully written: publish-before-transition in otaSafetySetupReachedRunning avoids a false hang diagnosis (and its comment accurately explains the race), the CAS into MarkingValid prevents double-marking, a failed mark_app_valid returns to Running for a rate-limited retry rather than giving up, and the supervisor is pinned to core 1 so a core-0 spin cannot starve it.
- Every recovery HTTP endpoint is authenticated with no ordering bypass — all eight call require_authorization as their first statement and return immediately on failure. No endpoint leaks the token, PSK, key material or filesystem contents. The AP is never up before a credential exists (start_network refuses without a validated 12..63-char pair), authmode is unconditionally WPA2_PSK with no open-AP window and no hardcoded default, esp_wifi_set_storage(RAM) plus WIFI_NVS disabled keeps the PSK out of the WiFi namespace, and the updater has no PSRAM so the token cannot land in probeable external RAM.
- Base64 auth decoding is bounds-safe end to end, chunked bodies cannot bypass the size checks (content_len is 0 for chunked, which is rejected), and the serial-only gates hold: CONTROL_START_NETWORK, CONTROL_RESET_JOURNAL and CONTROL_FORMATFS all re-check command.from_serial inside control_task, and no HTTP endpoint can emit any of the three.
- The build-time pair audit does real work: it fingerprints the canonical DER of each build's derived public key and requires them equal, runs espsecure verify_signature on both binaries, requires both emitted partition tables to be byte-equal to each other and to a table freshly compiled from the repo CSV with the build's own ESP-IDF, and requires matching IDF revisions. It is a hard dependency of every cable-write target, so a key or layout mismatch cannot reach a device.
- Build-directory isolation (hw1-layout-mode.txt) prevents reusing an ordinary build dir for an OTA build and vice versa, and CMakeLists.txt:481-494 reads COMPILE_DEFINITIONS back off the target and fails if HW1_OTA_LAYOUT/BOARD_ID/LAYOUT_ID did not land — the plumbing verifies itself rather than hoping.
- No private key material is committed: sdkconfig.ota and both updater sdkconfigs are gitignored generated artifacts, ota_signing_key.pem is ignored in both projects, and `git ls-files updater/` returns nothing. The build actively strips a stale signing-key line and regenerates it from HW1_OTA_SIGNING_KEY on every configure, and FATAL_ERRORs when the key path does not exist — key loss fails loudly.
- Host tooling never materialises the private key: sign_payload passes only the key path in argv and receives the signature through a file in a TemporaryDirectory. There is no verify=False anywhere; CERT_NONE is only reachable via explicit --insecure and is constructed in the correct order. Passwords use getpass or --password-env, never argv, and the recovery transport passes the Basic credential on stdin rather than in the adb command line.
- The Python encoder agrees with the C byte for byte. I checked every offset (magic@0, formatVersion@4, size@6, boardId@8, layoutId@32, projectName@56, version@88, imageSize@136, sha256@140, minUpdater@172, dataSchema@204, reserved 208-219, CRC@220 over [0,220)), the reflected CRC32, the printable-ASCII rule and the canonical NUL-padding rule. PSS parameters match on all three sides. The only divergence is the missing semver check.
- The bundle format is properly reproducible — ZIP_STORED, fixed 1980 timestamps, fixed member order and external_attr — and a test asserts two independent builds are byte-identical. Backup integrity is verified on restore before any device mutation, users.json is uploaded last and read back, and the tool refuses a restore that would revoke the active session's superadmin.
- Automatic staged retries terminate: boot_reconcile only re-enters apply_staged for a bounded phase set, and a failure moves the journal to FAILED which is not in that set — exactly one attempt per boot, no silent loop that could repeatedly erase ota_0.
- The --wrap interposers on nvs_flash_erase and esp_partition_erase_range are actually linked rather than inert, the updater mounts LittleFS read-only with format_if_mount_failed=false, and formatfs is compile-gated off by default and serial-only.
