## 2. The serious ones

### 2.1 OLED Map → Live Track silently corrupts a running Health Track file and switches Health Track off

Two taps from the shipped UI. Highest impact × highest confidence in the audit, and no area verifier could see it because it spans the Map caller, the format command and the row builders.

[OLED_Mode_Map.cpp:1526](components/hardwareone/OLED_Mode_Map.cpp:1526) gates on `GPSTrackManager::isLiveTracking()` — **not** on `gSensorLoggingRunning` — then fires three commands whose returns are all discarded:

```c
1537              executeOLEDCommand("sensorlog format track");
1538              executeOLEDCommand("sensorlog sensors gps");
1539              executeOLEDCommand("sensorlog start /logging_captures/tracks/live.csv 1000");
```

With a Health Track CSV session already running:

1. [System_SensorLogging.cpp:1253-1258](components/hardwareone/System_SensorLogging.cpp:1253) has **no** `gSensorLoggingRunning` test anywhere in the `format` block (1230-1262):
   ```c
   1255      gSensorLogMask = LOG_GPS;  // Track format is GPS-only
   1257      setSetting(gSensorLogMask, ...);
   ```
   `LOG_R1` is dropped and *persisted*, so `healthTrackIsActive()` at [:1443](components/hardwareone/System_SensorLogging.cpp:1443) goes false while `gSettings.healthTrackingEnabled` stays true.
2. `sensors gps` then sails through the *one* guard that exists, [:1345](components/hardwareone/System_SensorLogging.cpp:1345) `if (gSensorLoggingRunning && gSensorLogFormat == SENSOR_LOG_CSV)` — because step 1 already flipped the format the guard is conditioned on.
3. Only the third call fails, at [:1091](components/hardwareone/System_SensorLogging.cpp:1091), and its return is thrown away.

Net: the tick now routes through `buildTrackFromSnap`, so the live day file — created with the R1 header from `buildCsvHeader(LOG_R1)` — starts receiving `HH:MM:SS,lat,lon,alt,speed,sats` rows mid-file. The CSV roll gate at [:866](components/hardwareone/System_SensorLogging.cpp:866) requires `SENSOR_LOG_CSV`, so nothing rescues it. R1 vitals stop being recorded with no error on any surface, and `healthtrack status` reports "inactive" while the setting says "on".

**Fix:** a running-session refusal in the `format` block — but written as `gSensorLoggingRunning && fmt != gSensorLogFormat`, **not** gated on `== SENSOR_LOG_CSV` the way :1345 is, or `format csv` from a running TRACK session slips through the same hole. The already-designed `sensorLogSetFormat` chokepoint (`R1_HEALTH_CLOCK_AND_ACTIVITY_RESOLUTIONS.md:122-138`) is exactly this and covers all six format surfaces instead of one; use it rather than patching this branch. The Map path additionally needs to stop the session explicitly or refuse, and must stop discarding returns. **Effort: under an hour** (as part of WP4).

### 2.2 `healthlogmerge` writes through an unscoped system identity — an ordinary admin can truncate admin-read-only system logs

[System_SensorLogging.cpp:2007](components/hardwareone/System_SensorLogging.cpp:2007) + [:2024](components/hardwareone/System_SensorLogging.cpp:2024):

```c
2007  const AuthContext  sysCtx = VFS::systemAuth("health.stitch");
2024  File out = VFS::openGuarded(outPath, "w", sysCtx, true);
```

The single-arg overload leaves `ctx.scope` empty, so `pathWithinScope` is a no-op and `permsForRole` returns `rule.systemPerms` — `PERM_ALL` on every rule, including the one where admins are deliberately read-only, [System_Filesystem.cpp:1367](components/hardwareone/System_Filesystem.cpp:1367):

```c
{"/system/sys_logs/",  0,  PERM_READ,  PERM_ALL,  false, false},
```

The command is `requiresAdmin`, not `requiresSuperAdmin` ([:2098](components/hardwareone/System_SensorLogging.cpp:2098)), and the extension coercion at [:2003](components/hardwareone/System_SensorLogging.cpp:2003) accepts `.log` unchanged. So `healthlogmerge "/system/sys_logs/command-audit.log" "<any capture>"` truncates the audit record of the act and reports success. Same for `errors.log`, `failed_login.log`, `crash-history.log`, `events.log`.

Fixing only the sensor side hardens the command nobody calls. **Effort: minutes.**

### 2.3 `healthlogmerge` arg-0 truncation zeroes a real capture on the more natural CLI order

Established fact #4, with the mechanism corrected: inputs **are** validated first ([:2010-2019](components/hardwareone/System_SensorLogging.cpp:2010) is a full pre-flight loop with `requireQuotedPath`, the `in == outPath` compare at [:2014](components/hardwareone/System_SensorLogging.cpp:2014), and `existsGuarded`). What is missing is any validation of the **output** — no `existsGuarded(outPath)`, no confirm token, and the self-overwrite guard covers only inputs.

`healthlogmerge "day1.csv" "day2.csv" "merged.csv"` — output-last, the order most people type — truncates `day1.csv` at :2024 and refills it with `day2.csv`, printing `Stitched 2 files into /logging_captures/sensors/day1.csv`. LittleFS has no trash.

The same shape hits the **live** capture: `gSensorLoggingRunning`/`gSensorLogPath` are file-scope globals in the same TU ([:71-72](components/hardwareone/System_SensorLogging.cpp:71)) and are never consulted. Aftermath differs slightly from the raw finding: `gApproxSizeBytes` is not reset, so the next append still sees it over the cap and the rotation at [:947](components/hardwareone/System_SensorLogging.cpp:947) immediately renames the stitched output to `.1` — today's rows lost, plus a phantom rotation sibling.

**Fix:** copy `cmd_filedelete`'s bare-token gate ([System_Filesystem.cpp:1151-1159](components/hardwareone/System_Filesystem.cpp:1151)) and the active-file guard from [System_TimeAnchors.cpp:242](components/hardwareone/System_TimeAnchors.cpp:242). Two traps: the input loop bound at :2010/:2033 must exclude a trailing `confirm` token, and the normalization half must use `normalizeFsPath` ([System_Filesystem.cpp:1458](components/hardwareone/System_Filesystem.cpp:1458), which the open actually uses and which rejects `..`), **not** `VFS::normalize`. **Effort: minutes.**

### 2.4 CSV rows change column count against a fixed header — and a compile-disabled sensor makes it permanent

`buildCsvHeader` is mask-only ([:135-161](components/hardwareone/System_SensorLogging.cpp:135)). Four row blocks carry an extra validity conjunct:

```c
475      if ((gSensorLogMask & LOG_THERMAL) && s.thermalValid && remaining > 0) {
482      if ((gSensorLogMask & LOG_TOF)     && s.tofValid     && remaining > 0) {
502      if ((gSensorLogMask & LOG_GAMEPAD) && s.inputValid   && remaining > 0) {
509      if ((gSensorLogMask & LOG_APDS)    && s.apdsValid    && remaining > 0) {
```

while IMU ([:492](components/hardwareone/System_SensorLogging.cpp:492)), GPS ([:517](components/hardwareone/System_SensorLogging.cpp:517)), PRESENCE ([:526](components/hardwareone/System_SensorLogging.cpp:526)) and R1 ([:535](components/hardwareone/System_SensorLogging.cpp:535)) are correctly mask-only. R1 is the pattern to copy verbatim — [:536](components/hardwareone/System_SensorLogging.cpp:536) `// Empty fields when invalid so CSV stays column-aligned.`

Two triggers, one transient and one permanent:

- `SensorCacheSnapshot snap = {};` at [:607](components/hardwareone/System_SensorLogging.cpp:607) with `pdMS_TO_TICKS(10)` acquire timeouts on every populate block ([:612](components/hardwareone/System_SensorLogging.cpp:612), :625, :663, :680) means plain **mutex contention** drops 3 or 12 columns for that row. Thermal is the first optional block, so its miss shifts everything.
- **NEW, and worse:** the mask is settable for a sensor the build does not have — [:1373](components/hardwareone/System_SensorLogging.cpp:1373) `else if (sensor == "tof") gSensorLogMask |= LOG_TOF;` has no `#if`, while the only writer of `s.tofValid` is inside `#if ENABLE_TOF_SENSOR` at [:623](components/hardwareone/System_SensorLogging.cpp:623). With that sensor compiled out, **every row** is 12 columns short of its own header, forever, as a constant left-shift. This is the board-gating hazard the repo already warns about: invisible on a FeatherS3 with ToF enabled.

Concrete failure: `sensorlog sensors all; sensorlog format csv; sensorlog start /logging_captures/sensors/mix.csv` → 48-column header, 45-value rows on any contended tick, `imu_yaw` under `thermal_min`, `r1_wear` absent. Not reachable for a Health Track capture (mask == `LOG_R1`, and R1 is last and correctly padded).

**Fix:** delete the four conjuncts, pad inside each block like R1 does. Also fix the `remaining > 0` guards — a truncating row silently drops trailing columns too. Add a debug-only comma-count assert against `buildCsvHeader(gSensorLogMask)` rather than a literal, so it cannot drift. **Effort: a session, and it must land inside WP4** — the 7→14 column change touches the same two functions.

### 2.5 `gSensorLogPath` is a heap-backed `String` written from three tasks and read unlocked from five sites

Writer with no lock held: [:1201](components/hardwareone/System_SensorLogging.cpp:1201) `gSensorLogPath = filepath;` — the only `fsLock` in that function closed 22 lines earlier at :1176-1179, and :1180-1200 is pure CPU work. Reader: [:891](components/hardwareone/System_SensorLogging.cpp:891) `VFS::resolveOverflowPath(gSensorLogPath.c_str(), ...)` inside `FsLockGuard appendGuard` at [:855](components/hardwareone/System_SensorLogging.cpp:855) — a guard the writer never takes, so it protects nothing here.

The parallelism is genuine, not merely preemptive. The reader runs in `sensorLogTick()` from `hardwareone_loop()` → `main/hardwareone-idf.cpp:52`, i.e. the ESP-IDF main task pinned to CPU0 (`sdkconfig:1773 CONFIG_ESP_MAIN_TASK_AFFINITY_CPU0=y`) with Arduino's own `loopTask` compiled out (`sdkconfig:603 # CONFIG_AUTOSTART_ARDUINO is not set`). The writer is reachable on `cmd_exec_task` (core 0) and on `g2_session_w` (**core 1**), which calls `g2HealthAction()` → `healthTrackSet()` → `healthTrackRestartWithCurrentMask()` → `cmd_sensorlog` → :1201.

Both String failure modes are real against this tree's `WString.cpp`:
- new length ≤ capacity (the common case — `…/2026-07-28/health-2026-07-28.csv` → `…/2026-07-29/health-2026-07-29.csv`, identical length): `reserve()` returns early at [WString.cpp:173](components/arduino/cores/esp32/WString.cpp:173) and `copy()` memmoves in place → reader `snprintf`s a **torn** path, and `openGuarded(..., create=true)` at [:894](components/hardwareone/System_SensorLogging.cpp:894) silently creates a stray file with one row in it.
- new length > capacity: [WString.cpp:212](components/arduino/cores/esp32/WString.cpp:212) `realloc(isSSO() ? nullptr : wbuffer(), newSize)` may relocate and free → reader holds a freed pointer; heap poisoning leaves `0xFE` with no NUL.

The opposite direction is also open and is what defeats the obvious fix: the **tick itself** reassigns the path at [:879](components/hardwareone/System_SensorLogging.cpp:879) during the midnight/sync roll, while readers at [:1045](components/hardwareone/System_SensorLogging.cpp:1045), :1886, :1894, :1952 and [i2csensor_pa1010d.cpp:741](components/hardwareone/i2csensor_pa1010d.cpp:741) take no lock at all.

**Fix:** `char gSensorLogPath[128]`, written before `gSensorLoggingRunning = true`. That removes the realloc entirely (worst case degrades to a benign torn read — the tradeoff [:120-127](components/hardwareone/System_SensorLogging.cpp:120) already accepts for `gApproxSizeBytes`) and matches the `activePath[128]` / `resolved[128]` buffers used at :890, :213, :246. **This must be one commit with the `strncmp` change at [System_TimeAnchors.cpp:242](components/hardwareone/System_TimeAnchors.cpp:242)** — see §7 WP3; shipping it alone is worse than shipping nothing. **Effort: under an hour; needs a hardware test.**

### 2.6 `registryPersist` rewrites `.anchors.csv` from the ≤32-entry RAM cache — the first routine promotion atomically destroys older anchors

[System_TimeAnchors.cpp:99-115](components/hardwareone/System_TimeAnchors.cpp:99) writes the tmp file from `gAnchorCount`, which `registryLoad` hard-caps at 32 ([:38](components/hardwareone/System_TimeAnchors.cpp:38) `kMaxAnchors = 32`, drop-oldest at [:77](components/hardwareone/System_TimeAnchors.cpp:77)), then [:113](components/hardwareone/System_TimeAnchors.cpp:113) `VFS::renameGuarded(tmpPath, kAnchorsPath, ...)`. Its only caller is `registryPrune`, reached from [:302](components/hardwareone/System_TimeAnchors.cpp:302) inside `if (VFS::rmdirGuarded(folderPath, ctx))` — i.e. on every successful boot-folder promotion, which is routine.

Failure: a device with 200 boots has 200 anchor lines. One folder from boot 40 failed to promote once (±40-day sanity window at :253-255, or its file was held open). The next successful promotion of any *other* folder rewrites the registry with the newest ≤31 boots. Boot 40's anchor is gone from disk permanently; the folder is now unpromotable and its rows unmappable, with no diagnostic. The write-tmp-then-rename that exists to make the write crash-safe is what makes the loss irreversible.

The unbounded-growth half is also real but structural rather than pathological: `writeAnchorLine` appends for **every synced boot** ([:389-393](components/hardwareone/System_TimeAnchors.cpp:389)) whether or not it captured anything, while prune fires only on a successful rmdir — so a device that never runs `sensorlog` accumulates ~24 bytes/boot forever and re-reads it byte-at-a-time on the main loop ([:61-63](components/hardwareone/System_TimeAnchors.cpp:61)).

**Fix:** make `registryPersist` filter the **file** into the tmp file rather than dumping the cache, and add "boot folder no longer exists" as a prune criterion — that is the only rule that bounds the file on a non-capturing device. Do **not** raise `kMaxAnchors`: it makes the O(n) byte-at-a-time load worse. The proposed "never evict a line whose folder still exists" must live in `sweepPass`, not `registryFind` — the module deliberately loads outside the scan guard ([:311-314](components/hardwareone/System_TimeAnchors.cpp:311)). **Effort: under an hour.**

### 2.7 Rotation discards every rename/remove return, and on the SD tier with `rotations 1` the active log grows without bound

Three discarded returns — [:930](components/hardwareone/System_SensorLogging.cpp:930), [:942](components/hardwareone/System_SensorLogging.cpp:942), [:948](components/hardwareone/System_SensorLogging.cpp:948) — then [:954](components/hardwareone/System_SensorLogging.cpp:954) `gApproxSizeBytes = 0;` and [:955](components/hardwareone/System_SensorLogging.cpp:955) `log_trunc++` run unconditionally. A failed rotation is recorded as a successful one.

With `gSensorLogMaxRotations == 1`, [:926](components/hardwareone/System_SensorLogging.cpp:926) `if (gSensorLogMaxRotations > 1)` skips the oldest-delete and the shift loop at [:937](components/hardwareone/System_SensorLogging.cpp:937) runs zero iterations, so :948 renames base → `.1` with `.1` still present. On LittleFS that overwrites ([System_VFS.cpp:478](components/hardwareone/System_VFS.cpp:478)). On SD it **cannot**: [System_VFS.cpp:474](components/hardwareone/System_VFS.cpp:474) `return SD.rename(from.c_str() + 3, to.c_str() + 3);` → `vfs_fat_rename` is a bare `f_rename` with no unlink, and `f_rename` returns `FR_EXIST` on collision. Verified from the toolchain source on this machine, so this is confirmed, not inferred: the rename fails forever, the counter is zeroed anyway, `log_trunc` counts a rotation that never happened, and the file grows another full `maxSize` per cycle without bound. Tier-gated, so a flash-only test never sees it.

**Fix:** check all three returns; skip the bookkeeping on failure and emit one `logSystemEvent`. **Effort: minutes.** Note the same FatFs semantics booby-trap the proposal to route `.anchors.csv` through `resolveOverflowPath` — `registryPersist`'s tmp→live rename would silently stop working on SD. Don't do that (§7).

### 2.9 A 127-character path makes rotation delete the live log

[:890](components/hardwareone/System_SensorLogging.cpp:890) `char activePath[128]`; [:928](components/hardwareone/System_SensorLogging.cpp:928) `snprintf(oldestFile, sizeof(oldestFile), "%s.%d", activePath, ...)`. When `activePath` is exactly 127 chars, `oldestFile` truncates to byte-identical, so :929-930 `existsGuarded`/`removeGuarded` **delete the live log** and :939-942 rename it to itself — the `rotations 0` behaviour with rotations at its default 3.

Reachability is narrow and worth stating plainly: not reachable from any shaped, default or healthtrack path (I re-measured the shaper's worst case at 83 chars including `/sd` and `.N`, against a `pathBuf[256]` at [:1817](components/hardwareone/System_SensorLogging.cpp:1817)), fully reachable from a hand-typed `sensorlog start` path, since the only validation at [:1109](components/hardwareone/System_SensorLogging.cpp:1109) is "starts with /" and the mkdir walk at :1116-1136 creates deep paths happily. `CONFIG_LITTLEFS_OBJ_NAME_LEN=64` (`sdkconfig:2866`) caps a single *component*, not the path.

**Fix:** reject paths over ~100 chars at :1109 (128 − 3 for `/sd` − 2 for `.N` − headroom) **and** check the snprintf returns; the length reject alone misses the `/sd` case because the prefix is added inside `resolveOverflowPath`, after validation. Same reject for the two `resolved[128]` buffers at :213 and :246. **Effort: minutes.**

### 2.10 Row writes are unchecked; a full filesystem drops or truncates rows while status says ACTIVE

[:909-916](components/hardwareone/System_SensorLogging.cpp:909): both `f.write()` returns discarded, `f.close()` unchecked, then `gSensorLogLastWrite`, `log_writes` and `gApproxSizeBytes` all credited unconditionally. The merge path in the same file *does* check ([:2046](components/hardwareone/System_SensorLogging.cpp:2046)).

**The prescribed fix does not work and would ship false safety.** `close()` is `void` ([FS.h:70](components/arduino/libraries/FS/src/FS.h:70)) and `fclose`'s result is discarded in `vfs_api.cpp`; and the file is fully buffered at 4096 bytes ([vfs_api.cpp:250](components/arduino/libraries/FS/src/vfs_api.cpp:250)), so a 30-260-byte row's `fwrite` never reaches the filesystem — the error surfaces inside that discarded `fclose`. The detection that actually works: remember `onDisk + len + 1` and compare against `f.size()` at the **next** tick's open, where `_written` is false so the stat is honest ([vfs_api.cpp:380](components/arduino/libraries/FS/src/vfs_api.cpp:380)). Then increment a real `log_write_fail`, print it, and post a rate-limited SYSEVT. **Effort: under an hour.**

### 2.11 Log overflow gates on mount, not writability, and never reports SD failures

[System_VFS.cpp:628](components/hardwareone/System_VFS.cpp:628) `if (!isSDAvailable())` — mount only — while the header at [System_VFS.h:68](components/hardwareone/System_VFS.h:68) names "log overflow" as a *real write* case. `noteSDWriteFailure` has exactly one caller repo-wide ([System_Camera_Video.cpp:392](components/hardwareone/System_Camera_Video.cpp:392)), so a capture failure never invalidates `gSdWritable` and nothing re-probes. Card mounts but cannot be written (write-protect tab, dirty FAT, full, yanked since mount) → every resolve returns `/sd/...`, every open fails, `log_open_fail` climbs in a counter only printed under `DEBUG_LOGGER`, and **capture produces zero rows for the rest of the boot** while status says ACTIVE. This is the one item whose original `data-loss` label was correct as called.

**Fix at [:1183](components/hardwareone/System_SensorLogging.cpp:1183) only** (once per start, cheap). Do **not** put `isSDWritable()` at [System_VFS.cpp:628](components/hardwareone/System_VFS.cpp:628) as written: that is a per-row call, and `isSDWritable()` re-runs a full SPI open/write/flush/close/read/remove probe on every call when `gSdMounted && !gSdWritable` — on the exact failure this is about, it would run a failing SD probe per logged row inside the append lock. Consult the cached flag there and rate-limit the re-probe. And gate any `noteSDWriteFailure` on the `onSd` bool from :891, or a LittleFS open failure marks a healthy card unwritable. **Effort: under an hour.**

### 2.12 Per-day append plus rotation silently discards the earlier part of a high-cadence day

Defaults: `gSensorLogMaxSize = 250 * 1024` (256,000 B) at [:75](components/hardwareone/System_SensorLogging.cpp:75), `gSensorLogMaxRotations = 3` at [:77](components/hardwareone/System_SensorLogging.cpp:77) → family budget 1,024,000 B. I measured the all-sensor CSV row against the builder rather than estimating: 54 fields, ≈260 B. So 256,000/260 ≈ **985 rows → first rotation ~82 minutes in**, oldest generation first evicted at **~5.5 hours**. From then on a 24-hour day retains only the most recent ~1.02 MB; **~4.5 MB/day is discarded** with no event, no notification and no marker — the surviving day file simply begins mid-afternoon, indistinguishable from a device that was powered off. The only trace is `log_trunc++` and two debug-gated printfs.

Duty-cycle dependent, not a default: at Health Track defaults a day file never reaches the cap (see §7 storage math), so this is invisible until someone runs `sensorlog sensors all` with CSV.

**Fix:** one `logSystemEvent` per eviction next to [:955](components/hardwareone/System_SensorLogging.cpp:955), matching the rollover's own breadcrumb at [:882](components/hardwareone/System_SensorLogging.cpp:882). Ship that alone. Forward-numbered `partNN` rotation is rejected — see §7. **Effort: minutes for the event.**

### 2.13 The SD-overflow decoy chain: promoting a header-only stub prunes the anchor the real capture needs

Session start creates the file at the **unresolved** path — [:1148-1149](components/hardwareone/System_SensorLogging.cpp:1148) `existsGuarded(filepath)` / `openGuarded(filepath, "w", ..., true)` then `writeHeaderChecked` at :1154 — so a LittleFS `boot-NNNNNN/health-bootN-<ms>.csv` containing only the header always exists. Every row goes to the **resolved** tier ([:891-894](components/hardwareone/System_SensorLogging.cpp:891); `create=true` auto-creates `/sd` parents, [vfs_api.cpp:46-76](components/arduino/libraries/FS/src/vfs_api.cpp:46)). The sweep only ever scans LittleFS ([System_TimeAnchors.cpp:326](components/hardwareone/System_TimeAnchors.cpp:326), no `resolveOverflowPath` anywhere in the file).

After the session stops, the sweep promotes the header-only stub into the day folder, the boot folder is genuinely empty, `rmdirGuarded` succeeds, and [:302](components/hardwareone/System_TimeAnchors.cpp:302) `registryPrune(a.boot)` **deletes the anchor line**. The real `/sd/...boot-NNNNNN/...` capture keeps its boot name forever with no anchor left, and the day folder gains a plausible file with a header and zero data rows. Debug-only logging throughout.

**Fix:** the two obvious fixes must land together or whichever tier clears first still prunes — gate the prune on both tiers being clear, **and** resolve the stub creation at :1148 so exactly one tier ever holds the file. Note that WP6's session-scoped tier makes the second half redundant. **Effort: under an hour, sequenced after WP6.**

### 2.14 The TEXT row buffer is 512 B while CSV is 1024 B — a full-mask TEXT row truncates mid-token, unmarked

[:330](components/hardwareone/System_SensorLogging.cpp:330) `ps_alloc(512, ...)` vs [:456](components/hardwareone/System_SensorLogging.cpp:456) `ps_alloc(1024, ...)`. `R1_HEALTH_CLOCK_AND_ACTIVITY_RESOLUTIONS.md:114` already did this arithmetic against the builder and puts the **eight non-R1 segments alone at 629 B** at full mask (prefix 28 + thermal 62 + tof 147 + imu 127 + gamepad 52 + apds 57 + gps 93 + presence 63) — so **R1, the last segment, is already truncated today** at full mask. The truncation is silent: `snprintf` clamps, `written` still returns the would-be length so `remaining` goes ≤ 0, later blocks are skipped, and at [:445-448](components/hardwareone/System_SensorLogging.cpp:445) the row no longer ends in `" | "` so `hasSensorData` is false while `else if (remaining > 0)` is *also* false. Result: a row ending mid-number (`bat=8` where the value was 84) with nothing on disk indicating loss. Fix is one constant, already specified as `kTextRowCap = 1024` in WP4. **Effort: minutes, inside WP4.**

### 2.15 The boundary-newline write is the one unchecked write, defeating the guarantee it exists to provide

[:2057](components/hardwareone/System_SensorLogging.cpp:2057) `if (lastByte != (uint8_t)'\n') { out.write((uint8_t)'\n'); totalBytes++; }` — return discarded, `totalBytes` incremented regardless, while every chunk write two lines up **is** checked. Its entire purpose is stated in the twin's header comment ([System_Maps.cpp:3258](components/hardwareone/System_Maps.cpp:3258)): a torn last line must not fuse into the next file's first line. On an exactly-full filesystem the 512-byte chunks succeed and this 1-byte write fails silently, so for a CSV stitch the torn last row fuses with the next file's **header**: `…,72,55,98timestamp_ms,r1_connected,…`. `totalBytes` over-reports by one, so the success message conceals it. Same defect at [System_Maps.cpp:3340](components/hardwareone/System_Maps.cpp:3340). **Effort: minutes.**

## 3. Analysis blockers

### 3.1 The entire per-day design is unreachable in the shipped default, and every health file named `.csv` contains pipe-delimited TEXT

`sensorLogFormat` defaults to TEXT ([System_Settings.h:311](components/hardwareone/System_Settings.h:311), registry row at [:2122](components/hardwareone/System_SensorLogging.cpp:2122)). Health coercion is TRACK-only in both entry points — [:1862-1865](components/hardwareone/System_SensorLogging.cpp:1862) and [:2158](components/hardwareone/System_SensorLogging.cpp:2158). The extension is unconditional: [:1440](components/hardwareone/System_SensorLogging.cpp:1440) `#define CAPTURE_HEALTHLOG_DEFAULT CAPTURE_DIR_SENSORS "/health.csv"`. Every CSV-only feature is therefore dead on the default health path: day naming ([:1795](components/hardwareone/System_SensorLogging.cpp:1795)), the quiet roll ([:866](components/hardwareone/System_SensorLogging.cpp:866)), the header-compat probe ([:236](components/hardwareone/System_SensorLogging.cpp:236)).

Empirically confirmed against your own corpus: all 14 files in `docs/HealthCapture/` are pipe TEXT behind `.csv` names, and `grep -h "r1:" *.csv | awk '{print NF}' | sort -u` returns `4` for all 50 r1 rows — zero comma-delimited rows in the set. `pandas.read_csv` loads all 204 rows as one unsplittable column.

**Fix:** *not* flipping the `sensorLogFormat` default to 1 — `gSensorLogFormat` is global, so that silently changes every non-health capture and still leaves the `stop → format text → start` hole. The correct fix is already written in `R1_HEALTH_CLOCK_AND_ACTIVITY_RESOLUTIONS.md:140-152`: pin CSV inside `cmd_sensorlog`'s **start** branch on `gSettings.healthTrackingEnabled && (gSensorLogMask & LOG_R1) && gSensorLogFormat != SENSOR_LOG_CSV`, which covers manual CLI, `sensorLogAutoStart` and `healthTrackRestartWithCurrentMask`. Deriving the extension from the format alone is insufficient — it just renames the lie to `.txt` and leaves the day/roll/variant machinery unreachable.

### 3.2 Rows record the log time, never the measurement time — and the freshness data is dropped on the way in

`G2RingTelemetry` carries per-metric `*RxMs` receive stamps ([G2_Ring.h:174-178](components/hardwareone/G2_Ring.h:174)), whose own comment says the time axis must use them. The snapshot copy at [:749-761](components/hardwareone/System_SensorLogging.cpp:749) takes `connected`, six `*Valid` flags and six values — nothing else — and `SensorCacheSnapshot`'s R1 block ([System_SensorLogging.h:91-104](components/hardwareone/System_SensorLogging.h:91)) has no slot for it.

Measured in your corpus: `hrv=57` in **39 of 50** r1 rows (78%), spanning 23:01:17.703 to 00:27:40.469 across 12 of 14 files; `spo2=98` in 40 of 50. Three distinct hrv values in 95 minutes. The ring reported each once; the logger re-emitted it every forced sample. Variance, trend and time-in-range computed from these files are all wrong, and nothing distinguishes "measured again, same value" from "nothing new since 23:01".

**Fix:** absolute `_ts_ms` pairs frozen at receive — the design at `R1_HEALTH_CLOCK_AND_ACTIVITY_RESOLUTIONS.md:5-13`, which explicitly rejects both relative `_age_s` columns and any `AgeSec`-derived stamp (ring-clock custody re-bases those mid-session; [G2_Ring.h:169-173](components/hardwareone/G2_Ring.h:169) and `docs/G2_HEALTH_GRAPH_TIME_AXIS_PLAN.md:225` both say so). Do not build the `_age_s` variant from `R1_HEALTH_FIXES_PLAN.md`; it is superseded on paper.

### 3.3 One file, two clock bases — proven in the shipped corpus, and the CSV twin is machine-parsed

The quiet rollover is CSV-only ([:866](components/hardwareone/System_SensorLogging.cpp:866)), so a TEXT session keeps appending to its boot-named file after the clock syncs while the row prefix flips per row ([:336-339](components/hardwareone/System_SensorLogging.cpp:336)). `docs/HealthCapture/health-boot19-10065.csv` is exactly that — 75 `[BOOT` rows then 23 `[20` rows, seam verbatim:

```
[BOOT ms=643652]
[2026-07-26 00:21:00.429]
```

**NEW, and worse because it is machine-read:** the same hole exists for CSV on MANUAL paths. [:466-467](components/hardwareone/System_SensorLogging.cpp:466) `Clock::isSynced() ? Clock::epochMillis() : (int64_t)millis()` under a header that says `timestamp_ms` unconditionally ([:136](components/hardwareone/System_SensorLogging.cpp:136)); the comment defending this relies on the roll, which excludes MANUAL, and `sensorLogClassifyActivePath` assigns MANUAL to any flat file directly in `sensors/` ([:196-197](components/hardwareone/System_SensorLogging.cpp:196)). So `sensorlog format csv; sensorlog start /logging_captures/sensors/mine.csv` before sync writes 10-digit then 13-digit values into one column, forever, with no marker. Any grapher plots the pre-sync rows at 1970-01-01.

**Fix:** the provenance banner from `writeHeaderChecked` ([:174-185](components/hardwareone/System_SensorLogging.cpp:174)) — the single chokepoint for both the start-time create ([:1154](components/hardwareone/System_SensorLogging.cpp:1154)) and the mid-session header-on-create ([:901](components/hardwareone/System_SensorLogging.cpp:901)), so one edit covers rotation, the `/sd` mirror and roll targets. It **must** carry `epoch_ms` *and* the `millis()` at that instant, plus a schema token, or it still cannot resolve pre-sync rows. Add a `# clock synced ms=… epoch_ms=…` marker row at the sync edge for dark boots that have no epoch at create time.

### 3.4 Boots that never sync are permanently undatable — and this is the *only* genuinely unrecoverable case

`writeAnchorLine` runs only behind [:384](components/hardwareone/System_TimeAnchors.cpp:384) `if (!Clock::isSynced()) return;`, and `sweepPass` admits a folder only when an anchor exists ([:338-339](components/hardwareone/System_TimeAnchors.cpp:338)). `health-boot15-10609.csv` through `health-boot18-11249.csv` are 100% `[BOOT ms=]` rows — 20 rows including 11 r1 readings — from boots that never learned the wall clock. No file, folder, anchor or command can place them on a calendar; the information does not exist.

**This overturns the pessimistic framing in two areas.** Promotion has *already applied* the anchor: [System_TimeAnchors.cpp:250-252](components/hardwareone/System_TimeAnchors.cpp:250) computes `fileEpoch` and [:266](components/hardwareone/System_TimeAnchors.cpp:266)/[:273](components/hardwareone/System_TimeAnchors.cpp:273) bake it into the filename, so `row_epoch ≈ stamp_epoch + (row_ms − first_row_ms)` and the only dropped field is `fms`, bounded by one logging interval (5 s default, 900 s on a Health Track mine). Pruning the line afterwards costs **provenance and ±one interval, not datability**. What *is* unrecoverable there is labelling: a promoted name is byte-identical in shape to a genuinely-synced one ([:1803](components/hardwareone/System_SensorLogging.cpp:1803) vs [System_TimeAnchors.cpp:266](components/hardwareone/System_TimeAnchors.cpp:266)), so nothing on disk marks which timestamp domain a file's rows live in.

**Fix:** put `fb`/`fms` back into the promoted name — `"%s/%s-%s-boot%lu-%09lu%s"`; both are live locals at :272 and `dstPath[160]` has room (worst case 110 → ~125). That also makes the collision branch at :274-278 genuinely dead (delete it) and keeps the name `parseBootFile`-parseable, which the current promoted name is not.

### 3.5 A failed anchor write is recorded as success, forfeiting a whole boot's dating

[System_TimeAnchors.cpp:132-143](components/hardwareone/System_TimeAnchors.cpp:132) is `void`, bails at [:138](components/hardwareone/System_TimeAnchors.cpp:138) `if (!f) return;` with no WARN, no `logSystemEvent`, no SYSEVT, and never checks `f.print(line)` at [:142](components/hardwareone/System_TimeAnchors.cpp:142). The caller sets `gAnchoredThisBoot = true` at [:393](components/hardwareone/System_TimeAnchors.cpp:393) outside any success test, and nothing ever clears it. One transient open failure — flash at the overflow reserve, an FS-lock-starved moment — and the 5 s tick never retries. This is the one case with *no* epoch anywhere in the name, so it is unrecoverable in the §3.4 sense. Flash-full is the likeliest trigger because `kAnchorsPath` is opened directly at [:136](components/hardwareone/System_TimeAnchors.cpp:136) while log writes have already been rerouted to `/sd`.

**Fix:** return `bool`, check `f.print` too, latch only on success — free retries via the existing `everyMs` gate at [:387](components/hardwareone/System_TimeAnchors.cpp:387). Keep "latch on adopt" and "latch on successful write" as **separate** conditions or `registryFind` runs every 5 s forever on the adopt path. Do **not** route the path through `resolveOverflowPath` (§2.7). **Effort: minutes.**

### 3.6 `registryLoad` accepts any 3-field line and `registryFind` returns the first match

Unchecked append at [:142](components/hardwareone/System_TimeAnchors.cpp:142) meets a validation-free parse at [:72](components/hardwareone/System_TimeAnchors.cpp:72) `if (sscanf(line, "%lu,%lu,%lld", &b, &ms, &ep) == 3)` — no `Clock::isValidEpoch(ep)`, no ms bound, even though `isValidEpoch` is used 180 lines later at :253 — and a first-match return at [:90-92](components/hardwareone/System_TimeAnchors.cpp:90). A short write leaves `17,10291` with no newline (invisible until extended); boot 18's `18,11249,1785103000\n` then completes it into one line parsing as boot 17 / epoch 11249. Boot 18 has no anchor and is unpromotable forever; boot 17 has a 1970 epoch that :253 silently rejects; a later valid `17,...` can never win. One nuance in the firmware's favour: the cache is refreshed after the print, so the *current* boot still promotes — the damage surfaces on the next boot, which is why nobody would connect the two events. **Fix:** validate on load, prefer last match, dirty-flag a full rewrite — sequenced after §2.6. **Effort: under an hour.**

### 3.7 The anchor is latched once per boot and never corrected, so a stale ring-adopted clock mis-dates the whole folder

[:389-394](components/hardwareone/System_TimeAnchors.cpp:389) has no `else`, no drift test, and the record is three fields with no source column. `Clock::isSynced()` is purely `tm_year >= 120` and cannot distinguish NTP from ring adoption; `ringAdoptClockIfDark` satisfies it via `settimeofday` ([G2_Ring.cpp:399-401](components/hardwareone/G2_Ring.cpp:399)) from a ring **measurement** stamp, and the tick order at [HardwareOne.cpp:2398-2399](components/hardwareone/HardwareOne.cpp:2398) means the pass after an adoption anchors off the ring clock. NTP arriving 10 s later fires the corrective push at the ring but never revises the anchor, and the ±40-day sanity window cannot reject a minutes-to-hours error. Near local midnight the whole folder lands in the wrong `YYYY-MM-DD`, one-way. **Fix requires §2.6 first** — re-anchoring "via the existing `registryPersist` path" would truncate on-disk history to the cache every time.

### 3.8 The sweep is tier-blind, and the raw diagnosis of why was wrong

[System_TimeAnchors.cpp:326](components/hardwareone/System_TimeAnchors.cpp:326) opens the literal `CAPTURE_DIR_SENSORS` with no overflow resolution, while the writer resolves per write. But the stated mechanism — "dark-boot captures on SD never promote, and `gSweepDone` latches so it never retries" — is false: the LittleFS stub always exists, so the pass *does* work and completes normally. The real outcome is §2.13's decoy chain, which is strictly worse. Two smaller sub-claims also fail: the overflow latch **is** announced once ([System_VFS.cpp:605-615](components/hardwareone/System_VFS.cpp:605), WARN + `logSystemEvent` + `SYSEVT_FS_LOW_SPACE`) — though `sensorlog status` never reports the tier and `VFS::isLogOverflowActive()` has no caller in the logging TU, so the state is invisible after that line.

### 3.9 `healthlogmerge` is a byte concatenator with three structural defects

[:2043-2055](components/hardwareone/System_SensorLogging.cpp:2043) is a raw 512-byte copy loop in argument order. Consequences, all confirmed: **interior headers** (every CSV input and every rotated sibling carries its own header from :901/:1154, so a 4-generation family embeds 3 `timestamp_ms,...` lines mid-file — and the first field of those rows is a string, so any typed consumer aborts or coerces the column to text); **no ordering** (rotation numbers newest-first — `.N … .2, .1, base` — so the order a directory listing suggests is exactly reversed, and passing a path twice silently duplicates rows); **no format sniff** (a TEXT file and a CSV file, or two different masks, stitch into one file with two schemas under one header, and [:2003-2004](components/hardwareone/System_SensorLogging.cpp:2003) forces `.csv` onto the output regardless). Plus a **short read** silently truncates an input while `filesDone` increments unconditionally, so the success string cannot report a partial.

Corrections to the prescribed fixes: comparing an input's first line against `buildCsvHeader(gSensorLogMask)` is the wrong test — the live mask has nothing to do with the masks the inputs were captured under, so a correct merge of two old captures would be refused; compare input[0]'s first line against each later input's. The TEXT namespace check is necessary but insufficient, because a single TEXT file can contain both namespaces (§3.3). The epoch sort is **not implementable as described**: the CSV leading column is dual-basis, so keys from a boot-shaped file and a dated file are not comparable. And the whole-function `FsLockGuard` at [:2008](components/hardwareone/System_SensorLogging.cpp:2008) is currently what makes the stitch atomic against four independent renamers (the promote sweep, the midnight roll, the rotation ladder, the active append) — scoping it per input needs a documented abort-on-renamed-input failure mode, so the ordering dependency runs opposite to how the raw finding states it.

### 3.10 The web Log Viewer files 82% of a health capture's rows as UNKNOWN

Row census over `docs/HealthCapture` (re-derived): 204 non-empty rows — 95 `^\[BOOT ms=`, 37 `[ts] | `, **72 bare `[ts]` with no pipe**. 95+72 = 167/204 = **81.9%**. All 167 land at [:1307-1316](components/hardwareone/WebPage_Logging.h:1307) as `timestamp: 0, category: 'UNKNOWN'`.

Two consequence claims deflate it: the dropdown never *offers* UNKNOWN (that branch is the one with no `categories.add()`), so the 82% are unfilterable in either direction; and the timestamp is not blank — [:1387](components/hardwareone/WebPage_Logging.h:1387) renders the full raw line in muted colour. It reads as an unstyled grey dump, not corruption. **Fix:** make the pipe optional, add a `[BOOT ms=N]` format, use the leading `r1:`/`imu:`/`gps:` token as the category, and remember `categories.add()` for whatever bucket the bare rows land in. **Effort: under an hour.**

### 3.11 Rotated and dark-boot-promoted captures are unopenable on both hardware surfaces

[:947](components/hardwareone/System_SensorLogging.cpp:947) appends `.1` **after** the extension. [G2_Page_Files.cpp:432](components/hardwareone/G2_Page_Files.cpp:432) tests only the last four bytes (`ext = name + n - 4` → `"sv.1"`), so control falls to [:1060](components/hardwareone/G2_Page_Files.cpp:1060) `showFileChooser(e, FILE_CHOOSER_OTHER)` whose rows are Info/Rename/**Delete** only ([:566](components/hardwareone/G2_Page_Files.cpp:566)) — Delete being one of three offered actions on 250 KB of the user's oldest data. **Seam:** the promoter carries `.N` straight through. `parseBootFile` accepts `".csv.1"` into `ext[12]` and [:273](components/hardwareone/System_TimeAnchors.cpp:273) renames it to `<dayDir>/health-2026-07-26T00-14-50.csv.1` — unopenable on both surfaces **and** with no boot tag left to join to an anchor. Each area saw one leg; none saw the promoter's role.

**Fix:** insert the generation *before* the extension (`health-2026-07-26.1.csv`); the stem/ext split already exists at [:239-242](components/hardwareone/System_SensorLogging.cpp:239). All three snprintf sites, buffers unchanged. Then the viewer-side `.N` strip is unnecessary — don't ship both (§7).

### 3.12 Nothing consumes `.anchors.csv` on behalf of a human, and 75% of TEXT rows are naked timestamps

`grep -rn anchors components/` finds only the writer. And 154 of 204 rows (**75.49%**, per-file counts re-derived) are bare timestamps carrying no state — mask-empty, sensor-absent and ring-disconnected all render identically. ## 7. Work packages, in order

**Storage math, since two packages hang off it.** Active layout is `partitions.csv:19` → `littlefs, data, littlefs, 0x5A5000, 0xA5B000` = **10,858,496 B (10.36 MB)** — not the 2,863,104 B from the 8 MB layout that one investigator quoted. At Health Track defaults (`healthTrackPollIntervalSec` 900, one row per mine burst, 31 B/row measured against `docs/HealthCapture` + one 74 B header): 96 rows/day, ~3.05 KB/day of data, ~8-12 KB of partition/day with LittleFS's 4 KB blocks and a folder pair per day → **880-1,325 days, i.e. 2.4-3.6 years**, on a device you erase before every flash. At high cadence it is a different story: an all-sensor 5 s CSV day self-caps at 1.024 MB, so **~10-11 consecutive such days fill the partition** and nothing prunes them. Retention is therefore not a package; one `logSystemEvent` on eviction is.

## 8. The stitcher verdict

**Retire it.** `healthlogmerge` is a near-verbatim clone of `cmd_gpstrackmerge` that carries a security hole, destroys a real capture on the more natural argument order, embeds headers mid-file, cannot order rows, cannot tell TEXT from CSV, silently truncates on a short read, and holds the global FS mutex across megabytes — and every one of those fixes has to be written twice or hoisted first, for a command that no UI surface calls and whose output nothing on-device ever reads back. The one reconciliation job only the device could do — lifting boot-relative rows to wall clock — it cannot do at any point in its lifetime, and per §3.4 that job is already done by the promotion rename anyway. Ship WP1 and WP2 to make the existing command safe rather than merely defective, then delete the sensor-side clone and keep `gpstrackmerge` (which has a real picker) as the single stitcher; if per-day reconciliation is genuinely wanted later, the provenance banner from WP4 makes it an off-device three-line script instead of an on-device rewrite.
