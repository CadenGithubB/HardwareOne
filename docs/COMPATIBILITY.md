# Compatibility and upgrade promise

What a HardwareOne firmware version expects from the things around it, and what a 1.x upgrade
keeps. Readiness item P0-7; keep this file in step with CHANGELOG `[Unreleased]`.

## Companion and peer versions the firmware is built against

| Peer | Required / supported | Where it is checked | Notes |
|---|---|---|---|
| ESP32-C6 radio companion (P4X-EYE, Waveshare P4) | ESP-Hosted-MCU slave **2.12.13**, exact, with the HardwareOne ESP-NOW bridge | `c6status` reports `Hosted 2.12.13 (qualified)`; the P4 refuses an unqualified companion for radio work | A stock or Waveshare-factory C6 must be flashed with `c6update` from `tools/p4/companion` before Wi-Fi, Bluetooth or ESP-NOW work. Legacy companion compatibility is limited to that explicit update (0b3d0348). |
| Phone app (Android) | phone link **v2** (`APP_JSON_CONTRACT.md` section 11.9), phone pipe **HW1-PIPE-v1** (`PHONE_PIPE_HANDOFF.md`) | `bleinfo json` / `blestatus json` publish the link version; the pipe handshake carries its info string | Older v1 apps see the console-only path. |
| CM5 / Raspberry Pi AI service (XIAO-S3 + Pi builds) | the UART link protocol in `System_UartLink.cpp`, mirrored byte for byte by `cm5/ai-service link/protocol.py` | frame validation on both ends | Ship both sides from the same commit; there is no negotiation. |
| Even G2 glasses | the Even G2 BLE profile as exercised in the dated hardware records (`docs/G2_*.md`) | discovery and page protocol checks in `G2_Glasses.cpp` | Glasses firmware updates by Even can change pages; the records name the glasses firmware they were taken with. |
| Even R1 ring | advertised name `EVEN R1_XXXXXX` (six hex digits) | `classifyRingName` in `G2_Glasses.cpp`, mirrored in `G2_Ring.cpp` | Any other name is ignored by the ring scan. |
| Arduino core | arduino-esp32 **3.3.5** (`11bc7ac1a`) plus the patches in `docs/arduino-local-patches/` | `tools/vendor_arduino.sh --check`, run by every build script | Not a runtime peer, but the build breaks silently without it (see `docs/arduino-local-patches/README.md`). |
| ESP-IDF | **5.5.5** | `tools/p4/prepare_sdk.sh` (P4) and the build scripts | One IDF for every board. |
| Other HardwareOne devices (ESP-NOW mesh) | **ESPNOW V1 (1.0)**: HardwareOne's mesh format within Espressif ESP-NOW v1's 250-byte frames (frame version byte 4) | every received frame's magic and version byte | Mesh devices must run releases with the same format; there is no negotiation. A message type added within the format (the bond agreement frames) is ignored by firmware from before it, and a bond with such a partner behaves as it did. The sensor reading (154, 179), sensor status (151), sensor request (153) and time (35) frames got their 1.0 layouts before the 1.0 release: devices on builds from before that change exchange no readings, sensor status or time with devices after it. A sensor reading is at most 536 bytes. Mesh time reaches only devices paired with the master that name it (`espnowmasterfingerprint`, or `espnowbackupfingerprint` for the backup acting as master); a device that names no master takes no mesh time. It is good to a few seconds. The battery state (152, 24 bytes) and event (132, 128 bytes) frames are part of the 1.0 format; firmware from before them ignores both. A device sends readings switched on by hand only to the master named on it, and battery state and events to that master and the backup master named on it, each when it is paired with it; a device in several meshes therefore reports to one master. A master keeps the readings and battery state of at most 16 paired devices and the newest 24 events per mesh; an event's subject and detail are cut to 32 bytes and its user to 12 on the way. A bond worker sends its battery state, events and sensor status to its bond master only (bond opcodes 180, 182 and 185, the 152/132/151 payloads); a bond master can forward its partner's readings, battery state, events and sensor status to the master named on it when that master is paired in its primary mesh (FORWARD_LINK 155, and a reserved bit and byte of the 154/152/132/151 frames), which the master accepts from any paired device, and that master can ask for the partner's readings through the bond master (SENSOR_REQ 153 with a reserved byte as link byte). The bond request (183) and notice (184) carry whether the sender's user chose its role (a flag bit, and a byte that was reserved), and every request says that its sender yields to a partner's choice (a second flag bit); firmware from before ignores all three and sends none: its role counts as not chosen and it never yields, so with a device whose user chose the same role it is a role conflict, reported at once, as before (`bondrole` on either device ends it), and when neither chose the addresses decide, as before. No frame grew. A master on firmware from before this change would refuse the announcement as an unknown opcode and file nothing forwarded; a bond worker on such firmware still sends 152/132 to a named master; so the bond pair and the master are reflashed together, as for every 1.0 wire change. SESSION_UNKNOWN (opcode 18, 12 bytes plus the 16-byte group tag, 2026-11-18) is a device's answer to a sealed frame for a session it does not have (it restarted); firmware from before it never sends one and ignores it as an unknown opcode, and then recovers a stale session as before, after two of its sends time out. The boot notice (31) is sent group-signed instead of sealed since the same change, except to a device the sender still holds a session with (after `closeespnow`/`openespnow`), which gets it sealed as before; firmware from before it accepts it either way (its row takes both) and only files it, without ending a stale session. A group-signed notice is authenticated, not encrypted: anyone in radio range can read the sender's name, boot counter and clock time in it. 1.0 frame rules (full erase; no device from before them talks to one after): every layout is packed, little-endian and fixed at build time; each message type has a minimum length, frames shorter than it are dropped and counted (`espnowstats` `rxLengthDrops`), a longer frame is read up to the fields the receiver knows, and after 1.0 a frame only grows at its end, except the fixed-header frames, whose payload ends in text, data or entries and which never grow (RELAY_DATA, PEER_LIST, SENSOR_ENVELOPE, BOND_SENSOR_DATA, CMD_RESP, FILE_DATA, FS_LIST_REPLY, TEXT, STREAM, BOOT, CMD, USER_SYNC; a later need takes a new message type); the six handshake frames (KEY_EX_HELLO/REPLY/CONFIRM, SESSION_OPEN/CONFIRM/REKEY) are exact-length and never grow; reserved bytes are sent 0 and ignored. The group-signed tag is 16 bytes (the first 16 of the HMAC-SHA256): a signed frame carries up to 202 bytes, a routed frame 146 bytes of sealed payload (194 bytes of inner frame). Sensor masks are 32 bits (FORWARD_LINK 96 bytes, mask at 16, key at 20, name at 52; bond status 28 bytes; capability summary 84 bytes). Device-name fields in frames are 32 bytes (HEARTBEAT 44, PAIR_BEACON 36, PAIR_REQUEST/ACCEPT/REJECT 40 bytes). A command reply's text runs to the end of the frame with no NUL, after its answer header. Answers (rule F3): every answer frame starts with a 32-bit reqId (the number of the request it answers; 0 for a frame sent unasked, such as `startstream` output) and a status byte, 0 ok, 1-15 shared reasons with one meaning in every answer (1 busy, 2 refused, 3 unsupported, 4 too_large, 5 no_slot, 6 bad_request, 7 not_ready, 8 io_error, 9 not_found, 10 timeout, 11 cancelled; 12-15 not yet given out), 16 and up a reason of that frame alone; a receiver treats any status it does not know as a failure (a TOPO_START or TOPO_PEER that is not ok records nothing). The answers are TOPO_START (8 bytes), TOPO_PEER (47), CMD_RESP (5 before the text), FS_LIST_REPLY, FS_STAT_REPLY, FS_GET_ACK (their status numbers are the shared table's since this change), STREAM (5 before each line) and FILE_CANCEL (5; reqId is the FILE_START's message number). Every frame's header msgId is the sender's own number, answers included: no answer reuses the request's, and STREAM and CMD_RESP pass the duplicate check like any frame. The sensor request (153) carries a 32-bit request number (20 bytes: reqId 0, mode 4, link byte 5, mask 8, interval 12, lease 16); FILE_END's status byte is 0 for a complete file; the capability summary's byte 0 is reserved. Devices from before this change exchange none of these frames with devices after it. Session capabilities (1.0): SESSION_OPEN grows from 126 to 130 bytes and SESSION_CONFIRM from 142 to 146 (a 32-bit capability word before the signature, inside the signed transcripts, now 75 and 91 bytes); firmware from before refuses both by length, and firmware after refuses the old ones, so no session opens between them and the fleet is reflashed together, as the 1.0 full erase requires. SESSION_REKEY is unchanged and keeps the session's word. Header flags 0xF000 are must-understand (dropped when unknown); 0x0002, 0x0004, 0x0010, 0x0020, 0x0400 and 0x0800 are no longer sent, and a receiver of either side ignores them. Forward compatibility after 1.0 (back-capture design W1, W2, W4, W5): a device that only passes a routed frame on refuses only the 1.0 neighbour-only message types (RELAY_DATA, HEARTBEAT, PEER_LIST, TOPO_*, PAIR_* and the bond numbers 170-180 and 182-185) and passes every other inner type, unknown ones included, so a type added after 1.0 crosses a 1.0 relay; the final receiver decides by its own table. A bond master forwards its partner's battery state (152) and events (132) byte for byte at the received length, patching only the link byte and the forwarded bit, and keeps unknown flag bits of readings, so fields a later release appends to those frames reach the master (a path too short for a grown frame, or a frame longer than one sealed frame's 202 bytes, gets its first 24 or 128 bytes, never a cut inside a later field). FORWARD_LINK byte 7 is the bond master's announcement number, stepped on every announcement and echoed in the answer; the bond master takes an answer only to its latest announcement (an older acceptance, refusal or stale answer changes nothing) and an acceptance whose streams and sensors are a subset of what it announced, so a later bond master with a new sensor type works with a 1.0 master. Reserved for back-capture (switched on by capability bits): message types 82-85 (file catch-up, allocated 2026-11-19, below) and 156-158 (BACKLOG_*, still reserved), 86-89 and 159 free; session capability bits 8 `backlog_serve` (not set yet) and 9 `files_serve`; outbox stream numbers 0-127 (sensor type), 0xF0 (battery), 0xF1 (events); time sources 128 ring, 129 mesh, 130 carried. File catch-up (2026-11-19, docs/BACKCAPTURE_FILES.md): CATCHUP_LIST_REQ (82, 16 bytes: reqId 0, fromFileId 4, kindMask 8, link 10, maxEntries 11, maxFrame 12, reserved 13-15), CATCHUP_LIST_RESP (83, a 24-byte header: reqId 0, status 4, link 5, entryCount 6, headerLen 7, nextFileId 8, ledgerGen 12, ledgerId 16, bootTag 20, flags 22, entryFixed 23; then self-sized entries: entryLen 0, kind 1, flags 2, nameLen 3, fileId 4, start 8, end 12, createdBoot 16, delivered 20, the name at entryFixed), CATCHUP_READ_REQ (84, 24 bytes: reqId 0, fileId 4, offset 8, maxBytes 12, link 16, mode 17, maxFrame 18, flags 19 with bit 0 "stored before offset", ledgerId 20) and CATCHUP_READ_RESP (85, a 20-byte header: reqId 0, status 4, flags 5, link 6, headerLen 7, fileId 8, offset 12, end 16; then data). Their minimum lengths are 16, 24, 24 and 20; all four are session-sealed single frames from a paired device, never fragmented, and may be routed. The requests grow only at their end; the answers carry headerLen (and the entries entryLen and entryFixed), so a reader skips fields it does not know and they grow too. Status: the shared table, plus 16 no_link on LIST_RESP and 16 gone, 17 trimmed, 18 past_end on READ_RESP. A build with ENABLE_ESPNOW_SEND sets the session capability bit 9 `files_serve`, a build with ENABLE_ESPNOW_COLLECT sets bit 4 `collect`; a device serves only a master named on it (by key) whose confirmed capabilities include `collect`. Firmware from before this change answers nothing to 82-85 (unknown opcodes); firmware after it built without SEND answers 82/84 with status 3 (unsupported) once per session. |

Part B of the 1.0 format (device name and mesh id), for the ESP-NOW row above: every frame field that
carries a device name is 32 bytes with the NUL always present and the rest 0 (HEARTBEAT 44 bytes,
PAIR_BEACON 36, PAIR_REQUEST/ACCEPT/REJECT 40, BOND_CAP_RESP's name field 32; TOPO_PEER, METADATA and
FORWARD_LINK already had 32); a name breaking the device-name rule (1-31 letters, digits and `-`,
`System_DeviceName.h`) is treated as absent. The header's 16-bit mesh id (bytes 22-23) is
`pick(crypto_kdf_blake2b_derive_from_key(32, 3, "esp-mid1", stretched mesh key))`, the first nonzero
little-endian u16 of the subkey (`System_ESPNow_MeshIdCore.h`, pinned by `test_espnow_mesh_id_kat.py`),
never 0; a receiver drops 0 and every id no enabled mesh of its own has. Devices from before this change
stamp CRC16 of the label and drop, and are dropped by, devices after it at the mesh gate: reflash the
fleet together. The `SYSEVT_SETTING_CHANGED` key for the name is now `deviceName` (was
`espnowDeviceName`), its settings path `system.device.deviceName` (was `espnow.deviceName`), and the
`bluetoothDeviceName` setting is gone (a settings file with the old keys gives its name to the new one
once at load, converted to the rule when needed, and loses the old keys: `System_DeviceNameLegacy.h`);
`bleinfo json` keeps `deviceName`, now the device name.

`versions` on the device lists these, as this image carries them, in one place: the firmware, the
recovery updater and OTA layout, the ESP-NOW format and stack, the BLE console channel, the phone
link and pipe, the CM5 control protocol, the C6 companion's reported and expected versions, the
local STT model, the ESP-NOW identity and peer file versions, the automations file and backup
bundle formats and the ESP-IDF and Arduino core it was built with (`versions json` for tools;
`BUILD_INFO.md` in a build directory has the build-time half).

## Persisted data and what an upgrade keeps

- `settings.json` carries no format version; it records the `firmwareVersion` that last wrote it.
  Unknown keys are kept; a missing key takes its default.
- `automations.json` carries `"version": 2` (`kAutomationsFileVersion`, `versions` key
  `automations_file`). Every read checks it. A file with no `"version"` or with version 1 loads as
  before: the reader has never treated the versions differently (an entry from the old flat or
  `schedule` layout, without a `triggers` array, still has no trigger and does not fire). A higher
  version is from newer
  firmware: its automations are not loaded or run, and the file is left unchanged (nothing is written
  back from it), so that firmware finds it as it left it. The console says so once. `automation`
  commands, the web Automations page (`GET /api/automations`: `success` false with
  `formatVersion` and `supported`) and its exports (`409`) name the version instead of listing it.
- The web migration backup bundle (`HWBACKUP`) carries `"formatVersion": 1` (`kBackupFormatVersion`,
  `versions` key `backup_format`). Import from Backup refuses a higher or non-whole-number
  `formatVersion` before staging anything (`400`, `"error":"Backup format too new"` with
  `formatVersion` and `supported`). A bundle without the field is format 1.
- **Within 1.x**: settings, user accounts, saved Wi-Fi networks and automations are kept across an
  app update (OTA or cable app-only write). A renamed setting or event name gets an alias, or the
  change is listed under "Changed" in CHANGELOG with the migration step.
  - `g2_worn` (event) was renamed `g2_plugin_alive` in 64713c0d; saved automations and notification
    rules that still say `g2_worn` resolve to the new kind (alias in `systemEventKindFromName`).
  - `c6_console` (command) is an alias of `c6console`.
- **1.0.0 is a full-erase install** for boards coming from 0.99.x: `idf.py erase-flash` first, then
  the first-time setup. Settings from 0.99.x are not promised to carry over. On a recovery OTA
  layout (`HW_OTA_LAYOUT=1`) the erase also removes the recovery updater and the recovery
  credential, so it is refused there unless `HW1_ALLOW_FULL_ERASE=1` is set, and the install after
  it is steps 3-4 of `docs/OTA_DEVICE_SETUP.md`: `migration-flash`
  (`encrypted-migration-flash` on `feathers3_fe`), then `setpin` or `otapin`.
- OTA layout ids (`hw1-f3-ota-v1`, `hw1-f3fe-ota-v1`, …) and the OTA manifest format are frozen
  within 1.x; a new layout gets a new id rather than a changed meaning.

## Account recovery

A lost admin password on a single-account device cannot be recovered in place (`factoryreset`
needs a super-admin login). A second admin can reset it with `userresetpassword`; otherwise erase the
LittleFS region over the cable, which also removes settings and captures. An owner login file that
can no longer be read (`/system/users/user_settings/1.json`) is moved aside to `1.json.corrupt-1`,
and the next boot asks on the console or display for a new owner password; other accounts and
settings stay as they are. First-time setup refuses
reserved owner names (`system`, `AuthBypass`, the bond admin) and passwords shorter than 6
characters, so a fresh device cannot be set up into a lockout.

## Not promised

- Anything labelled experimental in the README matrix (currently the Waveshare P4 row and any OTA
  layout without a dated PASS record).
- Captured logs, transcripts and sensor logs on the SD card are data, not part of the upgrade
  contract; keep your own copies.
