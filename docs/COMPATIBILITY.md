# Compatibility and upgrade promise

What a HardwareOne firmware version expects from the things around it, and what a 1.x upgrade
keeps. Readiness item P0-7; keep this file in step with CHANGELOG `[Unreleased]`.

## Companion and peer versions the firmware is built against

| Peer | Required / supported | Where it is checked | Notes |
|---|---|---|---|
| ESP32-C6 radio companion (P4X-EYE, Waveshare P4) | ESP-Hosted-MCU slave **2.12.13**, exact, with the HardwareOne ESP-NOW bridge | `c6status` reports `Hosted 2.12.13 (qualified)`; the P4 refuses an unqualified companion for radio work | A stock or Waveshare-factory C6 must be flashed with `c6update` from `tools/p4/companion` before Wi-Fi, Bluetooth or ESP-NOW work. Legacy companion compatibility is limited to that explicit update (0b3d0348). |
| Phone app (Android) | phone link **v1**, phone pipe **HW1-PIPE-v1** | `bleinfo json` / `blestatus json` publish the link version; the pipe HELLO carries version byte 1 | The Android app speaks the same byte. A HELLO with any other byte is refused. |
| CM5 / Raspberry Pi AI service (XIAO-S3 + Pi builds) | the [HardwareOne_RaspPi_CoProcessor](https://github.com/CadenGithubB/HardwareOne_RaspPi_CoProcessor) service at **d7aff05** or later (no Pi + XIAO bench run with this firmware yet): UART **link protocol 3** (the framed command channel, `System_UartLinkFraming.h`; its `docs/ARCHITECTURE.md` "Framed command channel"), CM5 control protocol `cm5_control v1`, `cm5-presence-v1`, `live-pcm-v1` | the login reply ends ` link=3` and the service refuses any other version ("firmware too old for this daemon"); `uartlink status` shows `link=3` and `versions` the line `UART link protocol  3`; frame CRC checks on both ends | No fallback in either direction: the service has no unframed mode and a pre-framing service does not read framed replies, so update both together. A person at a terminal can still type unframed lines. |
| Even G2 glasses | the Even G2 BLE profile this firmware speaks | discovery and page protocol checks in `G2_Glasses.cpp` | Glasses firmware updates by Even can change pages; the records name the glasses firmware they were taken with. |
| Even R1 ring | advertised name `EVEN R1_XXXXXX` (six hex digits) | `classifyRingName` in `G2_Glasses.cpp`, mirrored in `G2_Ring.cpp` | Any other name is ignored by the ring scan. |
| Arduino core | arduino-esp32 **3.3.5** (`11bc7ac1a`) plus the patches in `tools/arduino-local-patches/` | `tools/vendor_arduino.sh --check`, run by every build script | Not a runtime peer, but the build breaks silently without it (see `tools/arduino-local-patches/README.md`). |
| ESP-IDF | **5.5.5** | `tools/p4/prepare_sdk.sh` (P4) and the build scripts | One IDF for every board. |
| Other HardwareOne devices (ESP-NOW mesh) | **custom ESP-NOW v1**: HardwareOne's own mesh format within Espressif ESP-NOW v1's 250-byte frames (frame version byte 1) | every received frame's magic and version byte | Mesh devices must run releases with the same format; there is no negotiation. A message type added within the format (the bond agreement frames) is ignored by firmware from before it, and a bond with such a partner behaves as it did. The sensor reading (154, 179), sensor status (151), sensor request (153) and time (35) frames got their 1.0 layouts before the 1.0 release: devices on builds from before that change exchange no readings, sensor status or time with devices after it. A sensor reading is at most 536 bytes. Mesh time reaches only devices paired with the master that name it (`espnowmasterfingerprint`, or `espnowbackupfingerprint` for the backup acting as master); a device that names no master takes no mesh time. It is good to a few seconds. The battery state (152, 24 bytes) and event (132, 128 bytes) frames are part of the 1.0 format; firmware from before them ignores both. A device sends readings switched on by hand only to the master named on it, and battery state and events to that master and the backup master named on it, each when it is paired with it; a device in several meshes therefore reports to one master. A master keeps the readings and battery state of at most 16 paired devices and the newest 24 events per mesh; an event's subject and detail are cut to 32 bytes and its user to 12 on the way. A bond worker sends its battery state, events and sensor status to its bond master only (bond opcodes 180, 182 and 185, the 152/132/151 payloads); a bond master can forward its partner's readings, battery state, events and sensor status to the master named on it when that master is paired in its primary mesh (FORWARD_LINK 155, and a reserved bit and byte of the 154/152/132/151 frames), which the master accepts from any paired device, and that master can ask for the partner's readings through the bond master (SENSOR_REQ 153 with a reserved byte as link byte). The bond request (183) and notice (184) carry whether the sender's user chose its role (a flag bit, and a byte that was reserved), and every request says that its sender yields to a partner's choice (a second flag bit); firmware from before ignores all three and sends none: its role counts as not chosen and it never yields, so with a device whose user chose the same role it is a role conflict, reported at once, as before (`bondrole` on either device ends it), and when neither chose the addresses decide, as before. No frame grew. A master on firmware from before this change would refuse the announcement as an unknown opcode and file nothing forwarded; a bond worker on such firmware still sends 152/132 to a named master; so the bond pair and the master are reflashed together, as for every 1.0 wire change. SESSION_UNKNOWN (opcode 18, 12 bytes plus the 16-byte group tag, 2026-11-18) is a device's answer to a sealed frame for a session it does not have (it restarted); firmware from before it never sends one and ignores it as an unknown opcode, and then recovers a stale session as before, after two of its sends time out. The boot notice (31) was removed in ESP-NOW 1.0 step 8 and its number retired: the heartbeat carries the boot counter (below). 1.0 frame rules (full erase; no device from before them talks to one after): every layout is packed, little-endian and fixed at build time; each message type has a minimum length, frames shorter than it are dropped and counted (`espnowstats` `rxLengthDrops`), a longer frame is read up to the fields the receiver knows, and after 1.0 a frame only grows at its end, except the fixed-header frames, whose payload ends in text, data or entries and which never grow (RELAY_DATA, PEER_LIST, SENSOR_ENVELOPE, BOND_SENSOR_DATA, CMD_RESP, FILE_START, FILE_DATA, FS_LIST_RESP, TEXT, STREAM, CMD, USER_SYNC; a later need takes a new message type); the six handshake frames (KEY_EX_HELLO/REPLY/CONFIRM, SESSION_OPEN/CONFIRM/REKEY) are exact-length and never grow; reserved bytes are sent 0 and ignored. The group-signed tag is 16 bytes (the first 16 of the HMAC-SHA256): a signed frame carries up to 202 bytes, a routed frame 146 bytes of sealed payload (194 bytes of inner frame). Sensor masks are 32 bits (FORWARD_LINK 96 bytes, mask at 16, key at 20, name at 52; bond status 28 bytes; capability summary 84 bytes). Device-name fields in frames are 32 bytes (HEARTBEAT 56, PAIR_BEACON 36, PAIR_REQUEST/ACCEPT/REJECT 40 bytes). A command reply's text runs to the end of the frame with no NUL, after its answer header. Answers (rule F3): every answer frame starts with a 32-bit reqId (the number of the request it answers; 0 for a frame sent unasked, such as `startstream` output) and a status byte, 0 ok, 1-15 shared reasons with one meaning in every answer (1 busy, 2 refused, 3 unsupported, 4 too_large, 5 no_slot, 6 bad_request, 7 not_ready, 8 io_error, 9 not_found, 10 timeout, 11 cancelled; 12-15 not yet given out), 16 and up a reason of that frame alone; a receiver treats any status it does not know as a failure (a TOPO_START or TOPO_PEER that is not ok records nothing). The answers are TOPO_START (8 bytes), TOPO_PEER (47), CMD_RESP (5 before the text), FS_LIST_RESP, FS_STAT_RESP, FS_GET_RESP (their status numbers are the shared table's since this change), STREAM (5 before each line), FILE_RESULT (12) and FILE_CANCEL (5; reqId is the transfer number FILE_START carries, since step 7). Every frame's header msgId is the sender's own number, answers included: no answer reuses the request's, and STREAM and CMD_RESP pass the duplicate check like any frame. The sensor request (153) carries a 32-bit request number (20 bytes: reqId 0, mode 4, link byte 5, mask 8, interval 12, lease 16); FILE_END's status byte is 0 for a complete file; the capability summary's byte 0 is reserved. Devices from before this change exchange none of these frames with devices after it. Session capabilities (1.0): SESSION_OPEN grows from 126 to 130 bytes and SESSION_CONFIRM from 142 to 146 (a 32-bit capability word before the signature, inside the signed transcripts, now 75 and 91 bytes); firmware from before refuses both by length, and firmware after refuses the old ones, so no session opens between them and the fleet is reflashed together, as the 1.0 full erase requires. SESSION_REKEY is unchanged and keeps the session's word. Header flags 0xF000 are must-understand (dropped when unknown); 0x0002, 0x0004, 0x0010, 0x0020, 0x0400 and 0x0800 are no longer sent, and a receiver of either side ignores them. Forward compatibility after 1.0 (back-capture design W1, W2, W4, W5): a device that only passes a routed frame on refuses only the 1.0 neighbour-only message types (RELAY_DATA, HEARTBEAT, PEER_LIST, TOPO_*, PAIR_* and the bond numbers 170-180 and 182-185) and passes every other inner type, unknown ones included, so a type added after 1.0 crosses a 1.0 relay; the final receiver decides by its own table. A bond master forwards its partner's battery state (152) and events (132) byte for byte at the received length, patching only the link byte and the forwarded bit, and keeps unknown flag bits of readings, so fields a later release appends to those frames reach the master (a path too short for a grown frame, or a frame longer than one sealed frame's 202 bytes, gets its first 24 or 128 bytes, never a cut inside a later field). FORWARD_LINK byte 7 is the bond master's announcement number, stepped on every announcement and echoed in the answer; the bond master takes an answer only to its latest announcement (an older acceptance, refusal or stale answer changes nothing) and an acceptance whose streams and sensors are a subset of what it announced, so a later bond master with a new sensor type works with a 1.0 master. Reserved for back-capture (switched on by capability bits): message types 82-85 (file catch-up, allocated 2026-11-19, below) and 156-158 (BACKLOG_*, still reserved), 86-89 and 159 free; session capability bits 8 `backlog_serve` (not set yet) and 9 `files_serve`; outbox stream numbers 0-127 (sensor type), 0xF0 (battery), 0xF1 (events); time sources 128 ring, 129 mesh, 130 carried. File catch-up (2026-11-19): CATCHUP_LIST_REQ (82, 16 bytes: reqId 0, fromFileId 4, kindMask 8, link 10, maxEntries 11, maxFrame 12, reserved 13-15), CATCHUP_LIST_RESP (83, a 24-byte header: reqId 0, status 4, link 5, entryCount 6, headerLen 7, nextFileId 8, ledgerGen 12, ledgerId 16, bootTag 20, flags 22, entryFixed 23; then self-sized entries: entryLen 0, kind 1, flags 2, nameLen 3, fileId 4, start 8, end 12, createdBoot 16, delivered 20, the name at entryFixed), CATCHUP_READ_REQ (84, 24 bytes: reqId 0, fileId 4, offset 8, maxBytes 12, link 16, mode 17, maxFrame 18, flags 19 with bit 0 "stored before offset", ledgerId 20) and CATCHUP_READ_RESP (85, a 20-byte header: reqId 0, status 4, flags 5, link 6, headerLen 7, fileId 8, offset 12, end 16; then data). Their minimum lengths are 16, 24, 24 and 20; all four are session-sealed single frames from a paired device, never fragmented, and may be routed. The requests grow only at their end; the answers carry headerLen (and the entries entryLen and entryFixed), so a reader skips fields it does not know and they grow too. Status: the shared table, plus 16 no_link on LIST_RESP and 16 gone, 17 trimmed, 18 past_end on READ_RESP. A build with ENABLE_ESPNOW_SEND sets the session capability bit 9 `files_serve`, a build with ENABLE_ESPNOW_COLLECT sets bit 4 `collect`; a device serves only a master named on it (by key) whose confirmed capabilities include `collect`. Firmware from before this change answers nothing to 82-85 (unknown opcodes); firmware after it built without SEND answers 82/84 with status 3 (unsupported) once per session. Channel follow (2026-11-19): HEARTBEAT byte 3, reserved before (sent 0, ignored), is `chanInfo`: bits 0-3 the sender's radio channel 1-13 (0 = not stated), 0x10 probe (a hunting worker asks its master to answer), 0x20 answer (the master's reply to a probe, sealed when a session is up), 0xC0 sent 0 and ignored. The frame stayed 44 bytes then (56 since step 8, below). Firmware from before sends 0 there and never reads it: a new worker follows such a master as one that states no channel (it confirms the channel from the master's acknowledgement of its probe and the next heartbeat, and among several such channels takes the strongest signal), and an old worker ignores the channel a new master states. ESP-NOW 1.0 clean-out (step 2): SUBSCRIBE_UPDATE (130) is removed and its number retired, like 150; the unused earmarks 2, 16/17, 37/38, 131 and 133-135 are released for later frames; BOND_HEARTBEAT bytes 12-15 (seqNum, never read) are reserved, sent 0 and ignored; a device's msgId starts at a random nonzero value each time ESP-NOW starts and goes from 0xFFFFFFFF to 1, never 0. ESP-NOW 1.0 handshake crypto (step 4): KEY_EX_HELLO and KEY_EX_REPLY keep 72 bytes but carry a 16-byte nonce and a 16-byte tag (HMAC-SHA256 under the mesh bootstrap key with the labels `hw1-espnow-1-kxhello` / `-kxreply`; the REPLY's tag also covers the initiator's MAC, key and HELLO nonce); KEY_EX_CONFIRM grows from 18 to 34 bytes (`pubFingerprint` is `keyId`, plus a 16-byte tag, label `hw1-espnow-1-kxconf`, over the frame, both MACs, both nonces and both keys; status 3 = not accepted); SESSION_OPEN grows from 130 to 154 bytes (`openEpochMs` u64 at 66, signed, then the signature at 74 and a 16-byte mesh tag at 138), SESSION_CONFIRM from 146 to 162 (mesh tag at 146; exactly the relay budget) and SESSION_REKEY from 130 to 146 (mesh tag at 130). The signed transcripts are 92, 100 and 84 bytes with the labels `hw1-espnow-1-sopen` / `-sconf` / `-rekey`; the mesh tag is HMAC-SHA256(bootstrap key of the identity's mesh slot, "<label>-mk" || mesh id || transcript || signature), first 16 bytes; the session keys are derived from HMAC-SHA256(bootstrap key, `hw1-espnow-1-session` || X25519 shared secret). The group tag covers `hw1-espnow-1-group` first. The mesh salt prefix is `hw1-espnow-1-mesh-salt:`, so every mesh id and key changes. `System_ESPNow_HandshakeCore.h` holds every layout, pinned by `test_espnow_handshake_kat.py` against vectors computed independently (`espnow_handshake_kat_vectors.py`). Devices before this change and after it share no mesh id, key exchange or session: reflash together. ESP-NOW 1.0 ACK frame (step 5a): the ACK (opcode 1) is an 8-byte payload (ackFor u32 at 0: the msgId of the frame answered; fragIndex 4; fragCount 5; status 6: 0 accepted, else a shared status 1-15; flags 7: bit 0 duplicate, the rest reserved), exact length, never grows; its header msgId is the sender's own and its fragIndex/fragCount are 0/1. It is never plaintext: a sealed frame is answered with a sealed ACK in the same session (56 bytes; sealed also while that session is REKEYING), a group-tagged frame with a tagged ACK (56); it never asks for an ACK and is never flooded. A receiver drops every frame that is neither sealed nor group-tagged except the six handshake frames (10-15), which carry no ACK_REQ and are never ACKed; TOPO_REQ/START/PEER were group-tagged then and are sealed since step 9 (below). A sender matches an ACK on (device, ackFor, fragIndex) and the class it expects. Devices before this change and after it do not acknowledge each other's frames (an old ACK is plaintext and empty): reflash together. ESP-NOW 1.0 ACK after accept (step 5b): the ACK keeps its layout; it now means accepted. A receiver answers ACK_REQ only after the frame passed every gate and its handler took it (a fragment: once reassembly stored it), with status 0; a frame it cannot take gets the ACK with a shared status (1 busy, 2 refused, 3 unsupported opcode, 4 too large or a fragCount over its reassembly budget, 5 no slot, 6 bad request, including a length under the row's minimum); a policy refusal (row gates, bond partner) is status 2 to a sealed frame's session peer and no answer to any other sender. A copy of an accepted frame or stored fragment (same class, sender, msgId and fragIndex, within 5 s) is answered with status 0 and flags bit 0 (duplicate) and not processed; a refused frame is not remembered, so its retry is processed again. A message whose reassembly ended refused (handler, length rule, or a fragment that broke it) is remembered for 5 s: a later fragment of it gets the same status and opens no reassembly entry. A sealed frame from a session peer that is not paired here is answered status 2. The encrypted multi-frame sender sends the whole message once more under a new msgId after a busy or no-slot answer (300-800 ms later) or a rekey it started mid-send, except TEXT (stored per fragment); an answered send (any status) counts the session alive, only an unanswered one toward the two-strike re-open. Devices before this change and after it disagree on what an ACK means and on the retry: reflash together. ESP-NOW 1.0 capacity and remote command results (step 6): no frame changes. A receiver reassembles 4 long messages at once (was 2; a fragment that finds all in use is answered 5 no_slot); a CMD that finds the one waiting slot taken is answered by its ACK alone with status 1 busy (no CMD_RESP(busy) is sent any more); received CMD_RESP messages wait in a 16-entry queue over a 24 KB ring, and a full queue answers the CMD_RESP status 1 busy (a device without the PSRAM for the queue answers 7 not_ready). A CMD_RESP is sent waiting for its ACK (one frame or many) and, after busy or no slot, once more under a new msgId 300-800 ms later; a CMD (also routed in fragments) answered busy is not sent again. The requester ends each CMD and USER_SYNC in one result: no ACK in 10 s is "no answer", no CMD_RESP within 30 s of the ACK (each STREAM line for its reqId adds 30 s) is "no result", and a CMD_RESP after that is a late result. A device from before this change answers a busy CMD with a CMD_RESP(busy) that the requester shows as a late or logged result, and does not resend a busy result: reflash together. ESP-NOW 1.0 files (step 7, the Q26 transfer layout, DESIGN 3.6): every file frame has its own msgId and names its transfer by a random nonzero 32-bit transferId in its payload. FILE_START (110) is a 12-byte fixed header (transferId 0, totalSize 4, chunkSize u16 8: at most 194 direct and 138 routed, kind 10: 0 file, 1 bond answer, 2-255 answered unsupported, nameLen 11: 1-96) followed by the name's bytes (minimum 13); it asks for an ACK, and a refusal is that ACK's status (4 too_large for a name over 96 bytes, or over the receiver's storage name limit, 63 on LittleFS, or a file over 4 MB; 5 no_slot; 8 io_error for no room; 6 bad_request; 3 unsupported; 2 refused for a bond answer from anyone but the online bond partner); no FILE_CANCEL is sent for a refused start. FILE_DATA (111) is transferId 0, chunkIndex u32 4, then up to 194 bytes (minimum 9), without ACK_REQ, and is not kept in the accept memory. FILE_END (112) is 16 bytes (transferId 0, chunkCount 4, crc32 8, status 12: 0 complete, else the sender stopped, reserved 13-15) with ACK_REQ. FILE_RESULT (113, was the reserved FILE_ACK) is the receiver's end-to-end verdict, an answer of 12 bytes (reqId = transferId 0, status 4: 0 stored, else a shared status or 16 incomplete / 17 crc_mismatch, reserved 5-7, bytesStored 8), sealed with ACK_REQ, sent once the file is renamed into place (a bond answer: processed) or known not to be stored; the receiver remembers its last 8 verdicts for 60 s and answers a FILE_END copy for a finished transfer with the same FILE_RESULT. FILE_CANCEL (115) keeps its 5 bytes and goes either way: from the receiver (a gap, a chunk for a transfer it does not have, its 30 s timeout) the sender stops; from the sender (no answer to its FILE_START) the receiver frees the slot. The sender waits about 600 ms for FILE_START's ACK, and up to 10 s after FILE_END for FILE_RESULT (sending FILE_END once more after 4 s); with no FILE_RESULT the send is reported unknown. Devices before this change and after it exchange no files: reflash together. ESP-NOW 1.0 two-way liveness (step 8, RC3, DESIGN 4): HEARTBEAT (30) grows from 44 to 56 bytes (bootCounter u32 at 44: the sender's persisted boot counter; echoMsgId u32 at 48: the msgId of the last heartbeat the sender heard from the recipient within 30 s, 0 none; linkRssi i8 at 52: the sender's RSSI of that heartbeat, 0 none; reserved 53-55), minimum 56. Heartbeats are per-peer unicasts with their own msgId, sealed when a session with the recipient is ACTIVE and group-tagged otherwise; the periodic and master-to-backup heartbeats carry no ACK_REQ (the channel-follow probe, the pairing seed and the app ping still do). Toward a peer not heard for 30 s a device sends at least every 10 s (was up to 30 s). A sealed heartbeat whose echoMsgId names one of the recipient's last two heartbeats to the sender within 30 s, and a sealed ACK received direct for a frame the recipient sent direct, prove the link both ways; tagged and relayed frames never do. A group-tagged heartbeat's boot counter that is newer than the one known (wrap-safe) closes the recipient's stale session with the sender (at most once per 10 s); a sealed one only records it. The BOOT frame (31) is removed and the number retired; the broadcast ACK tracking is gone (no broadcast asks for an ACK). Devices before this change and after it refuse each other's heartbeats by length: reflash together. ESP-NOW 1.0 remaining wire and names (step 9, DESIGN 5.3, 5.4): CMD (50) is a credential block (kind u8 at 0: 0 account, 1 bond token; userLen 1; passwordLen 2; reserved 3; then the user name and the password, no NUL, a ':' an ordinary byte; kind 1 has no user name and the 16 raw token bytes) followed by the command text to the end of the payload (minimum 5); USER_SYNC (56) is two such blocks (the receiving device's admin, then the account, both kind 0) and a flags byte (bit 0: an admin on the sender), minimum 9, and its row needs a paired sender as well as a session; a CMD or USER_SYNC whose blocks break these rules is answered status 6 (bad_request) on its ACK. TOPO_REQ/START/PEER (32-34) are sealed in a session with a paired peer (rows PAIRED + SESSION_ENC), sent to paired peers only, and TOPO_PEER's `encrypted` byte is 1 when that peer's session is live (it was always 0); only the six handshake frames remain without a row gate. BOND_REQUEST (183) is reqId u32 at 0, role 4, flags 5, reserved 6-7; BOND_NOTICE (184) is an answer: reqId u32 at 0, status 4 (0 accepted, 16 not_bonded, 17 bonded_elsewhere, 18 ended, 19 role_conflict; an unknown status is ignored), role 5, flags 6, reserved 7; both stay 8 bytes. FORWARD_LINK (155) byte 5 (result) is 0 for ok (an announcement accepted or a withdrawal done), 5 no_slot (full), 6 bad_request (bad partner), 16 not_receiver, 17 key_mismatch, 18 stale, 19 name_taken. Names: FS_LIST_RESP, FS_STAT_RESP, FS_GET_RESP (were _REPLY and FS_GET_ACK), BOND_MANIFEST_REQ, BOND_SETTINGS_REQ, BOND_SCHEMA_REQ, and the header's mesh id field `meshId` (was `meshFingerprint`); no number or layout changed with them. No receive path reads a payload through a pointer cast any more (the FS list entries are copied). Stored files (no conversion: boards are erased at 1.0): devices.json drops `encrypted` and `key`; a peer's identity.json has `"schema":1`, `pairedEpochMs` and `lastSeenEpochMs` (was `"version":2`, `bondedAtSec`, `lastSeenSec`); this device's identity.json has `createdEpochMs` (was `createdAtSec`). The wire byte is 1. Devices before this change and after it run no remote command, user sync, topology or bond agreement with each other: reflash together. |

Part B of the 1.0 format (device name and mesh id), for the ESP-NOW row above: every frame field that
carries a device name is 32 bytes with the NUL always present and the rest 0 (HEARTBEAT 44 bytes,
PAIR_BEACON 36, PAIR_REQUEST/ACCEPT/REJECT 40, BOND_CAP_RESP's name field 32; TOPO_PEER, METADATA and
FORWARD_LINK already had 32); a name breaking the device-name rule (1-31 letters, digits and `-`,
`System_DeviceName.h`) is treated as absent. The header's 16-bit mesh id (bytes 22-23) is
`pick(crypto_kdf_blake2b_derive_from_key(32, 3, "esp-mid1", stretched mesh key))` (the stretch is
PBKDF2-HMAC-SHA256 over `SHA256("hw1-espnow-1-mesh-salt:" || label)`, 100000 rounds, `"kdf":1` in the
settings file), the first nonzero
little-endian u16 of the subkey (`System_ESPNow_MeshIdCore.h`, pinned by `test_espnow_mesh_id_kat.py`),
never 0; a receiver drops 0 and every id no enabled mesh of its own has. Devices from before this change
stamp CRC16 of the label and drop, and are dropped by, devices after it at the mesh gate: reflash the
fleet together. The `SYSEVT_SETTING_CHANGED` key for the name is now `deviceName` (was
`espnowDeviceName`), its settings path `system.device.deviceName` (was `espnow.deviceName`), and the
`bluetoothDeviceName` setting is gone (1.0 reads only the new key; boards start erased);
`bleinfo json` keeps `deviceName`, now the device name. Without a stored name the device uses
`HardwareOne-` and the last two bytes of its address (`HardwareOne-B2C3`; builds before 2026-11-20 used
three), and replies with the name gain `deviceNameSet` (false for that fallback); a name stored earlier,
the old three-byte fallback included, is kept as it is. No frame changes: frame name fields carry the
stored name only.

`versions` on the device lists these, as this image carries them, in one place: the firmware, the
recovery updater and OTA layout, the ESP-NOW format and stack, the BLE console channel, the phone
link and pipe, the UART link protocol and the CM5 control protocol, the C6 companion's reported and expected versions, the
local STT model, the ESP-NOW identity and peer file versions, the automations file and backup
bundle formats and the ESP-IDF and Arduino core it was built with (`versions json` for tools;
`BUILD_INFO.md` in a build directory has the build-time half).

## Persisted data and what an upgrade keeps

- `settings.json` carries no format version; it records the `firmwareVersion` that last wrote it.
  Unknown keys are kept; a missing key takes its default.
- `automations.json` carries `"version": 2` (`kAutomationsFileVersion`, `versions` key
  `automations_file`). Every read checks it. A file with no `"version"` or with version 1 loads as
  before: the reader has never treated the versions differently (an entry from the old flat or
  `schedule` layout, without a `triggers` array, still has no trigger and does not fire). A higher
  version is from newer
  firmware: its automations are not loaded or run, and the file is left unchanged (nothing is written
  back from it), so that firmware finds it as it left it. The console says so once. `automation`
  commands, the web Automations page (`GET /api/automations`: `success` false with
  `formatVersion` and `supported`) and its exports (`409`) name the version instead of listing it.
- Sealed files (captures and health days that capture encryption seals on flash, and every log
  file on the SD card) start with the mark line `#HW1ENC v1 k1 id=<16 hex>`: `v1` is the row
  format (`ENC1:` and base64 of nonce, ciphertext and tag), `k1` the key slot, and `id` names the
  device key that sealed the file (it is not the key). A reader takes any first line that starts
  with `#HW1ENC` as the mark. The rows open only with that device's key (NVS `hw1cap`/`k1`); an
  NVS or flash erase removes it, and nothing can read the files afterwards. A row is also bound
  to the kind of file it was sealed for (the seal's additional data is `HW1ENC1|` and `syslog`,
  `bootdebug`, `capture`, `stt|u<id>`, or `path|<path>` for any other place, the same for a file
  and its `/sd` twin): read at a path of another kind it does not open. There is no reader for
  rows sealed with the earlier constant additional data (`HW1ENC1`): sealed captures and health
  days written by builds before this change show `[undecryptable row]` and do not load; 1.0
  starts from erased storage. A line of a sealed file that is neither the mark, a header line
  directly after it (a capture's column names or `#` lines, at most eight) nor a row reads as
  `[unsealed line]`. A log file on the card that does not carry this device's mark is moved aside
  to `<name>.foreign-<n>` (in the log folders only); it is never converted.
- The web migration backup bundle (`HWBACKUP`) carries `"formatVersion": 1` (`kBackupFormatVersion`,
  `versions` key `backup_format`). Import from Backup refuses a higher or non-whole-number
  `formatVersion` before staging anything (`400`, `"error":"Backup format too new"` with
  `formatVersion` and `supported`). A bundle without the field is format 1.
- **Within 1.x**: settings, user accounts, saved Wi-Fi networks and automations are kept across an
  app update (OTA or cable app-only write). A renamed setting or event name gets an alias, or the
  change is listed under "Changed" in CHANGELOG with the migration step.
  - Every command alias was removed before 1.0 (one name per command); `c6_console` is now only
    `c6console`. CHANGELOG "Changed" lists each removed name and the name to use.
  - New settings keys (2026-11-20), each with a default equal to the behaviour before it, so a
    device that has not saved them behaves as before: `apps.espsr.srAfeGain` (1.0),
    `apps.espsr.srAgcMode` (2), `apps.espsr.srVadMode` (3), `network.bluetooth.g2.streamWidth` (96),
    `network.bluetooth.g2.streamHeight` (96), the companion's read-only fault counts
    `network.companion.c6OutageCount`, `c6RebootCount` and `c6LastFaultEpochSec` (0), and
    `stt.sttphraselevel` (0: the
    phrase leveler, on before and never saved, is off after the update). A saved
    `c6ConsoleMirror: true` (any save since 2026-11-19 stored the old default) is kept and keeps
    the mirror on until `c6console off`. Older firmware ignores the new keys.
  - Roles come only from `users.json` (2026-11-20): an account stored without a role is a `user`,
    the first account included, and no account is super admin without `"role": "superadmin"`. A
    device first set up before v0.99.0 and never set up again has an `admin` owner and no super
    admin after the update; check `/system/users/users.json` before updating and add a
    `superadmin` account on the old firmware if there is none.
  - System logs (2026-11-20) are kept as `<name>.log.1` and `<name>.log` and together use at most a
    quarter of the LittleFS partition; a log above its new size loses its older part at its first
    write after the update.
  - Unnamed device (2026-11-20): a board with no stored device name advertises over Bluetooth and
    gives its Wi-Fi router the hostname `HardwareOne-` plus the last two address bytes
    (`HardwareOne-B2C3`; it was three, `HardwareOne-A1B2C3`), so after the update a phone that
    looked for the old name, a DHCP reservation or a router rule by hostname needs the new name;
    the master's pairing list and its Home Assistant bridge show an unnamed sender as `peer-B2C3`.
    Set a name with `devicename <name>` to keep one across updates. A stored name, the old
    three-byte fallback stored by a setup wizard included, is kept as it is.
  - MQTT / Home Assistant (2026-11-20): unique ids, topics and the device id are kept. In Home
    Assistant, GPS Speed changes unit to knots and IMU Gyro to rad/s, RTC DateTime becomes a UTC timestamp, Presence Object Temp and a
    mesh peer's Uptime and thermal entities are removed, and the gamepad entities are removed on
    encoder and touch builds. Automations or dashboards that read the state document by key need
    the new keys (`input` for `gamepad`, `gps.sats`, `rtc.temp`, `apds.r/g/b/c`, the presence
    builder's keys; CHANGELOG "Changed"). The device's name in Home Assistant, when no friendly name
    is set, becomes its fallback name (`HardwareOne-B2C3`); Home Assistant keeps entity ids it
    already made.
- **1.0.0 is a full-erase install** for boards coming from 0.99.x: `idf.py erase-flash` first, then
  the first-time setup. Settings from 0.99.x are not promised to carry over. On a recovery OTA
  layout (`HW_OTA_LAYOUT=1`) the erase also removes the recovery updater and the recovery
  credential, so it is refused there unless `HW1_ALLOW_FULL_ERASE=1` is set, and the install after
  it is steps 3-4 of `docs/OTA_DEVICE_SETUP.md`: `migration-flash`
  (`encrypted-migration-flash` on `feathers3_fe`), then `setpin` or `otapin`.
- OTA layout ids (`hw1-f3-ota-v1`, `hw1-f3fe-ota-v1`, …) and the OTA manifest format are frozen
  within 1.x; a new layout gets a new id rather than a changed meaning.

## Account recovery

A lost owner password cannot be recovered in place: `factoryreset` needs a super-admin login, and
`userresetpassword` refuses the owner account, also from another admin. A second super admin can run
`factoryreset` (every account is deleted); otherwise erase the LittleFS region over the cable, which also
removes settings and captures. A second admin can reset any other account's
password with `userresetpassword`. An owner login file that
can no longer be read (`/system/users/user_settings/1.json`) is moved aside to `1.json.corrupt-1`,
and the next boot asks on the console or display for a new owner password; other accounts and
settings stay as they are. First-time setup refuses
reserved owner names (`system`, `AuthBypass`, the bond admin) and passwords shorter than 6
characters, so a fresh device cannot be set up into a lockout.

## Not promised

- Anything labelled experimental in the [support matrix](README_DETAILS.md#support-matrix) (currently the Waveshare P4 row and any OTA
  layout without a dated PASS record).
- Captured logs, transcripts and sensor logs on the SD card are data, not part of the upgrade
  contract; keep your own copies.
