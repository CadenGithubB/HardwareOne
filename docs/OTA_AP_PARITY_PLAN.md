# OTA recovery-AP parity plan (v0.99.81)

Design-only. Produced 2026-08-05 by a 5-agent pass (3 design tracks, adversarial
reliability review, synthesis), each grounded in the real updater source.
User decisions honored: split the PSK from the HTTP token, NO TLS this release;
full parity with the BLE upload path.

## Summary

v0.99.81 replaces the single-PUT /firmware with a resumable, offset-addressed, sector-aligned chunked upload session, makes /status and /cancel answerable throughout, adds stall detection, and splits the WPA2 PSK from the HTTP token — no TLS. The single biggest design decision is to DROP the async writer task (httpd_req_async_handler_begin) that the concurrent-status design was built around. Chunking alone delivers concurrent status: once each request writes at most 64 KiB, the single esp_http_server task (httpd_main.c, one httpd_thread for all sockets) is blocked for ~1-2s instead of minutes, which is the entire reason /status was dead. That removes a confirmed IDF memory leak (httpd_txrx.c:657-663 allocates async_aux->scratch, and the resp_hdrs calloc failure path at :669-673 frees async_aux and async but never scratch — up to 2 KB per attempt, because recovery_network.c:545 raises max_req_hdr_len to 2048 at runtime), removes the "leaked async request permanently stops the server accepting connections" failure mode, and keeps esp_ota_* calls on exactly one task. The only remaining long operation is finish-time verification (esp_image_verify plus a second full-partition SHA-256 pass, hw1_ota_idf.c:118-159), which moves to the control task via the existing control queue — the proven path, since apply_staged already runs that identical verify chain there with feed_control_watchdog() between steps. A critical scheduling discovery: all three "cheap UI blockers" the plan was told to land early are ALREADY FIXED in the working tree but UNCOMMITTED (git diff of updater/main/recovery_network.c shows the quoted onclick, the strcspn path match with a 400 fall-through, and http.max_req_hdr_len = 2048), so step 1 is to hardware-validate and commit that existing work before it is lost, not to rewrite it. Every blocking item from the reliability review is resolved in-plan, and I confirmed each one against the source rather than inheriting it.

### 2. Rewrite the auth throttle as a per-peer leaky bucket before anything multiplies the request count

**Effort:** medium

**Files:** updater/main/recovery_network.c (:26-28 constants, :32-42 context, :67-82 record_auth_failure, :117-141 require_authorization), updater/main/updater_main.c:234-274 (status_json)

This must land before chunking, because one 2.2 MB upload goes from 2 authenticated requests to roughly 35, and the current throttle cannot survive that. Today it is a single global counter in recovery_network_context_t (:39-41): one attacker locks out the operator (:120-126 returns 429 before any credential check); every success zeroes the counter (:135-136) and the served page polls /status every 3000 ms (:207), so any authenticated station launders another station's failures ~20x/minute; and the 60 s sliding window (:70-74) restarts whenever the window elapses, so one guess per 61 s never accumulates.

Replace with a 4-entry table keyed on peer IPv4 from getpeername(httpd_req_to_sockfd(req)) — 4 is generous given wifi.ap.max_connection = 2 (verified at recovery_network.c:524, not :512 as the designs cite). Per entry: addr, last_seen_us, last_success_us, last_leak_us, blocked_until_us, failures, strikes. Under 200 bytes of .bss, no allocation. Constants: FAIL_LIMIT 5, LEAK_PERIOD 600 s (forgive one failure per 10 min — this is what catches the slow guesser the sliding window misses), BLOCK_BASE 30 s doubling per strike to BLOCK_MAX 1800 s, plus a global 20-failures-per-60 s backstop that known-good peers are EXEMPT from so a flooding attacker can never lock out an operator who authenticated in the last 10 minutes.

Two rules that are not optional:
- A MISSING Authorization header must NOT count as a failure. Today :127-128 calls record_auth_failure() for the header-less case, and every browser's first request to every path is header-less by design. Under a strict per-peer counter this alone locks out the operator's own browser. It must land in the same change as the per-peer table, not after.
- On block, do not evaluate credentials; return 429 with Retry-After AND Connection: close, so a blocked peer does not hold one of only 3 sockets.
Eviction: never evict a blocked entry (that is how an attacker escapes their own block) and reserve one slot for the most recent known-good peer (that is how an attacker rotating source IPs locks out the operator). If no slot is available under those rules, deny 429.
NO vTaskDelay, no penalty sleep anywhere in the handler — esp_http_server serves every socket from one task, so any delay stalls /status and /cancel for everyone.
Surface authBlockedPeers and authFailuresTotal in the authenticated /status JSON (status_json, updater_main.c:234-274) so an operator can see they are being attacked.

**Hardware validation:** Two stations required — a laptop and a phone. (1) Lockout regression, the one that matters most: from the laptop browser, load the recovery page 10 times (each generating header-less first requests) and confirm you are never blocked and never see a 429. (2) From the laptop, 6 bad-credential curls in a row; confirm 429 with Retry-After and Connection: close on the 6th, and confirm via `netstat`/serial that the socket is released. (3) While the laptop is blocked, confirm the PHONE can still authenticate and load /status — this is the cross-station lockout the old global counter caused. (4) Laundering: from the phone, hold an authenticated /status poll open; from the laptop send 4 bad credentials then a 5th; confirm the 5th blocks (previously the phone's successes would have zeroed it). (5) Slow guesser: script one bad credential every 61 s for 7 minutes; confirm it blocks at 5 (previously it never would). (6) Escalation: confirm the second block is 60 s and the third 120 s. Capture the /status authBlockedPeers/authFailuresTotal values at each stage.

### 3. Split the PSK from the HTTP token, with an absolute never-refuse-the-AP rule

**Effort:** large

**Files:** updater/main/recovery_network.h (recovery_credentials_t: auth_token -> http_token, add token_is_ephemeral), updater/main/recovery_network.c (:449-455 delete identity gate, :462-463), updater/main/updater_main.c (:339-343, :406-440 load_credentials, :506-538 store_recovery_pin, :1244-1275 start_network, :1352/:1375/:1389/:1465, :1534-1564 reset_journal_slots, :1815-1900 console), updater/boards/feathers3.defaults, components/hardwareone/System_OTA.cpp (:621-645, :647-660, :662-680, :1270-1298)

User-decided; no TLS this release. Be honest in the docs about what it buys: the AP is WIFI_AUTH_WPA2_PSK with pmf_cfg.required = false (recovery_network.c:525-527), which has no forward secrecy, so an attacker who captures the 4-way handshake AND an authenticated HTTP session and then cracks the PSK offline still reads the Basic header. What the split genuinely defends: a captured handshake with no HTTP traffic, PSK reuse, a PSK shared with someone who should not get console authority, and shoulder-surfing the PSK as it is typed into a phone.

Storage in NVS namespace hw1up: `ap_pass` unchanged (12..63 printable, operator-chosen); NEW `http_tok`, device-generated, 26 chars Crockford base32 = 130 bits, stored as the printable string. Retire `auth_token`. Display grouped (K7QD-2M9X-...) and strip hyphens/spaces/case on compare; Crockford folds I/L->1 and O->0, killing transcription errors. Plaintext, not a hash — the PSK must be plaintext anyway for WPA2, so a flash dump already yields association. Document that on the non-_fe board (updater/boards/feathers3.defaults, CONFIG_NVS_ENCRYPTION=n) both recovery secrets are readable from a flash dump.

THE BRICK-CLASS RULE, verified in source and the single most important line in this step: the updater must NEVER refuse to raise the SoftAP for a token reason. Both refusal sites are real — load_credentials requires ap_size == token_size and strcmp(ap_password, auth_token) == 0 (updater_main.c:427-431), and recovery_network_start repeats it (recovery_network.c:449-455) — and store_recovery_pin writes the SAME string to both keys under one commit (:529-535). A device whose NVS was written by today's code and then flashed with a token-splitting updater fails both gates, start_network returns at :1265, and all four boot_reconcile call sites discard the error with (void). Cable-only, silently. Required behavior: PSK valid + token missing/invalid/legacy-equal -> generate, persist, print on serial, START THE AP. Persist fails (NVS full/RO) -> keep the token in RAM, set tokenEphemeral:true in /status, print on serial, STILL START THE AP. PSK missing -> AP stays off (unchanged and deliberate). Delete both equality gates; validate each field independently.

ENTROPY FOOTGUN: esp_random() is only cryptographically strong once the RF subsystem is running, and new_operation_id() (updater_main.c:339-343) already calls it pre-WiFi — do not copy that pattern. But do NOT fix it by generating inside recovery_network_start after esp_wifi_start (:533) either: that puts an NVS writer in the network layer, on the control task, which holds no s_operation_mutex at any of its four start_network call sites (:1352, :1375, :1389, :1465), racing store_recovery_pin's nvs_open(NVS_READWRITE) on the console task (:1849-1853). Instead have the CONTROL TASK generate the token before calling recovery_network_start, bracketed by explicit bootloader_random_enable()/bootloader_random_disable(), persist it there, and pass it in. No NVS writer inside recovery_network.c, and no bounded-mutex-wait on the sole trigger_panic TWDT subscriber.

DROP the /bootstrap-token endpoint the credential-split design proposed. It is self-defeating and I verified why: the window is specified to close on 'the first successful authenticated request', but root_handler (:212) and status_handler (:224) both authenticate and the served page polls /status every 3000 ms (:207), so an operator who merely loads the recovery page closes their own window before reading the token. It is also the first unauthenticated endpoint on this server and sits outside require_authorization, so it has no rate limit at all — a PSK-holding attacker loops it and, because one task serves all sockets, denies the operator /status and /cancel for free. Disclosure is the USB console instead, which already carries the same physical-access trust model as resetjournal/formatfs.

Console additions (serial-only): `showtoken`, `rotatetoken confirm`, `verifypin <candidate>` (constant-time compare against stored ap_pass, prints match/NO MATCH, never echoes). `setpin <psk>` writes ONLY ap_pass and states explicitly whether the token was generated or left unchanged. Changing the PSK must NOT silently rotate the token.

WHITESPACE DIVERGENCE (audit finding 7), and the fix is one check in one place: the app dispatcher trims args before cmdOtaPin sees them (System_Utils.cpp:4823-4824), while the updater console passes line + 7 to store_recovery_pin (updater_main.c:1851) after stripping only CR/LF (:1843) — so the same keystrokes produce DIFFERENT stored PSKs depending on the path, and a phone's WiFi dialog does not trim either. Reject leading/trailing whitespace in store_recovery_pin, which already validates length and charset at :515-524, and name the rule in the error text. Mirror it in storeCredential (System_OTA.cpp:647-660). Do not plumb the raw line through.

App side: credentialConfigured() drops the memcmp equality test (System_OTA.cpp:621-645); storeCredential stops writing auth_token (:651); clearCredential erases http_tok (:662-680). Do NOT add `otatoken show confirm` this release (see deferred).

**Hardware validation:** This step is validated by a brick-test matrix run ENTIRELY from the hw1up> USB console, because every failure mode here is 'HTTP is unreachable'. After each case, confirm from serial that the AP is up and then confirm association from a phone. (1) Legacy NVS, the exact brick case: provision ap_pass == auth_token with the CURRENT firmware first, then flash the split updater WITHOUT erasing NVS; confirm the AP still comes up, serial logs a legacy warning, a fresh token is generated and printed, and the phone can authenticate with the new token. (2) Fresh NVS, no PSK: confirm the AP stays off and serial says so (unchanged, deliberate). (3) `setpin` a valid PSK: confirm the token is generated, printed grouped, the AP starts, and `showtoken` reprints the same value after a reboot. (4) Ephemeral path: fill or write-protect NVS so the token persist fails; confirm the AP STILL comes up, /status reports tokenEphemeral:true, and serial prints the RAM-only token. (5) Entropy: capture 10 generated tokens across 10 cold boots and confirm no repeats and no obvious structure — a predictable token is worse than the shared secret because it looks solved. (6) Whitespace: `setpin ' abc123456789 '` on the console and `otapin ' abc123456789 '` in the app; confirm BOTH now reject with the same named rule. (7) `verifypin` with the correct and an incorrect candidate. (8) Confirm `rotatetoken confirm` changes the token and the old one stops authenticating, while the PSK still associates.

### 4. Replace the single PUT with the resumable, sector-aligned chunked upload session

**Effort:** large

**Files:** updater/main/updater_main.c (:39-43, :98-100, :450-455 clear_upload_authorization, :887-908 receive_exact, :910-1011 accept_manifest -> upload_begin, :1013-1216 accept_firmware -> chunk/finish/abort, :812-815 apply_staged gating, :1104-1105 comment, :1244-1254 callback wiring, :1477-1532 cancel_recovery), updater/main/recovery_network.c (:178-218 page, :278-349, :351-389, :391-412), updater/main/recovery_network.h (:26-47), updater/main/updater_preflight.c/.h (:310-348, :524-551 mismatch out-param), updater/main/Kconfig.projbuild (UPLOAD_CHUNK_BYTES, APPLY_TIMEOUT_SEC restated session-wide)

Write directly into ota_0 and resume against the partition. Do NOT mount LittleFS read-write: mount_littlefs_read_only (updater_main.c:380-404) keeps format_if_mount_failed=false / read_only=true precisely so a damaged FS written by the broken main app is INERT, and accept_firmware never touches the FS today. Staging to littlefs would also risk ENOSPC on a 0x900000 partition shared with user data while 5.8 MB of ota_0 sits free, and double the flash write volume.

RESUME NEEDS NO CRYPTO STATE — this is what makes it cheap, and I verified the whole chain. The streaming mbedtls SHA in accept_firmware (:1113-1170) is redundant: updater_verify_written_candidate (:1183) -> hw1_ota_idf_verify_partition (hw1_ota_idf.c:118-159) does esp_image_verify, then hw1_ota_idf_sha256_partition over image_metadata.image_len reading back through esp_partition_read (:80-116), then hw1_ota_manifest_validate which checks BOTH image_size (hw1_ota_protocol.c:623) AND the 32-byte digest (:626). That hashes what is physically on flash, which is strictly stronger than hashing the socket. Delete the transport SHA; resume state becomes ONE INTEGER. A resume that splices two images cannot install: the partition hash will not match, and finalize_verified_image is the only route to canonicalize_and_select_main.
BUT PRESERVE THE OPERATOR-FACING RESULT CODE: with the wire SHA gone, a digest mismatch surfaces via hw1_ota_manifest_validate returning HW1_OTA_ERR_INCOMPATIBLE (any nonzero mismatch mask, verified hw1_ota_protocol.c:638) -> ESP_ERR_INVALID_VERSION -> HW1_OTA_RESULT_INCOMPATIBLE_IMAGE, telling the operator the wrong thing. updater_verify_written_candidate already computes `mismatches` and swallows it into a string (updater_preflight.c:528-537); give it an out-param and map MISMATCH_IMAGE_SHA256 back to HW1_OTA_RESULT_DIGEST_MISMATCH.

THE ONE LOAD-BEARING RULE: every accepted offset is a multiple of s_ota0->erase_size (read it from the partition, never assume 4096), except the terminal chunk which completes image_size. I verified why in esp_ota_write (esp_ota_ops.c:313-327): it erases the containing sector only when (wrote_size % erase_size) == 0; the else-branch erases from (first_sector+1)*erase_size, SKIPPING it. So an aligned resume re-erases the sector it resumes into and re-writing is safe, while an unaligned one ANDs into programmed cells — silent corruption on plain flash, an undefined double-write of a 16-byte block under flash encryption (ota_0 is always encrypted on _fe). One unconditional check, in exactly one place. Also: esp_ota_write's magic-byte guard fires only when wrote_size == 0 (:329-337), so it is skipped entirely on resume — the finish-time re-read of the 288-byte prefix is therefore MANDATORY, not an enhancement.
Use esp_ota_resume(partition, OTA_WITH_SEQUENTIAL_WRITES, offset, &handle) — verified present in the installed IDF at esp_ota_ops.h:131 / esp_ota_ops.c:212-258. Not esp_ota_write_with_offset, which asserts need_erase == 0 and thus requires the single partition-sized blocking erase the current code deliberately avoids (:1104-1105).

BLOCKING ITEM (review B4), and the design's own proposed fix does not work: esp_ota_resume does NOT call esp_ota_invalidate_inactive_ota_data_slot(), which esp_ota_begin does (verified esp_ota_ops.c:203-207 present in begin, absent in resume) — the current code gets that coverage by accident. The fix is NOT canonicalize_and_select_main: I read it (updater_main.c:575-593) and it returns ESP_ERR_INVALID_STATE unless main_partition_is_return_eligible() is true, which is precisely FALSE once ota_0 is being overwritten, and it ENDS by selecting ota_0 — the opposite of what is wanted. At session begin, before the first byte, call a bare esp_ota_set_boot_partition(esp_ota_get_running_partition()) with an explicit comment, and verify it committed.

BLOCKING ITEM (review B1): making the mutex per-request is what unblocks /apply mid-session. Today apply_staged's 0-timeout take (:812) fails because accept_firmware holds the mutex for the whole upload; with per-request take it SUCCEEDS between chunks. Two reachable damage paths: (a) source==RECOVERY_UPLOAD falls to `failed:` and record_failure runs transition_record(FAIL) on the LIVE record, journaling the active transaction FAILED with ota_0 already partly overwritten; (b) worse — I verified accept_manifest has no branch for an already-APPLYING record (it only calls hw1_ota_begin for FAILED/CANCELED/SUCCEEDED and IDLE, then falls through to begin_or_resume_applying), so a STAGED_FILE APPLYING record can carry an upload session, apply_staged passes its source check and calls write_staged_candidate -> esp_ota_begin at :735 while the session handle is still open: TWO live OTA handles on ota_0. Fix both ends: apply_staged fails closed on session.active under the mutex, AND /apply returns 409 at the HTTP layer.

Session state: one static struct replacing s_upload_manifest/s_upload_operation_id/s_upload_manifest_valid (:98-100): {active, op, image_size, sha256, manifest, accepted, started_us, last_chunk_us, handle, handle_open}. Guarded by s_operation_mutex, taken and released PER REQUEST, never across a socket read. Chunk buffer becomes a single static uint8_t[4096] in .bss, replacing the per-upload malloc (:1127-1133) — removes an allocation-failure branch and 35 malloc/free cycles from the recovery path.
Endpoints: POST /upload/begin (replaces /manifest; re-verifies the signed envelope every call, so it is idempotent and is the resume entry point; returns {op,size,sha256,offset,resumed,chunkSize,sessionExpiresSec}; a fresh size+sha256 differing from the session tears it down and resets offset to 0 — the anti-splice gate). PUT /upload/chunk?op=&offset= (200 {offset,size}; 409 {offset:<device's>} is the self-correcting resync signal, mirroring the BLE path's offset-mismatch reply; 412 no session/op mismatch; 413 overrun; 400 len==0 or misalignment on a non-terminal chunk; 503 mutex busy). POST /upload/finish?op= and POST /upload/abort?op= (explicit abort destroys the partial; the step-5 sweeper keeps it). DELETE the single-shot /firmware and the recovery_firmware_callback_t/recovery_upload_t plumbing — one write path into ota_0.
Pass &fresh (not NULL) to hw1_ota_begin at :954/:966 so the journal binds the transaction to the image. Note for the record: the record.candidate_present guard at :974-979 is NOT dead as the resumable design claimed — it is dead only for a recovery-upload transaction this updater started, and live for staged-file/BLE-written records. Do not delete it. And hw1_ota_record_candidate_matches_verified compares deterministic hw1_ota_manifest_encode output, so re-verifying the same envelope is byte-identical; the design's self-declared risk about breaking legitimate retries is a non-issue.
Finish runs INLINE on the httpd task in this step (re-read 288 bytes from ota_0 and re-run updater_validate_image_prefix; re-run updater_validate_not_downgrade and updater_power_require_safe, because a session spanning hours must not install on a battery that drained; esp_ota_end; verify; finalize). /status is briefly unanswerable during verify — step 5 fixes that. Rewrite the built-in page's upload() as a File.slice loop with 409-driven resync, keeping it a single dependency-free static string.

**Hardware validation:** Script the client with curl so offsets are explicit and reproducible; do not test resume through the browser first. (1) Happy path: begin, 35 aligned 64 KiB chunks, finish; confirm the device verifies, arms trial boot, reboots, and the main app comes up. (2) LINK-DROP RESUME, the headline feature: kill curl at ~40%, re-run /upload/begin with the same manifest, confirm it returns resumed:true and the exact byte offset, resume from there, and confirm the install still verifies — proving the partition hash accepts a spliced-in-time transfer of the SAME image. (3) ANTI-SPLICE: upload 40% of image A, then /upload/begin with a DIFFERENT signed manifest B; confirm offset resets to 0 and resumed:false. Then force the bad case by resuming B's bytes onto A's prefix at the same offset and confirm finish FAILS with HW1_OTA_RESULT_DIGEST_MISMATCH (this also validates the mismatch-mask mapping). (4) ALIGNMENT: send a 1000-byte non-terminal chunk; confirm 400 and that nothing was written. Send a correctly unaligned TERMINAL chunk and confirm it is accepted. (5) Wrong offset: confirm 409 carries the device's actual offset and that a client blindly retrying at that offset succeeds. (6) POWER CUT: pull power at ~50%; on reboot confirm from serial that the device lands in FACTORY (not a half-written ota_0), that boot_reconcile reports main_valid=false without treating it as a read failure, that the recovery AP comes back up, and that /cancel correctly REFUSES to boot the destroyed main. This is the no-cable guarantee — test it on both feathers3 and feathers3_fe, since ota_0 is always encrypted on _fe and the 16-byte write granularity differs. (7) /apply during a live session returns 409 and the session survives untouched.

### 5. Move finish to the control task, publish live transfer progress, and add the session sweeper

**Effort:** large

**Files:** updater/main/updater_main.c (:68-71 control_command_t, :91-103 s_transfer block, :187-194 delete snapshot_progress from hot path, :234-274 status_json, :498-504 feed_control_watchdog guard, :887-908 receive_exact stamping, :1661-1706 process_idle_timeout, :1741-1802 control_task sweeper + supervisor + CONTROL_FINISH_UPLOAD), updater/main/recovery_network.c (:178-218 page, :240-276 /cancel 202 + /apply 409), updater/main/Kconfig.projbuild (UPLOAD_IDLE_SEC, TRANSFER_STALL_WARN_MS)

Now close the last two gaps: the multi-second finish, and the new wedge that a resumable session creates.

FINISH ON THE CONTROL TASK. The only remaining long operation is verification — esp_image_verify plus a SECOND full-partition SHA-256 pass (hw1_ota_idf.c:80-116 and :118-159), two full reads of ~2.2 MB. Route POST /upload/finish through the existing control queue (a new CONTROL_FINISH_UPLOAD) instead of running it on the httpd task. This is the proven path, not a new one: apply_staged already runs that identical verify chain on the control task today with feed_control_watchdog() between steps, and /status does not take s_operation_mutex, so status stays answerable throughout. Decision to record: finish returns 202 and the client polls /status to observe verify -> arming -> reboot, rather than blocking for a response the client would likely never see through the reboot.

BLOCKING ITEM (review B2), the use-after-free. The idle sweeper must never free an OTA handle out from under the httpd task. I verified there is no synchronization in IDF's handle list: esp_ota_abort does LIST_REMOVE(it, entries) then free(it) (esp_ota_ops.c:438-448) while esp_ota_write walks the same s_ota_ops_entries_head and dereferences `it` across a multi-millisecond erase/write (:311-315). Two mandatory rules: (a) the sweeper takes s_operation_mutex with timeout 0 and SKIPS the sweep if it cannot get it — never a blocking take, because the control task is the sole trigger_panic TWDT subscriber (updater_main.c:485-487); (b) last_chunk_us is stamped on every successful recv via the existing note_activity hook (:905), NOT at chunk completion, or a client trickling bytes keeps the httpd task inside esp_ota_write past the threshold with no stamp update. Chunking already makes this far safer than the async-writer design would have — the httpd task is inside a chunk for ~1-2s, not minutes.

THE NEW WEDGE, and it is why the sweeper is not optional polish. Today a dropped link ends the request and record_failure moves state to ERROR. With a session that survives a dropped link, state stays UPDATER_STATE_WRITING — and process_idle_timeout returns immediately unless the state is IDLE or ERROR (verified updater_main.c:1661-1670). A stalled session would therefore pin the updater in WRITING forever and DISABLE the idle-return-to-main logic entirely. Without the sweeper this whole release is a net regression in recoverability. On CONFIG_HW1_UPDATER_UPLOAD_IDLE_SEC (default 180) since last_chunk_us: esp_ota_abort the handle, KEEP accepted and the manifest so a returning client can resume, and move state to ERROR with a detail naming the offset — mirroring housekeepBleUpload's rule that an idle teardown keeps the partial while an explicit abort destroys it. Separately, APPLY_TIMEOUT_SEC must become a session-wide deadline measured from started_us; applied per 64 KiB chunk it is meaningless.
Add a supervisor in the same loop: if a session outlives the session-wide deadline, force it terminal. Nothing else catches a wedged write, and 'server alive, ota_0 half-written, nothing ever times out' is worse than an honest failure.

TRANSFER PROGRESS. Publish a "transfer" object from a lock-free atomic block and REMOVE snapshot_progress() from the hot path — today it takes s_snapshot_mutex with portMAX_DELAY (:187-194) ~500 times per upload, and the TWDT-subscribed control task reads that same mutex every second from process_idle_timeout. Fields: active, expected, accepted (bytes off the socket), committed (bytes esp_ota_write accepted — keep it separate, it is the number resume trusts), stage (receiving|flashing|image_verify|partition_hash|arming|failed), stallMs, elapsedMs, rateBps, idleSec, abortRequested, error, and mainDestroyed — the loud operator-facing flag meaning 'ota_0 is partially overwritten; this upload must complete or the device needs a cable'. Publish expected/started_us with relaxed stores BEFORE a release-store of active; /status acquire-loads active first. accepted/committed are monotonic uint32 so a stale read is only slightly behind. No seqlock.
stallMs is the field that distinguishes 'slow client' from 'wedged', but report it as 0 during image_verify/partition_hash — those are legitimately multi-second flash-read-and-hash passes, and a naive stall reading there makes a healthy verify look like a hang and provokes an operator power-cut at the worst possible moment. Client rule: stage==receiving && stallMs > threshold -> offer /cancel.
/cancel sets an abort atomic BEFORE enqueueing CONTROL_CANCEL and answers 202 immediately, never taking s_operation_mutex. Because chunks are short, cancel_recovery's existing 0-timeout take now contends only with one in-flight chunk, so 'cannot cancel active flash write' becomes a sub-second condition instead of minutes-long — and the ~20 s worst case the review computed for the async design does not arise here, because there is no async response send holding the mutex.
Make feed_control_watchdog structurally safe (:498-504): esp_task_wdt_reset() from an unsubscribed task returns ESP_ERR_NOT_FOUND, the function then CLEARS s_control_watchdog_active, and both accept_manifest (:919) and the upload path (:1038) then refuse ALL writes for the rest of the boot with no re-arm path except the compile-time-gated formatfs. Guard it with esp_task_wdt_status(NULL) == ESP_OK, the pattern the main app's BLE path already uses. A comment is not enough.
Update the page to render accepted/expected as a percentage plus stage and stallMs, polling 1000 ms while transfer.active and 3000 ms otherwise.

**Hardware validation:** All tests need a SECOND station polling /status throughout — that is the feature. (1) Concurrency: during a 35-chunk upload, poll /status once a second from a phone and confirm it answers continuously with a monotonically rising accepted/committed and a plausible rateBps. Confirm it keeps answering through the finish-time verify (this is what moving finish to the control task buys) and that stage walks receiving -> image_verify -> partition_hash -> arming. (2) Confirm stallMs reads 0 during image_verify/partition_hash and does NOT look like a hang. (3) STALL DETECTION: open a chunk request, send a partial body, then send nothing; confirm last_chunk_us stops advancing, stallMs climbs, the sweeper fires at 180 s, state LEAVES WRITING to ERROR, `accepted` is PRESERVED, and a subsequent /upload/begin resumes from that exact offset. (4) THE WEDGE REGRESSION: after the sweeper fires, wait out CONFIG_HW1_UPDATER_IDLE_TIMEOUT_SEC and confirm process_idle_timeout now runs — before the sweeper it would have been disabled forever by the pinned WRITING state. (5) /cancel mid-upload: time from the 202 to the state actually changing; confirm sub-second, and confirm the UI shows abortRequested so the gap reads as 'working'. (6) Use-after-free hunt: run a trickle client (a few bytes per second) across the 180 s boundary repeatedly and confirm no panic and no corrupted heap — this is the exact race the mutex-guarded sweeper prevents. (7) Confirm mainDestroyed appears in /status the moment byte 0 lands and clears only on successful finish. (8) Full end-to-end on BOTH feathers3 and feathers3_fe before shipping.

## Deferred or dropped, with reasons

- TLS on the recovery HTTP server — explicit user decision for this release. Consequence to state plainly in the docs: the HTTP token crosses the air protected only by WPA2-PSK with pmf_cfg.required = false (recovery_network.c:525-527), which has no forward secrecy, so an attacker who captures both the 4-way handshake and an authenticated session and then cracks the PSK offline can still read the Basic header. The credential split does not close that; it closes handshake-only capture, PSK reuse, PSK sharing, and shoulder-surfing.

- The async writer task and httpd_req_async_handler_begin — DROPPED, not merely deferred, and this is the plan's central simplification. Chunking bounds each request to ~1-2s, which is what actually unblocks /status and /cancel; the async machinery would add a confirmed IDF leak (httpd_txrx.c:657-663 allocates async_aux->scratch and the resp_hdrs failure path at :669-673 frees async_aux and async but never scratch — up to 2 KB per attempt given the runtime max_req_hdr_len = 2048 at recovery_network.c:545), a leaked-async-request mode that permanently stops the server accepting connections, and a second task calling esp_ota_* and the journal.

- GET /bootstrap-token — DROPPED. Self-defeating as specified: the window closes on 'the first successful authenticated request', but root_handler (:212) and status_handler (:224) both authenticate and the page polls /status every 3000 ms (:207), so loading the recovery page closes the window before the operator can read the token. It would also be the first unauthenticated endpoint on this server, outside require_authorization and therefore outside the rate limiter, lettting a PSK-holding attacker deny /status and /cancel for free. Disclosure is the USB console (showtoken), same physical-access trust model as the existing resetjournal/formatfs.

- Tier 2 durable power-loss resume — cut from the design entirely rather than deferred, including the note about the 4 reserved-zero bytes in the journal record wire format (leaving an implementation hint for a rejected option is how it gets built anyway). hw1_ota_nvs_commit_to_partition does a read-modify-write-verify of a 384-byte record into a 16 KB nvs partition (partitions.csv line 4) that also holds ap_pass and http_tok; churning it ~35 times per attempt to save a re-upload trades the recovery credential — i.e. a cable — for convenience. Link-drop resume covers the common cases (WiFi roam, tab close, laptop sleep) with RAM state alone.

- Per-chunk crc32 query parameter — dropped. A weaker integrity mechanism layered under a strong one that already runs unconditionally over flash at finish; its only benefit is earlier detection on a link that corrupts past the TCP checksum, and the cost of not having it is one re-upload, which is exactly what the resumable design removes. Also eliminates an optional-vs-required client capability decision.

- App-side `otatoken show confirm` — deferred because it has a hard prerequisite that is out of scope: command RESULTS are not redacted anywhere. System_Utils.cpp:1104-1133 redacts command LINES only, and the serial path sets outputMask = MSG_ROUTE_SERIAL | MSG_ROUTE_FILE (HardwareOne.cpp:2730) after which deliverCommandResult mirrors the result to every non-serial masked sink (HardwareOne.cpp:952-957). Shipping it now would write the recovery token into the file log, turning a superAdmin secret into an admin-readable one. Serial `showtoken` is the disclosure channel this release; a general result-redaction allowlist is its own change.

- HMAC PSK fingerprint in any response — dropped, as the credential-split design half-concluded itself. A 24-bit tag over a 12-character human passphrase is an offline dictionary-narrowing aid with no compensating benefit, and MAC-binding does not help because the MAC is in the beacon. The console `verifypin` covers the operator need without publishing anything. Keep otastatus reporting only the existing boolean (System_OTA.cpp:1240, 1262).

- POST /cancel?force=1 — dropped. It duplicates the serial cancel/reboot commands (updater_main.c:1878-1881) and the queue_reboot_or_restart_directly fallback (:595-613), and its only distinguishing property is guaranteeing a partially written ota_0. An escape hatch whose unique feature is more damage does not belong in the recovery firmware.

- WPA2/WPA3 transition mode on the recovery AP — deferred. It is the only change that would defend against the full capture-then-crack attack, but its failure mode is 'a phone cannot join the recovery AP at all', which in this component is a brick rather than an inconvenience. It needs a survey of the actual client phones first.

- Rate-limiter keying on station MAC via esp_netif_get_sta_list — deferred in favour of peer IPv4 from getpeername. MAC keying is strictly stronger (IP rotation within one association becomes re-association) but adds an API that can fail inside the single httpd task. Revisit once the IPv4 table has field time.

- staged_pair_available()'s two stat() calls on the LittleFS mount (updater_main.c:282-291), invoked from inside boot_reconcile's reconcile loop (:1385, up to 3 iterations) and again at :1468, on the control task under the 15 s panic-armed TWDT with no feed between the stats. A filesystem healthy enough to mount but slow enough to stall is already a panic exposure in the last line of defense. Pre-existing; none of these changes makes it better or worse; deserves its own bounded fix.

- Raising the 12-character PSK minimum (updater_main.c:516, System_OTA.cpp:58) — deferred. 12 printable ASCII is weak against offline GPU cracking of a captured handshake and the WPA2 layer has no throttle and cannot get one, but raising it can break an established provisioning script. Strengthen the usage-string recommendation this release instead of the hard minimum.
