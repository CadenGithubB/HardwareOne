# Hardware One 1.0 release-readiness assessment

Assessed revision: GitHub `main` at `7fd1f996`, tagged v0.99.99.1 (2026-11-08), on the rewritten
history. Assessment date: 2026-11-13. This supersedes the 2026-10-30 draft of v0.99.99 (`aa6508fd`).

Nothing was flashed and no firmware was changed. Every claim below was checked in a detached,
read-only worktree of `7fd1f996`. A build or a host test is never counted as a hardware check.

## 1. Verdict

**Not ready for 1.0 yet. The remaining work is mostly finishing and proving, not building.**

v0.99.99.1 closed a large share of what the October draft flagged. A fresh clone now builds
through `tools/vendor_arduino.sh`. The history rewrite removed the leaked Wi-Fi capture.
SECURITY.md, NOTICE.md, KNOWN_ISSUES.md, docs/COMPATIBILITY.md, issue templates, a host-test CI
workflow and a tiered support matrix all exist. Of the 89 earlier finding groups, 22 are fixed,
13 are honestly documented as known issues, 36 are partly fixed and 18 are still open. Only one is
still rated must-fix.

Three things stop a credible 1.0 today:

1. **The release gate is not real yet.** The only CI run, on the v0.99.99.1 commit itself, failed
   at the build step, so the suite has never run in CI. The gate in RELEASING.md has no hardware
   step, while README tells users that stable rows are hardware-checked before every tag. Every
   stable row's newest hardware record predates the code it ships, and OTA has no pass on any
   current image.
2. **Two confirmed data or trust problems remain.**
   - Photos can silently overwrite earlier photos. The counter restarts at every boot and
     timestamps only have one-second resolution.
   - Git history still contains internal security documents, and old refs on GitHub may still
     hold the leaked credentials.
3. **Unification has a pattern problem.** The core layers have one owner each: command execution,
   authorization, settings writes, the event catalog, file access control and the BLE stack. The
   layer above them, where each surface reports results and lists things, is half migrated almost
   everywhere. The largest single theme is truthfulness when something fails. A refused action
   often shows nothing, shows a bare "ERROR" or an HTTP 400, or is even reported as success.

Realistic distance: one focused cleanup release, then one hardware qualification pass on the
stable rows. Most of it is bounded work, and many items are S-sized (under a day each).

## 3. Worthwhile before 1.0 (P1), grouped by theme

Each theme is one bounded piece of work with one owner. IDs point to Appendices A and B.

**T1. Failures must say why, on every surface** (the biggest unification item)
- The executor's verdict is lost on the way out:
  - `/api/cli/batch` and BLE drop it.
  - `hw.postFormText` turns a refusal into a bare "HTTP 400".
  - More than six web pages and about 25 native call sites each re-guess success. (CMD-1, WEB-1, WEB-2)
- 85 handlers return a bare `"ERROR"` and put the reason only on the live stream. Automations are a
  prominent case. (CMD-2, UA-5)
- The executor's failure test is a prefix list:
  - JSON errors and `features <unknown> on` are stamped OK.
  - So are invalid conditions and a truncated `espnowlist`. (CMD-3, FEAT-2, G-56)
- The local display has two wrappers. 54 call sites use the fire-and-forget one, which drops
  refusals silently. G2 has about 11 more. (SURF-1, CMD-7)
- Help text: 28 hand-typed usage hints name commands that don't exist. The drift gate doesn't scan
  web, G2 or async call sites. The P4X-EYE Speech page calls missing commands, and its model upload
  posts to an unregistered `/api/upload`. (CMD-4, CMD-8, WEB-3)
- Done when the executor returns `{ok, reason}` to every transport, every surface shows the reason,
  and `executeOLEDCommand` no longer exists.

**T2. Settings and feature toggles: one meaning for "enabled"**
- `features <id> on|off` is a second toggle path:
  - Per feature it flips the master switch or the autostart flag.
  - It skips the owner's live stop, and it reports "disabled (+NKB freed)" while the service keeps
    running. (SET-1, FEAT-1, RAD-2)
- Fields written through `setSetting` with no registry row are never saved, for example the G2 stream
  size and ESP-SR tuning. (SET-2)
- Runtime-only overrides leak to disk on the next unrelated save, for example the mesh failover
  role. (SET-3)
- The setup wizard commit skips the name and metadata checks. MQTT discovery then builds JSON from
  those strings without escaping. (SET-5)
- `setting_changed` has a non-unique subject, and some paths post it twice or not at all. (SET-6)
- "enabled" or "active" means master, running or autostart depending on who answers. The G2 ESP-NOW
  "Auto Start" row actually flips the master switch. There are four bool parsers, and some invert
  or write on a bare query. (RAD-3, RAD-4, RAD-5)
- `sensorautostart`, `detect apply` and the archetype seed write around `setSetting`. (FEAT-4)
- The admin flags on equivalent commands follow no rule. (CMD-5)
- Done when every feature row exposes both axes, every toggle goes through the owner's command, and
  a host test asserts every `setSetting` key has a registry row.

**T3. Sensors: one roster, one data shape**
- MQTT and Home Assistant discovery for thermal, ToF and IMU name pre-envelope keys. Thermal never
  fits its 2 KB buffer, so those entities never show a value, and a host test pins the wrong
  template. (SEN-1)
- `espnowsensorstream thermal|apds|camera|microphone on` replies OK and streams nothing. (SEN-2, ledger N-12)
- `/api/sensors` is half migrated to the envelope. (SEN-5)
- RTC time is shown three ways, and the conversion is duplicated. (SEN-4)
- `<x>Enabled` blocks a manual start only for thermal. (SEN-6)
- Automation variables drift from the sensor model, for example `MOTION` reads APDS. (SEN-8)
- At least six to twelve hand-maintained sensor lists disagree on membership, ids and what "running"
  means. (SURF-2, SEN-3) A per-sensor descriptor is the real fix, but it is L-sized and can wait;
  fixing the user-visible drift above cannot.

**T4. Notifications: readable and complete**
- 42 of the 72 notifying kinds show raw tokens like `ota_rolled_back: x` on every surface. That
  includes 13 of the 15 ALERT kinds. `tools/showcase/showcase.py` already has wording for all 175. (EVT-1)
- Several fault kinds have no rule and can't be opted into: SD write failure, sensor auto-disable,
  settings save failure, low heap, low space, Wi-Fi connect failure, ring and G2 disconnects. (EVT-2)
- Serial login-gate failures skip `login_fail`. (EVT-3)
- A commanded Wi-Fi disconnect likely posts twice. (EVT-4)
- The debug mask has two persistent owners, which KNOWN_ISSUES already lists. (EVT-5)

**T5. Automations**
- The web editor cuts multi-word names to the first word. (UA-1)
- Export cannot be re-imported for time, manual or boot triggers, which breaks backup and restore. (UA-2)
- Argument keys match by substring, so an edit can overwrite a different automation. (UA-3)
- `automations.json` has no single mutation owner. (UA-4)
- Deleting a user leaves their automations running under a reusable name. (UA-7)
- Condition variables are not validated and live in four lists. (UA-8)
- Password length rules differ by surface, so a password set on the web can be impossible to type on
  the display keyboard. (UA-6)

**T6. Files and captures**
- G2 Snapshot is a second photo pipeline. It writes to a `/sd/PICTURES` that nothing creates and
  fails silently. (FILE-2)
- The LittleFS reserve meant to protect settings and users is honoured only by log writers. Mic
  WAVs, ESP-NOW received files, uploads and images each apply their own rule. (FILE-3)
- The GPS track picker is duplicated, lists every track twice and misses the SD overflow. (FILE-4)
- The Logging page cannot reach logs that overflowed to SD. (FILE-5)
- The ESP-NOW remote browser scrapes text beside the structured protocol. (FILE-6, WEB-5)
- **Security:** recording names and remote ESP-NOW device names reach `innerHTML` or inline
  `onclick` unescaped. Any non-guest user can upload into `/sd/VIDEOS`, so this is a stored-XSS
  path. (WEB-4, ledger D-29)

**T7. Network services after boot**
- HTTP and MQTT autostart run once, at boot. A headless FeatherS3 or Feather V2 whose router comes up
  after the 150 s boot hunt, or that rejoins through `openwifi`, `radiopower on` or a C6 restart,
  stays without a web UI or MQTT until reboot. On a headless stable profile those are the only
  interfaces. (RAD-1, rated P0 by the lane, P1 by its reviewer)
- A refused `openg2` still persists `bleMode=client`. (RAD-6)

**T8. Install, recovery and robustness**
- A used board still halts with `FATAL: Filesystem initialization failed` and no fix printed. The
  docs now explain it, but the firmware message should name the fix. (G-08)
- There is no identity or partition-layout check at cable-flash time. (G-30)
- Backup leaves out NVS, the notification policy and the capture key while the user guide oversells
  it. (G-31)
- The login salt is the device key, so a flash-UID read failure can lock out every account. (G-40)
- Task watchdog:
  - It panics only on OTA-layout images, and only for IDLE starvation.
  - Cable images, including P4X-EYE and the QT Py and XIAO rows, never reboot on a hang.
  - No image detects an application-task deadlock.
  - Run the existing `--wdt-soak` 24 h per stable row, then promote panic and main-loop
    subscription; until then add a KNOWN_ISSUES row. (G-11)
- Task stacks under 1.5 KB free (G-45), the P4 composite heap low-water (G-46), BLE open/close drift
  on S3 and classic (G-43), and the S3 MSPI clock-sync change, which is host-tested only and missing
  from CHANGELOG (G-48, DELTA-2).
- Light sleep ignores the API return value and has no hardware record. (G-49)
- No power-cut test exists for any atomic-save claim. (G-41)
- No soak record exists for any profile. (G-42)
- Ledger P1s:
  - `loadIpBans` marks the ban list loaded before parsing, so a corrupt file wipes all bans. (N-52)
  - MQTT TLS defaults to off while the command envelopes carry device passwords. (D-36)
  - The web CLI stores typed `login user pass` lines in browser localStorage. (N-38)
  - The login PBKDF2 salt is device-wide and derivable, at 10k iterations. (N-26)
  - ESP-NOW history buffers are sized wrongly for the 32 MB P4 and the 2 MB-PSRAM boards. (D-45, D-46)
  - Three OTA recovery weaknesses. (N-44)

**T9. Connectivity qualification** (hardware runs, not code)
- Fresh ESP-NOW discover-confirm pairing. Its control frames are single-shot and the state machine
  has no test. (G-32)
- The G2 orphan recovery and the R1 wedge fix, which have no hardware record. (G-33, G-34)
- Multi-hop relay and channel follow. (G-35)
- ESP-NOW file transfer over the radio path. (G-36)
- Induced C6 outage. (G-37)
- Peers leaving range and returning.
- Any path without a run should be labelled experimental in the matrix.

**T10. Docs and release record**
- Board tables that contradict code. (G-07)
- Compatibility statement gaps: COMPATIBILITY.md exists, and the C6 install path disagrees across
  three documents. (G-12, DELTA-8)
- The handheld P4 contract was never built and still compiles automations and the headline local STT
  out. (G-13, DELTA-7)
- Shared-header defaults ship features every contract disables. (G-15)
- References to unreadable documents. (G-22)
- Version-site drift. (G-23)
- Thin build provenance. (G-27)
- OTA documentation errors. (G-29)
- RELEASING.md lacks the 1.0 process and contains a build instruction the build now refuses. (DELTA-5)
- The `c6console` rename. (G-21)

## 4. Unification scorecard

Answering the direct question "is it unified?" per area:

| Area | Core owner | Above the core | Worst user-visible gap |
|---|---|---|---|
| Notifications | Unified: one catalog, one ring, one resolver, one message to every surface | Text and rules are per-kind switches outside the catalog | Raw tokens on 13 of 15 alert kinds |
| Settings | Unified write path: every editor sends a registered command, one schema builder, defaults match | Two toggle axes mixed; unregistered fields; wizard bypass | `features x off` reports freed memory while the service keeps running |
| Commands | One executor, one authorization funnel, one OK stamp | Verdict and reason lost on the way to web, BLE, display and G2 | Refusals look like success or say nothing |
| Users and roles | Unified: one roster reader, one password function, every surface issues user commands | Length rules and login side effects per transport | Web password not typeable on the display |
| Radios | BLE well unified; boot autostart consistent | No post-boot reconcile; three meanings of "enabled" | Headless device without a web UI until reboot |
| Files | Access control unified: one rule table, guarded VFS, shared listing and viewer | Each capture type picks its own folder, name, admission and retention | Photo overwrite; G2 snapshots silently lost |
| Sensors | Data and lifecycle unified: private caches, snapshot accessors, one start/stop queue, one envelope | 6 to 12 hand-kept sensor lists | Home Assistant thermal/ToF/IMU never show values |
| Feature availability | Registry rows never `#if`-wrapped; wizard reads the registry | 7 parallel capability lists; one pointer per row for a two-axis model | "Enabled" true for a feature its owner refuses to start |
| Events and logging | One catalog for kinds; one debug-flag vocabulary | Two durable event logs; two owners of the debug mask | Debug mask returns after reboot |
| Web | One auth/guest gate; status endpoints share JSON builders | Client result handling per page; scraping CLI text | Failure reasons never shown; stored XSS via names |
| Automations | All editors go through the `automation` command | Wire format and file handled ad hoc | Export can't be re-imported; edits can hit the wrong rule |
| Surfaces | Same executor and shared cores for files, JSON, power, versions | Each surface rebuilds lists and success checks | Display swallows refusals at 54 sites |

The pattern is consistent. Owners exist and are respected for writes. What drifts is how results
and lists come back out. That makes T1 (result truthfulness) and the roster consolidation in T3
the highest-leverage cleanup, because each removes a whole class of drift rather than one bug.

## 6. Order of work, with stopping conditions

1. **Gate first** (P0-1). Fix the CI include, add the Python suites to CI, triage the two web tests
   and add the hardware step to RELEASING.md. Stop when CI is green on main.
2. **Data and trust** (P0-3, P0-4, the WEB-4 XSS, ledger N-52). Stop when each has a host test or an
   owner confirmation.
3. **Result truthfulness** (T1). One executor change carries `{ok, reason}` to every transport; then
   the display wrappers, the bare "ERROR" returns and the batch endpoint. Stop when
   `executeOLEDCommand` is gone and a host test asserts no handler returns a bare "ERROR".
4. **Toggle and settings semantics** (T2, T7). Stop when every feature row reports both axes, a
   registry test covers every `setSetting` key, and services reconcile on `GOT_IP`.
5. **User-visible drift** (T3 MQTT/ESP-NOW/API, T4 text and rules, T5, T6). Each item is S or M.
   Stop at the listed items. Don't start the sensor descriptor refactor here.
6. **Docs and record** (T10, the watchdog KNOWN_ISSUES row, CHANGELOG for the S3 clock change).
7. **Release candidate.** Tag `1.0.0-rc1` from a clean tree. Run the gate including hardware on
   every stable row, the 24 h `--wdt-soak` per stable row, the T9 runs and one power-cut run on
   FeatherS3 and one 8 MB board. Fix only regressions, then rc2 if needed.
8. **Promote** the exact rc commit to 1.0.0 when the checklist below passes.

Stop expanding scope at step 5. Anything new found during the RC goes to KNOWN_ISSUES unless it is
data loss, a security hole, or a crash on a stable row.

## Appendix B. Unification audit findings (11 lanes)

Every P0/P1 finding was given to a reviewer told to refute it. "Review" shows that verdict; P2 findings were not reviewed. Effort: S under a day, M a few days, L a week or more.

### SETTINGS

At the RC (7fd1f996), the way settings get written is mostly unified. The web settings page (both of its renderers), the OLED/LCD SettingsEditor, the G2 Settings and G2 Camera pages, the bonded remote editor, MQTT and automations all send a registered command. The command goes to handleSettingCommand or a dedicated service command, then to setSetting/finishSettingChange. The schema has one builder. The editors never build a command name from a JSON key, and host tests enforce that. Outside the owners and test harnesses, direct gSettings writes are down to about a dozen sites. Constructor defaults match registry defaults: of 322 rows scanned, none really differ. The weak spots are around that core rather than in it. (1) The feature registry still points `features <id> on|off` at the old single flag. That flag is a mix of *Enabled and *AutoStart fields, and the call goes through setSetting with no entry, so it skips the live stop that `<x>enabled 0` performs. It still replies "disabled (+NKB freed)" while the service keeps running. (2) Some fields are changed with setSetting but have no registry row (g2StreamWidth/Height, srAfeGain/AgcMode/VadMode), so they are silently never saved. (3) Runtime-only overrides are written into saved fields (mesh failover's meshRole), and the next unrelated save of any setting writes them to disk. (4) The setup wizard's commit applies identity and metadata strings with raw setSetting, skipping the checks that the dedicated commands enforce. MQTT discovery then builds JSON from those strings without escaping. (5) The settings page has two separate renderers. The one used for sensor and app modules reads only bare comma lists, so the micSource dropdown (value|label options) shows wrong labels and sends values that cmd_micsource rejects. (6) The setting_changed event uses the human label as its subject, and 18 settings are labelled just "Enabled". Some paths post twice, debug and web per-user paths post nothing, and the event catalog promises subject=key. Smaller drift: ranges are checked again in dedicated commands and have drifted, the OLED/LCD editor cannot edit about 28 float/u8/u16/u32 settings, restart-required exists only as label text, and several docs that code comments point to are missing. Debug settings are deliberately split into debug.json (setDebugSetting). KNOWN_ISSUES already lists the double owner of the debug mask. Nothing in this lane is P0. Hardware behaviour and the phone app's own settings UI are unverified.

### SENSORS

The sensor subsystem is half unified at the RC. The data and lifecycle layers have one owner and one path. Every driver exposes a private cache through a `<x>CacheSnapshot` accessor, and no consumer outside the drivers touches a cache or its mutex. Start and stop go through `requestSensorStart`/`requestSensorStop` and the queue worker, and OLED, G2 and web all start sensors through the same authorized `open<id>`/`close<id>` commands. Every `<x>BuildDataJSON` opens with `sensorEnvelopeBegin`. Above that layer there is no single per-sensor descriptor. At least 12 hand-maintained per-sensor lists exist: `sensors json`, the sensor status JSON, the autostart table with heap costs, the feature registry, processAutoStartSensors, the G2 rows, the ESP-NOW specs, MQTT local/discovery/peer, the sensor-log bits, web `/api/sensors`, the OLED list and the automation resolver. They have visibly drifted. The clearest user-visible result is MQTT. Home Assistant discovery for thermal, ToF and IMU still points at pre-envelope keys, and the thermal state never fits its 2 KB buffer, so those entities can never show a value. A host test even pins the wrong `tof.distance` template. ESP-NOW `espnowsensorstream thermal|apds|camera|microphone on` replies OK but streams nothing. The RTC shows UTC on G2, local time on OLED, CLI and web (web has its own second conversion), and naive UTC in `sensors json` and MQTT. The `<x>Enabled` setting blocks a manual start for thermal only. Autostart has three writers, one of which bypasses `setSetting`. Web `/api/sensors` is half migrated: the gps, presence, rtc and input readings are still hand-rolled, and APDS is missing. The automation variable MOTION reads APDS proximity, not the presence sensor. None of this is P0. The shared default build and every stable profile compile no data sensors: `xiao_s3` and `p4x_eye` use I2C level 0, and the shared custom section has GPS, IMU, ToF, thermal, APDS, FM, RTC and presence off. These defects are reachable only on the candidate QT Py sensor appliance (GPS, presence, ToF; MQTT off) and on custom builds. That makes them P1/P2 consistency debt, not release blockers. Nothing here was built, run or hardware-tested.

### SURF (cross-surface parity)

At the RC (7fd1f996), the base layer is well unified. Every surface (serial, web /api/cli, local display, G2, MQTT, phone console, ESP-NOW) changes state through the one command executor, which owns the OK:/Error: verdict. Settings writes all resolve to the setting's registered cmdKey command and are range-checked once, server-side, in handleSettingCommand. Files, JSON pretty-printing, the power-mode table, versions/status JSON and the user roster each have one shared owner. OLED, P4X-EYE LCD and Waveshare touch share one UI behind HAL_Display backends. The drift is in the layer above, where each surface rebuilds its own list or verdict instead of reading the owner's. The worst user-visible case is the local display: it has two command wrappers, and 54 call sites (power mode, sensor start, G2 connect, ESP-NOW role and channel, light sleep, LED, FM radio) still use the fire-and-forget executeOLEDCommand, which drops refusals into a debug log. Forty other call sites already use oledRunCommand, which shows the refusal as a toast, so this is a half-finished migration, sometimes inside a single menu. Sensors are the weakest area. At least six hand-maintained sensor lists (sensors json, G2 rows, OLED overview, web dashboard JS, MQTT, ESP-NOW specs) disagree on which sensors exist, what their ids are and even what "running" means: APDS has three definitions, and an ANO-encoder build drops out of `sensors json`. ### CMD (commands / CLI layer as the common API)

At the RC (7fd1f996) the command layer has one execution path. Every transport (serial, web, BLE, OLED/LCD, G2, MQTT, ESP-NOW, UART, voice, automations) submits to the single cmd_exec executor. Authorization is centralized, the OK: stamp has one chokepoint, and the registry drift gates (`command_registry.py audit` and `reference --check`, both clean today) run in CI. Unification breaks down after a command finishes. The executor computes a success/failure verdict, but /api/cli/batch drops it per command, the BLE reply drops it entirely, and `hw.postFormText` turns a web refusal into a bare "HTTP 400". So at least six web pages and about 25 native call sites each work out success again with their own regexes or strncmp prefixes, and they do not agree. The executor's own failure test is a prefix list, so JSON error payloads count as success: there are three different error envelopes, `features <unknown> on` is stamped OK because the exact-match special case is dead, `validate-conditions` returns OK on invalid input, and `espnowlist` silently truncates its JSON at 1 KB. There are 85 bare `return "ERROR";` sites that put the reason only on the live broadcast stream. MQTT, OLED toasts, G2 and every web page except the CLI and LLM pages therefore get "ERROR" with no reason, which contradicts CONTRIBUTING.md:137. Usage text has two sources of truth: registry rows are correct, but 254 hand-typed "Error: invalid arguments — Usage:" strings drift, and 28 of them name spellings that do not resolve (`espnow pair`, `user changepassword`, `fmradio tune`, `llm generate`). Admin flags on equivalent persistent settings follow no stated rule (micautostart and per-sensor *autostart are user-level, cameraautostart and wifiautostart are admin, oledenabled is the only user-level *enabled). Three implementations of a bool setter coexist. About 53 OLED and 11 G2 call sites still run commands fire-and-forget and swallow refusals, although CONTRIBUTING:141 requires oledRunCommand. The BLE side is the most unified concern in the lane: one stack owner, matching open/close verbs for glasses, ring and phone, a per-peer auto-reconnect setting with a user-close latch, and one BleLinkStatus vocabulary shared by OLED, G2, web and the system JSON. Boot is also consistent: every service starts on enabled && autostart through ramFlushResolve, with one atomic hand-off to the background Wi-Fi connect. The weak point is what happens after boot. HTTP and MQTT autostart are evaluated once, at boot, and only if Wi-Fi happens to be connected at that moment. Nothing re-applies them when Wi-Fi joins later: not the GOT_IP edge, not openwifi after closewifi, not `radiopower on`, and not the C6 companion's late bring-up or restart. A headless device that boots while its router is down therefore never brings up its web UI or MQTT without a reboot. That is the one P0 candidate in this lane. The second family is setting-axis drift. The feature registry binds http and bluetooth to their autostart flags but wifi, espnow and mqtt to their master switches, and it skips the owners' live stop actions. "enabled" means master, running or autostart depending on which MQTT producer you ask. The G2 ESP-NOW "Auto Start" row actually toggles the master switch, and ramflush compares ESP-NOW against the wrong flag. The third family is CLI validation drift: at least four bool parsers, so `espnowenabled on` turns ESP-NOW off and a bare `wifiautoreconnect` disables auto-reconnect. A refused `openg2` also silently rewrites the saved BLE boot role. Naming (flat g2* commands vs `ring status` / `phone status`, *read aliases, camelCase httpAutoStart, ERROR: vs Error:) and stale usage text are P2. Not verified on hardware: whether the Arduino driver rejoins after a failed boot hunt, and how often the C6 comes up late; both affect how severe RAD-1 is in practice, not whether the code path exists.

### FILES (file browsers, viewers, upload/download, permissions/visibility, capture types/loca

The access-control core is genuinely unified at the RC. One per-path rule table and the guarded VFS decide every read and write. Web, OLED/LCD and G2 now all mutate files through the same filerename/filedelete/mkdir commands. The web /api/files/list, the CLI and BLE `files json` share one listing envelope, and all four viewers share one JSON re-indenter. DirectoryReader owns virtual mounts. Bonded web and OLED peer browsing share the structured FsList protocol, and transcripts and notes share one private-owner path policy. What is not unified is the capture side. Each capture type picks its own folder, naming scheme, storage-admission rule and retention rule. That produces one confirmed data-loss defect: ImageManager falls back to a per-boot counter (img_000000.jpg) when the clock is invalid, or uses 1-second timestamps, and promotes with replaceFileGuarded, which overwrites an earlier photo. This is reachable on the P4X-EYE profile (camera on, SD off). The G2 lens Snapshot is a second photo pipeline that bypasses ImageManager. It writes to a hard-coded /sd/PICTURES that nothing creates, so it fails silently on a fresh card. The VFS LittleFS reserve, documented as protecting settings and users files, is respected only by log writers. Mic WAVs (LittleFS when no SD), ESP-NOW received files (up to 4 MB each), web uploads (up to 90% of free space) and images (their own 100 KB constant) each apply their own rule or none. Domain views drift from the generic browser in several places. The web and OLED GPS track pickers duplicate one scan that lists every track twice (the host fixture hides this) and ignores the SD overflow tier. The Logging page cannot reach overflowed captures. The web ESP-NOW remote browser still scrapes the human `files` text beside the structured protocol, and never completes on an empty or failed folder. Smaller drift: four file-kind classifiers with different case rules, different listing-visibility rules (dotfiles, admin-only paths, .tmp/.bak), dead FileManager mutators that bypass the command path, quote-in-name dead ends, and inconsistent download error statuses. Nothing here was hardware-checked. The defects are from reading the code, and reachability depends on the profile flags noted.

### FEAT

Feature availability is only partly unified at the RC (7fd1f996). The core pieces are sound. System_FeatureRegistry is the declared owner, its rows are never #if-wrapped, and `features json` has a compile-time overflow guard. The setup wizard builds its rows from the registry, and the host build tool reads its choices from the editable section of System_BuildConfig.h instead of keeping a second table. The registry's model is still incomplete. Each row has one `enabledSetting` pointer, but the settings already use two axes (<x>Enabled for admission and <x>AutoStart for boot). Rows point at the admission flag for wifi, espnow, mqtt, oled, i2c, automation and edgeimpulse, and at the boot flag for http, bluetooth, every sensor, camera, mic, espsr and llm. As a result, "enabled" in `features json` can be true for a feature its owner refuses to start. The G2 page labels this field "Auto Start" even for OLED, where it actually flips the display's master switch. The wizard hand-codes which rows are startup rows. Around the registry there are at least seven hand-maintained capability lists with different ids and coverage: /api/buildconfig (fetched by the web settings page but never read), /api/settings features, /api/sensors/status xCompiled, the ESP-NOW CAP_* masks built twice, the OLED per-mode availability switch, the G2 sensor rows, and the I2C `sensorautostart` table. The last one duplicates registry rows and writes settings directly. Three paths write feature settings without going through setSetting or the feature-toggle event. Reports for compiled-out features are inconsistent: most command families vanish and answer "Unknown command", a few answer "Error: not in this build", and `features <unknown> on` is stamped "OK:". I found nothing that rises to P0. The defects are truthfulness and maintenance-risk problems, and the user-visible ones fall mainly on the handheld/G2 and web/app surfaces. CMake source selection versus C++ guards stays hand-mirrored, but the mirror is fail-fast and conservative (CMake includes a superset of sources). It is noted as unverified, not as a defect. No hardware behaviour was checked.

### USERS_AUTOMATIONS

I reviewed the RC worktree at 7fd1f996 without changing anything. Users and roles are mostly unified. The display user managers (OLED/LCD and G2) and the web Settings page read the roster from System_User's readUserRoster and change accounts only by issuing the real user* commands, so the executor's one authorization funnel (live role, guest, forced password change, admin and super-admin gates) applies on every surface. isValidUser is the single gate for bans and reserved names. Password change goes through one function, userChangePasswordCore, and self-registration through one intake. What drifts on the users side is policy at the edges: the password length rule in isValidPublicPassword is skipped by change, reset and first-setup, and the display keyboards cap at 32 characters while web and G2 allow 64, so a password set on the web can be impossible to type on the handheld display. The display user managers also offer different action sets with no stated reason, three legacy /api/admin approve/reject/pending routes are still registered with no caller, and each transport re-implements its own login side effects. Automations are much less unified. Every editor (web, OLED wizard, G2, CLI) does go through the `automation` command, and summaries and event pickers are shared. But the command wire format and the stored file are handled ad hoc. The web form sends an unquoted name, so multi-word names are cut to the first word. Export writes v1 type names (time/manual/boot) that `automation add` rejects, so backup and restore fails for timed and manual automations. Argument keys are found by plain substring search, so `id=` inside a command can redirect an edit to a different automation. automations.json is edited by string splicing with prefix id matching and no lock held across read-modify-write, while users.json has a proper mutateUsersJson owner. Automation failures return a bare "ERROR" and only broadcast the reason, so web, OLED and G2 users never see why something failed. Automations are owned by a username string and survive deletion of that user. Nothing here was verified on hardware or in a browser; all findings come from reading code.
