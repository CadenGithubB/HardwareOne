1 · Task / thread topology

A lightweight Wi-Fi-context callback copies frames into a ring. espnow_task does almost everything (drain + dispatch + sweeps + heartbeats + bond orchestration) in a 10 ms polled super-loop. Only a few heavy handlers are deferred to the cmd_exec_task serial worker.

2 · Receive pipeline (v4_try_handle_incoming)

Every inbound frame passes these stages in order: header sanity, CRC (skipped for encrypted frames), mesh-fingerprint scope, BROADCAST_AUTH HMAC, SESSION_FRAME AEAD unwrap, reassembly, dedup, then table dispatch with REQ_* gating.

headerLen ok?"}
    B -->|no| DROP1["drop"]
    B -->|yes| C{"SESSION_FRAME?"}
    C -->|no| D{"CRC16 matches?"}
    C -->|yes| E["skip CRC
(AEAD tag is integrity)"]
    D -->|no| DROP2["drop"]
    D -->|yes| F
    E --> F{"meshFingerprint known?
(0 = no scope, allowed)"}
    F -->|unknown mesh| DROP3["silent drop"]
    F -->|ok| G{"BROADCAST_AUTH flag?"}
    G -->|yes| H["verify HMAC-SHA256 vs
mesh group key, strip 32B tag
then wasAuthenticated=true"]
    G -->|no| I
    H --> I{"SESSION_FRAME flag?"}
    I -->|yes| J["find ACTIVE session by sessionId+src
sessionUnwrapFrame() AEAD-decrypt
+ replay-window check
then plaintext, wasSessionEncrypted=true

    I -->|no| K
    J --> K{"fragCount > 1?"}
    K -->|yes| L["reassemble into PSRAM slot

3 · Session lifecycle

KEY_EX (opcodes 10-12) is the prerequisite that stores the peer's Ed25519 long-term key. Sessions then negotiate forward-secret AEAD keys via signed ephemeral X25519. REKEY auto-fires on volume or age.

stateDiagram-v2
    [*] --> NONE
    NONE --> ESTABLISHING: SESSION_OPEN sent/received
(requires peer KEY_EX done)
    ESTABLISHING --> ACTIVE: SESSION_CONFIRM
(Ed25519 verify + X25519 ECDH + KDF)
    ACTIVE --> REKEYING: REKEY (txSeq>=10k OR age>=1h)
    REKEYING --> ACTIVE: fresh keys staged,
old accepted briefly
    ACTIVE --> CLOSED: explicit teardown
    CLOSED --> [*]

4 · Send-path call graph

Top-to-bottom flow: an outbound send request (sensor poll · user CMD · timer tick · sync event · bond heartbeat · …) enters at ①, gets dispatched at ②, framed at ③, AEAD-sealed at ④, and finally written to the radio at ⑤. Late 2026-05 update: the encrypt-or-wait foundation is complete. v4_send_payload_smart is now strictly encrypt-or-fail (no plaintext fallback). The strict-encrypt typed wrappers (text / user_sync / time_sync) now route through smart instead of bypassing it. v4_send_encrypted_or_queue auto-kicks KEY_EX when no peer identity exists (was previously hard-fail) and auto-kicks SESSION_OPEN when no session — so first contact with any same-mesh peer just works (frame queues + handshake auto-completes + frame drains, all from a single send call). Cross-mesh peers can't establish KEY_EX (bootstrap HMAC mismatch), so cross-mesh sends silently fail at the pending-frame timeout sweep — correct: different mesh = locked out. Broadcasts still fan out per-peer with BROADCAST_AUTH HMAC (no per-peer session for FF:FF:...). Raw v4_send_frame remains reserved for ACKs and handshake frames (can't be encrypted by the layer they implement).

Why all unicast callers now flow through v4_send_payload_smart: smart used to have a plaintext fallback ("encrypt if session available, else send cleartext"). That was load-bearing for "best-effort" callers but unacceptable for strict-encrypt callers (user_sync carries hashed credentials, text/time_sync had documented "refuse rather than leak" contracts). So strict-encrypt callers used to bypass smart and call the encrypted layer directly. Late 2026-05: smart's plaintext fallback was deleted. Smart is now strictly encrypt-or-fail, which is exactly what the strict-encrypt callers want — so they now route through smart too. The diagram collapses to a clean tree: BOND, T_BE, T_STRICT, FILE → SMART → ENCQ/ENCCHUNK → WRAP → FRAME → RADIO. One spine, no bypasses except the unavoidable ones (broadcasts use a different crypto primitive; raw frames ARE the layer underneath).

Encrypt-or-wait foundation: if a caller sends to a peer it has never handshaked with, v4_send_encrypted_or_queue queues the frame, kicks KEY_EX, and the chain auto-completes: KEY_EX_REPLY → peer identity persisted → SESSION_OPEN kicked → SESSION_CONFIRM → pending-frame ring drains the original frame AEAD-encrypted. From the caller's perspective, the first send takes ~300ms; all subsequent sends use the live session and are instant. Cross-mesh peers can't pass the KEY_EX HMAC check, so cross-mesh sends silently fail at the pending-frame timeout sweep — correct: different mesh = locked out by design.

Broadcasts bypass smart because there's no per-peer session for FF:FF:FF:FF:FF:FF — AEAD isn't applicable. They use BROADCAST_AUTH HMAC (group-key tag over header + payload), proving mesh membership without per-peer state.
Raw frames (ACKs, KEY_EX_*, SESSION_OPEN/CONFIRM/REKEY, TOPO_*) skip every middle layer because they are the layer underneath — they bootstrap the encryption + ACK semantics that everything else depends on.

Change history:
• 2026-05-23 audit: Removed ghost wrapper v4_send_worker_status (deleted 2026-05-21). Added bondSendEncrypted, sendFileToMac, the broadcast tree. Merged the strict-encrypt typed wrappers into one node.
• 2026-05 encrypt-or-wait foundation: Added espnowprobe CLI (KEY_EX-as-reachability-probe). Made _or_queue auto-kick KEY_EX when no peer identity exists; KEY_EX_REPLY handler now auto-kicks SESSION_OPEN when pending frames are waiting. sendFileToMac's "session-ready snapshot" wart removed.
• 2026-05 plaintext fallback removal: Deleted the three return v4_send_chunked(...) fallbacks from v4_send_payload_smart. v4_send_text / _user_sync / _time_sync now call smart instead of branching themselves. meshSendEnvelopeToPeers and bigsend CLI migrated to smart. v4_send_chunked deleted (zero callers remained). Saved ~4 KB binary.

5 · Bond mode — implicit state machine (reverse-engineered)

This diagram does not exist as code. Bond state lives in ~20 boolean flags on EspNowState, set by RX handlers and polled/cleared by super-loop steps 9b-9k. This is the behavior reconstructed as the FSM it implicitly is — the target shape for a possible future explicit-FSM refactor.

The facade layer is the answer to the question "which file do I touch when the OLED status screen needs the same data the web UI shows?" — touch the facade, not the underlying module. Adding a new accessor in SelfDevice:: or MeshPeers:: automatically makes it available to all UI surfaces (web, OLED, G2, MQTT, CLI) at once.

Notable absences from this chart by design: the build/ tree (auto-generated), the managed_components/ tree (vendored third-party), sdkconfig* files (build-target switches), and the various .md reports under docs/ (commentary, not code). Anything else missing is probably worth adding if you notice it.

7d · Sensor file pattern (per-chip triplet)

Each I2C sensor follows a consistent four-file pattern: the driver, the public header, an OLED rendering helper, and a web rendering helper. This keeps the per-chip UI integration close to the driver. Once you understand one sensor's layout, the others read the same way.
